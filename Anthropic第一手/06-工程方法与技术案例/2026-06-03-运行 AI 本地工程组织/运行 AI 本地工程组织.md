在 Code w/ Claude SF 2026 大会上，Claude Code 与 Claude Cowork 工程总监 Fiona Fung 讲述了：当智能体式编码成为团队的默认工作方式后，流程与组织结构发生了怎样的改变。

[视频：运行 AI 原生工程组织](https://www.youtube.com/embed/igO8iyca2_g?start=433)

多年来，工程带宽一直是构建应用最昂贵的部分。我们过去围绕软件规划与交付所建立的全部流程——先是瀑布，后是敏捷——都是围绕这一成本搭建的。

我的职业生涯始于 2000 年代初，当时在做 Visual Studio。那个年代，我们以 CD-ROM 形式交付软件，并定下严苛的制造截止日期。一旦能够在线分发软件，我们就开始持续不断地增加更新。如今我们正再次改变工作方式，而这一次，改变的是编写软件所需的时间和人力。

在 Claude Code 团队，写代码、写测试、做重构，已经很少再拖慢我们的节奏。但是，当智能体式编码消解了"亲手敲代码"的实际需求后，瓶颈并未消失——验证、代码审查与安全接管了它的位置。

如今我们都能极快地生成大量代码，但这也带来了新问题：这段代码对吗？它如何被维护？我从 fellow 工程领导者那里听到的最高频问题之一便是："你们是怎么跟上自家代码审查的节奏的？"

## 悄悄失效的流程

我们当初建立流程，都是有原因的——为了填补某个缺口，或让某件事做得更好。但当那个缺口不复存在、这些流程变得过时之后，它们却很少会自行消失。当 Claude Code 团队开始把智能体式编码作为默认工作方式时，我们的许多既有流程就停止运转了。以下是我们重写过的规范，以及背后的原因。

### 规划：把路线图转向"准时制"

旧规范之所以投入大量时间做预先规划，是因为写代码的时间太贵。我刚加入 Claude Code 团队时，我们写就了一份相当不错的六个月路线图，结果 *因为* Claude Code 本身，太多事情发生了变化，到第三个月它就已经过时了。

如今工程的速度与吞吐量已截然不同，因此我们规划迭代的方式也随之改变。我称之为准时制（JIT）规划，几乎就像 JIT 编译：如何在正确的时间做正确的量？我们的规划仪式，从设计文档转向了 PR 或原型中的讨论。这个领域变化太快，所以我们不太做产品评审。我们现在的流程是：做原型，让大量内部用户用起来，然后依据他们的反馈采取行动。

### 上下文收集：问 Claude，而不是问作者

当工程师写代码时，要回答大多数问题，第一步都是找到写这段代码的人。如今，由于我们所有的 PR 都有 Claude 协助，"谁做的这个改动？"已经不够用了。我们的新规范是再深入一层：你究竟需要知道什么？比如：你是在找导致回归的人？找一位能回答客户问题的专家？还是想要某个决策的背景？你向 Claude 提出这个问题，并考虑 Claude 能否凭借更多的数据和上下文直接给出答案。

在 Claude Code 工程团队，无论这个问题是什么，我们的流程还会多问一句："有没有办法把它自动化？"举个例子：让 Claude 每天早上汇总客户反馈渠道，这件事从我端着咖啡手动完成的仪式，变成了我只需让它在后台自动跑起来。

### 代码审查：信任，但要验证

我们重度使用 [代码审查](https://code.claude.com/docs/en/code-review)。Claude 包揽了所有样式与 lint 检查、PR 反馈请求、在完整提交前捕捉并修复 bug，以及补充测试。而我们仍然绝对需要人的地方，是专业判断。

新规范是：在要害处做人工审查——法律审查方面，我始终希望我的法务伙伴参与风险承受度的把控；涉及信任边界与安全敏感代码时，我要的是领域专家；产品经理与设计师也需要在产品质感与品味上参与进来。

不过，持续评估很重要，因为随着模型不断改进，"信任"与"验证"的正确平衡点会不断移动。今天你需要人介入的地方，到了下一个模型可能就不一样了。

### 团队构成：角色边界正在模糊

Claude 与 AI 重塑了整个团队的角色。我们的产品经理如今写大量代码，这很有意思。有了 Claude，非传统意义上的编码者现在能承担更多工程工作，而工程师也能接手内容与设计这类传统上不属于技术侧的事务。

在 Claude Code 工程团队，我对两类画像投入了很高的权重。一类是具备产品嗅觉的创意型构建者：那些对交付解决问题的产品充满好奇与热情的梦想家。另一类是拥有深厚系统专业知识的工程师。比如，我刚加入团队时就注意到，我们缺少具备系统背景的专家，而在构建 [网页版 Claude Code](https://www.anthropic.com/news/claude-code-on-the-web) 时恰恰需要他们，以确保我们能在任何地方运行 Claude。

另一方面，我投入权重较低的是原始吞吐量——模型能搞定这个。更重要的问题是：哪里仍然需要人的专业知识？那才是我关注的焦点。

|  | 之前 | 之后 |
| --- | --- | --- |
| 规划 | 六个月的产品路线图。 | 准时制（JIT）规划：做原型、让内部用户用起来、依据反馈采取行动。 |
| 上下文收集 | 找到写代码的人并去问他。 | 先问 Claude。再问你问的这件事能否被自动化。 |
| 代码审查 | 人审查一切。 | Claude 负责样式、bug 与测试；人在领域专长重要的地方审查。 |
| 团队构成 | 固定角色：工程师写代码、PM 做规划、设计师做设计。 | 角色模糊：PM 做原型，工程师承担设计与上下文；招募创意型构建者与深厚系统专家。 |

## 我们如何推行新规范

随着这些规范的改变，某些方面被硬性规定为团队原则，另一些则交由小型子团队（pod）自行摸索。有一组 Claude Code 核心团队原则是毫无商量余地的"必做项"：

- **坚持不懈地亲身使用自家产品（dogfood）：** 每位 Claude Code 团队成员（含跨职能伙伴）都在使用 Claude Code（以及 Claude Cowork）。我们一直在琢磨，如何让 Claude 帮我们把工作做得更快、更高效。
- **尽可能让团队保持扁平。** 我加入 Claude Code 时，希望每位经理都先从 IC（个人贡献者）做起，通过交付真正学会如何成为团队里高效的工程师，并真切地体会、理解在 Anthropic 当工程师是什么滋味。我们在 Claude Code 与 Claude Cowork 上有一项整体团队使命。经理们支持一个个工作 pod，同时保持团队敏捷，让人能流动到工作所在之处。
- **毫不犹豫地砍掉不再奏效的流程：** 最后，我们持续追问"我们为何要这样做"。当某件事不再说得通时，团队成员拥有明确的权限去质疑并终止旧流程。

不过，在这几条规则之内，每个 pod 都拥有很大的自主权。他们有空间去调整如何借助 Claude 做分类、如何运行任何规划仪式或每日站会，以及哪些工作流最先被"Claudified"（用 Claude 改造）。

## 如何判断你的新流程是否真正落地

每一位工程领导者，在推行变革时都应开始追踪以下三个数字。

- **入职爬坡时间下降：** 工程师、设计师或产品经理要多久才能开始产出价值？在我们团队，这比一年前快得多——工程师现在第一周内就能交付真正的代码。
- **PR 周期时间下降：** 这个数字深挖起来很有意思，因为它能帮你定位管道在哪些环节难以扩展。随着我们生成的代码越来越多，有时构建系统与持续集成（CI）可能跟不上。
- **Claude 辅助的提交量上升：** 对我们而言，默认情况下，每次提交都是 Claude 辅助的。我想过去四个月里，我没见过一次非 Claude 辅助的提交。

关于第三点，不要把吞吐量与成功混为一谈。吞吐量是一个指标，但真正的指标衡量的是你想要解决的问题。只要对齐得当，吞吐量能帮你更快地解决问题。

## 上手开始

如果只留给你一句话：**挑出你最"吵"的工作流。** 它可能是你最昂贵的工作流、你心底有些发怵的工作流，或是团队毫无期待的工作流。然后问一句：它还在实现它的目的吗？如果是，你能把它自动化吗？

我曾待过一个团队，每周都有一场昂贵的评审会，会议室里坐着一大票人。我注意到，除了轮到自己汇报状态的时刻，每个人都在摆弄笔记本电脑。他们会抬起头、报个状态，然后又埋回电脑里。我问了一个简单的问题："我们到底为什么还要开这个会？这简直是在浪费大家的时间。" 恰恰是这一个问题，让所有人意识到它并无必要。于是我们把它取消了。

所以，问问你自己：在工程工作流里，有没有哪一块是你或许可以考虑自动化、甚至彻底放弃的？

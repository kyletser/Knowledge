工程界常有人说“缓存支配着我周围的一切”，这条规则对智能体同样成立。

像 Claude Code 这样长时间运行的智能体式产品之所以可行，靠的是[**提示词缓存**](https://x.com/RLanceMartin/status/2024573404888911886)——它让我们能够复用之前往返计算的结果，并显著降低延迟与成本。

在 Claude Code 中，我们围绕提示词缓存构建了整套线束。高提示词缓存命中率能降低成本，并帮助我们为订阅计划设置更宽松的速率限制，因此我们会针对提示词缓存命中率设置告警，并在命中率过低时宣布 SEV（严重事件）。

以下是我们从大规模优化提示词缓存中学到的（往往不直观）的经验教训。

## **为缓存组织提示词**

![](images/04637cd350b7-69f2f39fa10dea4e26853e8c-2371721a.png)

Claude Code 的系统提示词经过组织，使得稳定的片段保持缓存，只有对话本身随回合逐步增长。

提示词缓存通过前缀匹配来工作——API 会缓存从请求开头一直到每个 `cache_control` 断点之间的全部内容。这意味着你放置内容的顺序至关重要：你希望尽可能多的请求能共享同一个前缀。

如何组织提示词不仅关系到缓存命中，也关系到输出质量——[提示词工程基础](https://claude.com/blog/best-practices-for-prompt-engineering)是这门学科的另一半。

最好的做法是静态内容在前、动态内容在后。对于 Claude Code，这看起来像这样：

1. **静态系统提示词**与工具（全局缓存）
2. **CLAUDE.md**（在项目内缓存）
3. **会话上下文**（在会话内缓存）
4. **对话消息**

通过这种方式，我们最大化了能共享缓存命中的会话数量。

但这种方式可能出人意料地脆弱。我们之前出于多种原因打破过这种顺序，包括：在静态系统提示词里放入精确的时间戳、以非确定性的方式打乱工具定义顺序，以及更新工具的参数（例如任务工具可以调用的智能体）。

## **用消息来传递更新**

有时，你放入提示词中的信息可能会过时，例如时间推移，或用户更改了文件。你可能会想直接更新提示词，但这会导致缓存未命中，最终对用户来说可能相当昂贵。

不妨考虑一下，能否在下一次回合中通过智能体的消息来传递这些信息。在 Claude Code 中，我们会在下一条用户消息或工具结果中附加一个 `<system-reminder>` 标签，带上需要让模型知道的更新信息，这有助于保留缓存。

## **不要在会话中途更换模型**

提示词缓存是与具体模型绑定的，这会让提示词缓存的计算变得相当不直观。

例如，如果你已经就某个话题和 Opus 进行了 10 万令牌的对话，现在想问一个相当容易回答的问题，那么切换到 Haiku 实际上会比让 Opus 来回答更贵——因为我们需要为 Haiku 重新构建提示词缓存。

如果你需要切换模型，最好的做法是使用子代理；沿用上面的例子，你可以部署一个子代理，让它提示 Opus 去准备一条“交接”消息，说明需要由另一个模型完成的任务。我们在 Claude Code 中经常用 Explore 智能体来做这件事，它使用的是 Haiku。

## **绝不要在会话中途增删工具**

在对话过程中更改工具集，是人们破坏提示词缓存最常见的做法之一。这看起来很直观——你只应该给模型它当下需要的工具。但由于工具是缓存前缀的一部分，增删工具会让整个对话的缓存失效。

**用计划模式围绕缓存约束做设计**

[计划模式](https://code.claude.com/docs/en/common-workflows) 是一个围绕缓存约束设计功能的绝佳范例。直观的做法是：当用户进入计划模式时，把工具集换成只包含只读工具，但这会破坏缓存。

相反，我们在所有请求中始终保留*全部*工具，并把 EnterPlanMode 和 ExitPlanMode 本身当作工具来用。当用户开启计划模式时，智能体会收到一条系统消息，说明自己正处于计划模式以及具体的指令：探索代码库、不要编辑文件，并在计划完成时调用 ExitPlanMode。工具定义永远不变。

这还有一个额外好处：因为 EnterPlanMode 是模型可以自行调用的工具，所以当它检测到难题时，可以自主进入计划模式，而不会中断任何缓存。

**用工具搜索来推迟而非删除**

同样的原则也适用于我们的[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)。Claude Code 可以加载数十个 MCP 工具，在每次请求中都包含所有这些工具成本很高，但在会话中途删除它们又会破坏缓存。

我们的解决方案是：`defer_loading`。我们不删除工具，而是发送轻量级的存根（仅包含工具名称，并带 `defer_loading: true`），模型可以在需要时用工具搜索来“发现”它们。完整的工具 schema 只有在模型选中它们时才会被加载。这保证了缓存前缀的稳定性，因为相同的存根始终以相同的顺序存在。

你也可以通过我们的 API 使用[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)来简化这一过程。

## **在不破坏缓存的前提下压缩**

![](images/a7454e021f42-69f2f39fa10dea4e26853e8f-9e1aba00.png)

当上下文窗口填满时，Claude Code 会分叉（fork）一次缓存的调用来总结对话，然后用总结替换原始消息继续。

[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction) 发生在你用尽上下文窗口的时候。我们会总结到目前为止的对话，并基于这份总结开启一个新的会话。

压缩与提示词缓存的交互方式很容易出错。要压缩一段对话，你必须把完整对话发送给模型，它才能写出总结。最简单的方式是一次独立的 API 调用，带上自己的系统提示词（类似“总结一下这个”）且不含任何工具，但那正是成本陷阱所在。提示词缓存只在某个请求的前缀与已缓存内容逐字节匹配时才生效。你的主对话是在一套系统提示词和工具集下被缓存的；而总结调用使用的是不同的系统提示词，且没有工具，因此前缀在第一个令牌处就出现了分歧，缓存完全用不上。最终你要为发送的完整对话支付全额、未缓存的输入价格——而且对话越长（也就是你一开始越需要压缩），这一次调用的成本就越高。

**解决方案：缓存安全的分叉**

当我们执行压缩时，我们会使用与父对话*完全相同*的系统提示词、用户上下文、系统上下文和工具定义。我们在父级的对话消息之前加上前缀，然后在末尾把压缩提示词作为一条新的用户消息追加进去。

从 API 的角度看，这个请求与父级的最后一次请求几乎一模一样——相同的前缀、相同的工具、相同的历史——因此缓存的前缀会被复用。唯一新增的令牌就是压缩提示词本身。

不过，这确实意味着我们需要预留一个“压缩缓冲区”，以便在上下文窗口中有足够的空间来容纳压缩消息和总结的输出令牌。

压缩很棘手，但幸运的是你不必亲自踩这些坑——基于我们从构建 Claude Code 中学到的经验，我们已把[压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)直接做进了 API，让你能在自己的应用中套用这些模式。

## **经验教训**

以下是在构建智能体时，我们发现对优化提示词缓存有用的几个模式：

1. **提示词缓存是前缀匹配。** 前缀中任意位置的任何改动，都会使之后的所有内容失效。围绕这一约束来设计整个系统。只要顺序排对，大部分缓存是“免费”的。
2. **用消息代替系统提示词的修改**。你可能会想通过编辑系统提示词来做诸如进入计划模式、更改日期之类的事，但其实更好的做法是在对话过程中把这些内容插入到消息里。
3. **不要在对话中途更换工具或模型。** 用工具来建模状态转换（如计划模式），而不是更改工具集。推迟工具加载，而不是删除工具。
4. **像监控可用性一样监控缓存命中率。** 我们会对缓存中断发出告警，并将其视为事件。几个百分点的缓存未命中率，就会对成本和延迟产生巨大影响。
5. **分叉操作需要共享父级的前缀。** 如果你需要运行辅助计算（压缩、总结、技能执行），请使用相同的缓存安全参数，以便在父级前缀上获得缓存命中。

我们分享如何与 Claude Opus 协作，构建威胁模型、发现代码库中的漏洞，然后加以验证、分类和修补的最佳实践。

模型能力正在快速、却不均衡地进步。我们一直在[与安全团队合作](https://www.anthropic.com/glasswing)，寻找并修复他们自己代码和开源软件中的漏洞，这项工作让我们更清楚地理解了如何用模型来保护源代码。**我们的核心结论：发现环节现在已经可以直截了当地并行化，瓶颈已经转移到了验证、分类和修补。**

为了说明这种差距有多大，作为[我们自己的扫描](https://www.anthropic.com/research/glasswing-initial-update)的一部分，截至 2026 年 5 月 22 日，我们已披露了 1,596 个开源软件漏洞。据我们所知，其中 97 个已被修复。

本指南将介绍如何与 Claude Opus 协作，构建威胁模型、发现代码库中的漏洞，然后加以验证、分类和修补。虽然我们还没有所有答案，但我们会分享团队如何扩展发现规模，以及在后期阶段有哪些行之有效的做法。*今天就开始用* [*随附的代码仓库*](https://github.com/anthropics/defending-code-reference-harness) *，它包含用于交互式工作流的技能和用于自主扫描的演示线束；阅读过程中，我们会指出实现每一步的技能。*

## 发现与修复循环

在发现和修复漏洞数量上领跑的团队，都不约而同地收敛到了现有最佳实践的一个变体。我们将其提炼为一组六个步骤：

1. **威胁模型：** 在开始扫描之前，先界定什么算作漏洞。
2. **沙箱：** 构建一个沙箱环境，用来隔离智能体并验证漏洞利用。
3. **发现：** 让模型在你的源代码中寻找漏洞。
4. **验证：** 独立确认哪些发现是真正可被利用的。
5. **分类：** 去重、分配严重性，并排定需要修复的优先级。
6. **修补：** 应用修复、确认漏洞已被消除，并搜寻变体。

![](images/928a59f50ef9-6a17340b26b22fa10e3ed68e-image1.png)

对威胁建模和沙箱的一次性投入，为防御者的循环——发现、验证、分类、修补的不断重复——提供动力；在这个循环里，瓶颈不是找漏洞，而是找完之后的一切。

前两步（构建威胁模型和沙箱）是循环其余部分的准备工作。它们通常每个代码库只做一次，并在底层系统发生变化时重新审视。接下来的四步，是你针对源代码反复运行的循环：发现、验证、分类、修补。

对一个代码库的第一次运行，通常产出最多的发现。后续运行发现的漏洞往往会更少（尽管常常更复杂），因为较简单的那些已经在之前的运行里被修补了。不过，别指望第 *n* 次运行就零新发现。模型是随机的，而大型代码库可能拖着一长串漏洞的尾巴，即使代码没改，也会持续冒出来。

对一个代码库的第一次迭代，你应该多次运行这个循环，根据净新增发现的数量、以及你对该系统的风险承受度，来决定何时停下。第一次迭代之后，继续定期扫描（1），或在代码发生实质性变更时（2）扫描。

接下来，我们逐一审视每个步骤，解释它为何重要、产出什么，以及如何落地。

## 1. 威胁模型：界定什么算作漏洞

误报最常见的原因，是模型对你的信任边界缺乏充分理解。模型可能会把代码标为易受攻击，因为它假设客户端能发来损坏的值、或攻击者能控制配置——即使这些输入在你的环境里其实是*受信任的*。反过来，模型也可能假设一个面向互联网的服务「仅供内部使用」，从而漏报真正的漏洞。这两种情况里，错的是模型对威胁模型的判断，而不是代码。

> *有个团队注意到他们发现中的一个规律：在那些拥有文档完备的威胁模型、系统设计文档、需求和约束的系统上，模型表现最好。当威胁模型定义清楚时，模型的发现「90% 的情况下都是可被利用的」。*

你可以分两步，与 Claude 协作构建威胁模型：

**首先，从代码、文档和漏洞历史中引导（bootstrap）。** 把你在第一天会交给一位新安全工程师的东西喂给模型：架构文档、wiki、入口点、git 历史和过去的漏洞。这有助于克服「仅凭代码推断隐性知识、权衡与设计决策」这一难题。然后，让模型创建一个威胁模型，包含系统上下文、资产、入口点和信任边界。最后，让模型对过去的缺陷做聚类，列出相关的漏洞类别。确保威胁模型写清楚你们关心和*不*关心哪些漏洞，以及为什么。

> *一个团队回顾了数百个过去的 CVE 和安全修复提交，把它们提炼成「bug 形状」提示，并向模型提了两个问题：修复是否完整？有没有应用到其他地方？他们在一小时内找到了三个可被利用的问题。正如他们所说：「『人们过去利用过什么』，有时比『在这个代码库里给我找漏洞』更容易成为走向成功的作弊码。」*

**其次，让模型去采访熟悉该系统的人。** 参考 [Shostack 的四个问题](https://github.com/adamshostack/4QuestionFrame)：*我们在建什么？会出什么错？我们在做什么？我们做得好吗？* 先跑引导步骤，这样受访者就不用从零开始。如此一来，他们可以基于一份草稿起步，而不必花几个小时从头研究和构建威胁模型。访谈这一步虽然可选，但它补上了模型无法从代码或文档中获得的上下文，从而改善了威胁模型。

一些做法能带来很大不同：

- **考虑你依赖项的安全策略。** 许多开源项目都发布了一份。例如，vLLM 的 [`security.md`](https://docs.vllm.ai/en/latest/usage/security.html)、SQLite 的[《黑魔法防御术》](https://www.sqlite.org/security.html)，以及 [ImageMagick 的安全策略](https://github.com/ImageMagick/ImageMagick/security/policy)。你的威胁模型应当直接参考它们，而不是从零开始另造一套策略。
- **明确写出什么是受信任的。** 如果你信任配置文件或已通过身份验证的客户端，就把它写进威胁模型。这些假设有助于把不可利用的缺陷与真正的漏洞利用区分开。
- **在代码旁放一份 `THREAT_MODEL.md`。** 把它放进仓库，并在代码变更时更新。这样发现智能体在搜索前可以先读它，跳过已知的「非问题」。

你会在两个地方用到威胁模型。在*发现*阶段，作为范围**：**对代码做分区、排定目标优先级、跳过范围之外的内容。这有助于处理那些无法完整扫描的大型代码库。在*分类*阶段，作为过滤器：在广泛扫描之后，用威胁模型更好地把严重性与你的系统、环境对齐校准。

> *一个扫描大型项目的团队，误报率高达 40%，于是深挖原因。发现是可复现的，PoC 也证明了可利用性。但拥有这段代码的开发团队却把它们当作误报打发掉，因为这些缺陷不符合该项目的威胁模型。另一个团队的 CISO 一句话点破：「[模型]对代码有很好的上下文，但对『我们』缺乏上下文。」*

**试试** [**威胁模型技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/threat-model)**。** 它走完本节描述的两个步骤——`bootstrap` 从你的代码、CVE 和 git 历史中得出一份草稿，interview 则引导系统所有者走过 Shostack 的四个问题来完善它。输出是一份 `THREAT_MODEL.md` 文件，在发现和分类步骤中使用。

## 2. 沙箱：安全运行智能体并验证可利用性

**沙箱的目的之一是保护你的系统。** 要让模型能够安全、自主地运行，你需要一层强力的隔离。没有它，智能体可能越过目标，做出意料之外的事。

> *一个团队告诉模型它「没有网络访问权限」——而实际上它有——结果模型发现自己照样能从 GitHub 取东西。另一个团队在扫描中观察到智能体中途去回复了一个 GitHub issue。这两个动作都不怀恶意，但都表明：约束必须通过代码和配置来强制执行。*

隔离强度要与你的威胁模型匹配。容器用来让发现智能体读代码没问题；但要让目标及其 PoC 跑在 microVM（如 Firecracker）或完整 VM 里，并锁死出口，让任何东西都碰不到你的生产系统。而且绝对不要给智能体任何凭据（`~/.aws`、`~/.ssh`、`.env`）。

只在搭建阶段给沙箱网络访问权限。拉取依赖、构建、安装工具、部署目标，并跑一遍既有测试确认一切正常。然后，对环境做快照，并撤掉它的网络访问。扫描期间，只允许流量经本地代理路由到模型 API。每次运行开始时加载快照，这样每一次扫描都从同一份干净状态起步。

**沙箱的另一个目的是证明可利用性。** 在静态扫描时，模型读代码、假设哪些地方可能出问题，却无法测试某条路径是否真的可达、是否存在补偿性控制。于是，模型可能会标出你其实并不关心的、不可利用的代码正确性缺陷。当团队搭起一个沙箱，让智能体能够编译代码、跑测试、并引爆概念验证（PoC）时，不可利用的发现显著下降。

> *一个进攻安全团队搭了一个线束，给智能体一个测试台，规则很简单：只有智能体能构建 PoC 并在测试台上跑起来，才算真正的真阳性。六周后他们的评估是：「最大的效能杠杆，就是给模型测试台、实时系统，并让它跑 PoC。」*

构建沙箱时，尽可能把一切都固定下来，让每次运行都在同一环境里用同一份代码：镜像标签、提交 SHA、依赖项和构建命令。在本地缓存一份副本，这样构建无需联网；并尽量让容器持久化，以便多个测试循环直接加载它。

> *一个团队的扫描标出一个漏洞，结果发现那只是智能体下载了旧版本库、而不是实际部署的库所带来的副产品。一位工程师读了记录、发现下载的是不同的依赖项，才揪出这个问题。他们现在构建 Docker 容器时，把依赖项固定到与生产一致，这样发现智能体和验证智能体操作的，都是攻击者会操作的同一批制品。*

构建足够贴近生产的沙箱很重要。遗漏依赖项（比如队列或数据存储），可能导致生产里实际存在的 bug 被漏报。反过来，忽略生产防御（比如 WAF 或认证网关），又会让模型报出你的生产环境已经缓解掉的、不可利用的发现。

话虽如此，如果因为云依赖、数据存储或其他现实复杂度，构建有代表性的沙箱不切实际，那就从下面的*发现*步骤开始。你不一定非得在沙箱里跑 PoC。前沿模型很擅长仅凭分析源代码来发现漏洞。包括我们在内的多个团队都发现这招有效。代价在验证阶段：没有运行着的目标，我们就无法用 PoC 来证明发现，所以要为验证多留些时间。一旦发现量足以证明其价值，你也可以之后再投资沙箱。

**参考** [**线束 `README.md`**](https://github.com/anthropics/defending-code-reference-harness/tree/main/harness)**，作为沙箱的参考实现。** 在这个实现里，智能体和目标都跑在 gVisor 隔离的容器中，出口被锁死到模型 API。目标从一个固定到特定提交的 Dockerfile 构建，[`setup_sandbox.sh`](https://github.com/anthropics/defending-code-reference-harness/blob/main/scripts/setup_sandbox.sh) 负责处理搭建阶段。

## 3. 发现：提供丰富上下文、更短的提示词和有用的工具

给发现智能体访问「可按需加载的上下文」的权限，例如威胁模型、架构文档和过往扫描的结果。当智能体理解了你的信任边界、以及系统实际是怎么部署的，它就能更好地识别专属于你系统的漏洞。

我们发现，前沿模型在发现阶段反而受益于越来越简单的提示词。反直觉的是，越是规定得细，发现反而越差——长长的清单往往会压低模型的创造力，产出更少的新 bug。以下是一些在发现阶段有用的提示词技巧：

- **给出目标和背景。** 说清「为什么」和「是什么」——为什么要扫描、有价值的发现长什么样、正在扫描的是什么系统——而把「怎么扫描漏洞」留给模型。前沿模型在安全任务上越来越强，过度规定反而会窄化它们尝试的范围。
- **试着指定某个漏洞类别。** 如果你想聚焦某种由既往 CVE 或代码库语言引导的特定漏洞类型，就明说。描述这个漏洞类别、它的作用、以及它通常出没的位置，好让模型在你的代码库里认出它。
- **定义输出格式。** 要求一份带有预定义字段的结构化报告，并排好顺序，让模型的推理建立在前一个字段之上。示例字段包括理由、发现、影响、严重性等。留一个「逃生舱口」，让模型在发现很弱时可以提前退出。

给模型提供搜索和读取代码库的工具，比如 grep、glob 之类。同时，让模型能用上你团队可能用到的、安全专用的工具，例如 SAST 扫描器或模糊测试器。问问模型某项具体任务需要什么工具，并提供给它。最后，让模型按需自己造工具：近期的前沿模型越来越擅长写它们自己需要的工具。

> *除了源代码，一个渗透测试团队还给发现智能体配了发送请求、检查响应、查询流量日志的工具。于是智能体不必猜测某条路径是否可达，可以一边走一边对着运行中的应用测试每个候选，把真阳性率拉到接近 100%。*

先让模型对系统做一次首轮遍历，把搜索空间分区，比如按攻击面、端点或组件。然后，把这些分区交给并行的发现智能体，这样它们就不会都收敛到同一批浅层 bug 上。最后，跑一轮系统级遍历，把分区级的发现当作上下文，再去搜寻漏洞。

> *试图靠蛮力做发现的团队，很快就撞上了收益递减。一个团队说：「我们最初想的就是横向扩展、派更多智能体，结果看到的只是有限的回报。」另一个增加了焦点区域和并行智能体的数量，得到了「一大堆问题」，其中大部分彼此重复。*

如果你有能跑目标的沙箱，就要求发现智能体为发现构建 PoC，比如一个脚本、一个能令程序崩溃的输入，或一份会失败的测试。构建 PoC 有助于智能体迭代、锁定发现，而这份制品也给验证智能体提供了具体的评估证据。话虽如此，智能体无法复现的发现仍然可以上报，并标记为「未经证实」，这样你就能保持较高的召回率。

[**`vuln-scan` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/vuln-scan) 在这个阶段很有帮助。它读取你的 `THREAT_MODEL.md`，把目标划分成若干焦点区域，并按区域扇出并行的审查智能体。输出是结构化的发现，下一步可直接消费。

## 4. 验证：过滤掉不可利用的发现

发现环节优化的是*召回*；验证优化的则是*精确*。换句话说，发现应当尽可能多地找出漏洞——哪怕是不太可能的那些——而验证应当排除那些其实不可利用的发现。当一个智能体试图在同一步里*两者*都做时，它可能会自我审查，把可被利用的真阳性也排除掉。我们是从惨痛教训中学到这一点的：当初让发现智能体顺带做验证，结果它们把本可由独立验证步骤确认的真阳性给过滤掉了。

验证智能体应当与发现智能体相互独立。把它放在一个全新的容器里运行，没有共享的文件系统，也没有对话历史。如果验证者接触到发现智能体的推理过程，它可能只是点头同意，而不是去检验那个论断。所以，只把（1）概念验证或书面发现，以及（2）代码库，交给验证者，这样它才能去搜寻发现者漏掉的缓解措施（例如上游校验、认证闸门、类型约束，或不可达的代码）。

如果单次验证通过仍然放进来太多不可利用的发现，就试着跑多个独立的验证器。它们可以从不同角度切入，或用不同模型来跑。然后，按多数票裁决。也可以考虑让一个独立的裁判，在发现与验证智能体的结果之间做决断。

提示词验证智能体去*反驳*发现智能体的结论。让验证者假设每一个发现都是误报，并去寻找这个发现是错的原因。给出验证智能体可以用来判断「是否为真阳性」的明确标准。当发现智能体的输出里没有 PoC 时，这一点最为关键。目标是尽可能多地排除不可利用的发现，从而减轻人工审核的工作量。

> *在我们合作过的团队里，加上对抗式验证器，大约把发现阶段不可利用发现的比例砍掉了一半。再要求验证器也构建一个 PoC 来确认漏洞，就把误报率压到了接近零。这两步合在一起，显著减轻了下游的分类和修补负担。*

如果你能在沙箱里充分复现生产环境（见步骤 2），就提示词验证智能体去构建并执行一个可复现的概念验证（PoC）。如果 PoC 有效，你就可以断定这个发现是可利用的。注意，反过来不成立——无法生成有效的 PoC，并不等于证明它是误报。

> *一个扫描开源包的团队，搭了一个有助于闭环的验证步骤：扫描这个包、生成概念验证，再部署一个用到这个包并触发该 PoC 的模拟应用。他们的体会是：「验证是最大的瓶颈，而 PoC 就是验证。」*

## 5. 分类：按根本原因去重，按先决条件和影响排序

验证确认了某个发现可被利用，而分类评估的是修补的优先级。过去，当发现还很费劲时，找到 bug 的工程师也会顺手把它分类。如今，模型能在午饭前找出一百个候选，分类便成了瓶颈。

恰当的分类有助于防止告警疲劳。如果你提交太多重复、或严重性被夸大的 bug，产品工程师可能干脆不再读它们——哪怕那些本需要立刻修补的。开源维护者尤其容易被未分类的发现淹没，因为他们要面对来自许多不同用户（都依赖他们的软件）的报告。

> *多个团队分享了同一个教训：如果我们甩给产品工程师一堆发现，其中多数还不可利用，他们就会对报告失去信任、然后放弃。他们也会优先处理关键和高危发现，以免拖垮下游工程师。另一些团队找到了突破口：把模型指向他们既有的待办积压（早先扫描器的、早先模型的未结发现、漏洞赏金 intake），几天内就清掉了几百条陈年项目。*

要给发现去重，得从根本原因着眼。扫描器常常会在多个调用点标记同一个 bug，或把单一根本原因的多种症状各报一遍。一个实用的做法是：先用廉价的确定性遍历——同一文件、同一类别、漏洞行号彼此在十行以内；然后，让模型对剩下的部分套用定性规则：

- **视为重复**：根本原因相同但表述不同；同一个漏洞在多个调用点被报告；每个端点都报告了缺失的全局防护（如鉴权检查）；或在同一条路径里，把某个原因及其后果都标了出来。
- **视为独立**：同一文件里不同的漏洞类别；不同的变量流向不同的汇点；一个辅助函数里有两个独立的 bug；两个端点都缺同一项检查，但各自需要自己的修复。

如果你的线束为每个发现都生成 PoC 和补丁，另一种去重方法是：检查一个发现的补丁，是否也解除了其他发现的 PoC。

去重之后，根据以下维度为每个发现评定严重性：

- **可达性。** 攻击者能从真实的入口点触及这段代码，还是只能从内部代码和端点抵达？
- **攻击者控制。** 不可信输入是否原封不动地到达汇点，还是有上游的东西做了清洗或限制？
- **先决条件。** 触发这个 bug 必须满足什么前提：非默认设置、某个特定功能开关、攻击者必须卡准的一个极窄时间窗？
- **认证。** 未经验证的攻击者能否触发它，还是必须登录用户或管理员？
- **读与写。** 攻击者只能读数据，还是也能改数据？
- **爆炸半径。** PoC 一触发，谁会受影响？一个用户还是所有用户、一个租户还是整个平台、用户态还是内核？

要把这套评分细则变成分数，先让模型在分配严重性之前，把每个问题的答案写出来。先过一遍证据，能防止模型锚定在某个 bug 类别上（「SQL 注入，所以致命」），然后为了匹配而夸大严重性。作为起点：未经验证、远程可达、零先决条件的，是致命或高危；一两个先决条件，或一条需要登录的路径，是中危；三个及以上，或仅本地可达，是低危。按你的系统调整阈值。

模型可能因为上下文不足而夸大严重性。它们可能不知道攻击者实际能控制哪些输入，也可能看不到补偿性控制。前者的例子：一个 SQL 注入，若由未经验证的请求触发则致命，若只是由仅管理员可见的配置文件触发则无关紧要。后者的例子：上游 WAF 或阻挡利用的认证，单看源代码可能根本看不见。

解决办法是在分类阶段提供威胁模型，告诉模型在你的系统里关心和不关心哪些类型的漏洞。例如，澄清「我们信任已通过身份验证的客户端」，可以简化甚至砍掉整整一类高危项。

> *一个团队发现，模型往往过于自信——除非有需要验证的东西，或者有更多上下文来判断某件事是否本就属于威胁模型的一部分。他们的解法是：给分类智能体一份与发现智能体相同的威胁模型。*

**试试** [**`triage` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/triage)**。** 它同时做验证和分类：对每个发现做多票验证、跨运行去重、并按推导出的可利用性重新排序。输出是一份简短、已排序、有人认领的清单，而不是原始转储。

## 6. 修补：闭环，并为下一轮改善上下文

修补是闭环、修复漏洞的地方。它还有助于根据已验证的发现来改善威胁模型——更新信任边界或需要更多审查的组件——并把过去的发现反馈进下一轮扫描的上下文。每一轮循环都加固了代码库，也让下一次扫描更有依据。

修补之前，先写一个新测试，让它在现有代码下失败。然后实施修复，确认同一个测试现在通过、且没有破坏其他任何东西。（对，这就是测试驱动开发）。如果你不补测试，修复可能悄悄回退，而且很难回过头去证明那个 bug 是真的。

> *一位渗透测试人员发现，他生成的补丁时好时坏——有的好，有的糟——直到线束让模型通过对修补后的代码重新跑 PoC 来验证补丁。通过给模型反馈让其迭代，补丁质量大幅提高，省下了人工审核时间。*

模型可能只狭隘地修掉某个具体调用点上的发现，而不是根本原因。只要提示词让模型去识别并修复根本原因，往往就有效。然后，让模型在两个层面搜寻变体：（1）同模式——别处还有别的调用点、或同一份问题代码的副本；（2）同类别——一个有过一个 SQL 注入漏洞的代码库，往往还有更多 SQL 注入。用已验证的发现和补丁更新威胁模型，完成闭环。

发布补丁前，跑一次对抗式检查。让一个新发现智能体扮攻击者去探查这个补丁，确认它是否覆盖全面。然后，简化生成的补丁，收拾那些过于侵入性的部分。最小的补丁更好审查，也更不容易引入新 bug。提示词追求「修复根本原因的最小改动」——不要重构、不要顺手清理、不要重新格式化。

> *一个团队谈到最常见的补丁失败：「推荐的补丁往往限制得尽可能死，结果会切断与其他服务的连接。问题是解决了，但也先把让服务能正常工作的依赖关系给弄断了。」*

你可以对照一套由廉价到昂贵的检查阶梯，来逐一验证每个补丁：

1. **构建。** 补丁能编译，新测试通过。
2. **尝试复现。** 原来的 PoC 应当失效。这能抓住无效补丁。
3. **检查回归。** 原来的测试套件仍全绿。这能抓住破坏性或过严的补丁。
4. **重新攻击。** 一个全新的发现智能体跑对抗式检查。这能抓住不完整的补丁。

最后，虽然模型能写补丁，但最终还得由人来认领它。生成的补丁会以可预测的方式失败——修症状而非根因、挡掉合法输入、或删掉对依赖服务的访问。目标是尽可能多地验证每个补丁，好让人审更省力。目的是帮开发团队专注于模型可能不知道的细微之处（比如传入的变更、代码风格），让补丁所需的审查和更新降到最少。

**试试** [**`patch` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/patch)**。** 它消费分类输出，为每个发现生成候选 diff，并由一个独立的审阅者智能体逐一检查。

## 开始使用

自己跑一遍这个循环试试。克隆 [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)，并在 Claude Code 里 `run /quickstart`。它会带你在一个演示目标上走完从威胁建模、扫描到分类的交互式工作流。这个仓库还包含一个自主线束，以及一个用于按你的环境更新线束的 /customize 技能。

然后，在你的代码上跑它。挑一个服务或包。从代码和文档里引导出威胁模型，并完成访谈。投资搭建你环境的沙箱。扫描。用独立智能体验证发现。按你的标准做分类，并复核所有评级为高及以上的项。修补。然后定期重新扫描。

你的第一次扫描会冒出比你预期更多的发现。其中大多数都需要验证和分类。在预算更多扫描之前，先为扫描*之后*的这条流水线做好预算。

你可能会觉得这些资源有用：

- [Claude 安全](https://www.anthropic.com/product/security)：Anthropic 用于智能体式漏洞检测与修补的托管产品。
- [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)：配套代码仓库，含交互式工作流技能和用于自主运行的演示线束。
- [`claude-code-security-review action`](https://github.com/anthropics/claude-code-security-review)：GitHub Action，让 Claude 在每个拉取请求上担任安全审阅者。
- [威胁情报丰富智能体](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)：构建智能体的食谱，针对威胁情报源富集失陷指标。
- [漏洞检测智能体](https://platform.claude.com/cookbook/claude-agent-sdk-06-the-vulnerability-detection-agent)：构建智能体的食谱，构建威胁模型、扫描漏洞，并将发现分类汇入结构化报告。

## 向前看

我们相信，模型[在代码中找到并利用漏洞](https://red.anthropic.com/2026/exploit-evals)正变得越来越容易。因此，作为防御者的我们，要在对手利用代码中的漏洞之前把它们找出来、修掉。一些团队甚至已经把他们的线束连到了事件上：漏洞赏金报告触发自动变体分析，安全审查触发扫描并附上候选发现，或者，一个已验证的漏洞会更新静态分析工具，以防将来再发生。

这项工作至关重要、赌注极高。但做得对，它将开启一个更大、更令人期待的转变——在那个转变里，我们将*能够*在攻击者利用漏洞之前就找到并修复它们。

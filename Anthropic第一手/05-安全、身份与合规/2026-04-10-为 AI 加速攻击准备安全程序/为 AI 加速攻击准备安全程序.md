# 为 AI 加速攻击准备你的安全程序

---

AI 正在改变漏洞被发现和被利用的速度。我们发布这份初步建议，目的是基于我们自身的发现与安全实践，帮助你们加固防御。

本周早些时候，我们宣布了 Glasswing 项目——我们紧急尝试将最新前沿模型 Claude Mythos 预览版的强大网络安全能力用于防御目的。在[公告](https://www.anthropic.com/glasswing)以及[随附的技术博客文章](https://red.anthropic.com/2026/mythos-preview/)中，我们描述了 AI 模型如何快速降低在软件中发现并利用漏洞所需的资源、时间和技能门槛。

着眼 AI 的飞速进展，我们也注意到，能力水平相当的模型在不久的将来就会广泛可用。未来 24 个月内，大量长期潜伏、可能已被忽视数年的代码缺陷，将被 AI 模型发现并串联成可用的漏洞利用。事实上，如今公开发布、能力低于 Mythos 的模型，已经能够[发现严重漏洞](https://www.anthropic.com/news/mozilla-firefox-security)——那些被传统审查方法遗漏了很久的漏洞。

值得庆幸的是，这是把双刃剑：攻击者可以用 AI 加速行动，采用 AI 工具来自我保护的防御者同样可以。在本文中，我们根据安全团队与研究人员在使用前沿 AI 模型保护真实代码库和系统的过程中观察到、总结出的经验，给出安全建议与实用技巧。在进入 AI 驱动的网络安全的时代之际，我们希望安全团队及其他读者能从中受益。

下面许多建议本身已是现有安全共识的一部分；我们依据「哪些控制措施依然有效、哪些已然失效」对其做了优先级排序。如果贵组织按 SOC 2 和 ISO 27001 报送，这些建议将直接对应你们已经在跟踪的控制项。

随着我们和 Glasswing 项目合作伙伴持续推进网络安全工作，本指南也会持续更新。

## 现在该怎么办

### 1. 缩小补丁差距

AI 模型极其擅长识别未修补系统中那些已知的、已被修补漏洞的特征。把一个补丁逆向还原为可用的漏洞利用，正是这类模型所擅长的机械化分析。这意味着，补丁发布到漏洞利用可用之间的时间窗口正在缩短。

- *立即修补* [*CISA 已知被利用漏洞（KEV）目录*](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) *中的每一项。* 该目录收录的是已被确认正在被积极利用的漏洞。目录中任何可从网络访问到的条目，都应视为紧急事件。
- *用* [*EPSS*](https://www.first.org/epss/) *为其余漏洞排定优先级。* 漏洞利用预测评分系统（EPSS）每天更新概率值，预测某个给定的通用漏洞披露（CVE）在未来 30 天内被利用的可能性。先修补 KEV 目录中的项，再修补所有高于所选 EPSS 阈值的项，就能把成千上万个未处理 CVE 变成一份可管理的队列。
- *缩短面向互联网系统的补丁周期。* 我们建议在漏洞利用出现后 24 小时内修补面向互联网的应用，其余漏洞在数日内修补。
- *自动化补丁部署与重启*——前提是自动更新导致宕机的风险可以接受。人工审批步骤只会增加延迟，而延迟如今已成为主要风险。

**实用提示：** 大多数云服务和操作系统厂商已经提供了补丁自动化能力；启用它通常只是一次简单的配置变更。对于容器镜像和依赖清单，有若干开源扫描器可作为单个持续集成步骤运行，并借用 KEV 目录和 EPSS 的数据为 CVE 标注优先级，因此优先级排序是内置的。

### 2. 准备好应对数量激增的漏洞报告

在接下来的大约两年里，你们用来接收、排定优先级并修复漏洞（无论在自己代码中，还是从供应商处购买的软件中）的流程，将面临比今天大得多的压力。你们的漏洞管理流程应当为来自供应商和上游、数量多得多的补丁做好准备。

- *为发现量的数量级增长做规划。* 接收、分类和修复跟踪等环节，都需要跟上不断暴露的漏洞数量。如果你们的安全会议仍围绕一张电子表格和每周例会展开，几乎不可能跟得上。值得引入一定程度的自动化——当然，人类仍应在回路中，以应对这里的庞大数量。
- *检查开源依赖项的安全性。* 大多数软件供应链主要就是开源的。大多数开源项目没有服务等级协议，也不承诺维持高水平的安全。 [OpenSSF 记分卡](https://securityscorecards.dev/) 会根据分支保护、模糊测试覆盖率、签名发布和维护者活跃度等信号，自动为每个依赖项打分。它运行于 CI 中，有助于识别无人维护的包。
- *对供应商提出同样的要求。* 你们的第三方风险管理流程，应当询问供应商*他们自己*如何为加速的利用时间表做准备，以及他们是否扫描自己的代码。

**实用提示：** 研究并评估那些能够判断易受攻击代码「可达性」的开源软件与第三方服务。构建自动化流程，通过对更新做回归测试来持续把新的软件更新交付到 IT 和生产基础设施，从而确信自己能够快速部署它们。

上面我们提到了这些流程的自动化。AI 能从多个重要方面提供帮助：

- *加快分类速度。* 分类之所以成为瓶颈，是因为它需要专家审核与归类。前沿模型可以对着既有待办清单去重，利用它对资产的了解来估算暴露面，并在受影响代码路径已被预先识别的情况下起草修复工单。
- *检查依赖项是否存在冗余。* 大多数大型代码库都会累积多个做同一件事的库（好几个 HTTP 客户端、好几个 JSON 解析器）。这给攻击者更多可乘之机，而你们却得不到任何功能上的好处。让 LLM 对着一份锁定文件（lockfile），问它哪些依赖项重叠（以及迁移和整合会是什么样子），通常是一小时的投入就能见效。
- *AI 升级自动化。* 前沿模型正越来越擅长在漏洞报告之外顺带生成补丁。当报告清晰完整、甚至带有概念验证时，模型可以直接测试补丁以确认利用路径已被关闭。它还能直接把接受上游补丁的过程自动化，并验证升级不会破坏测试或内部系统。
- *AI 自研依赖（AI vendoring）。* 某些小型依赖项在 OpenSSF 记分卡上得分很低——也许是因为它们不再被积极维护。你们不应继续依赖这些；相反，应考虑让 LLM 自己编写代码，重新实现你们实际用到的功能。

### 3. 在发布之前发现缺陷

预防永远胜于治疗。你们应当假设：那些流入生产环境的缺陷终会被发现，因此安全测试必须提前进行。

- *将静态分析和 AI 辅助代码审查加入持续集成流水线，* 并基于高置信度结果阻断合并。如果误报让这一做法难以落地，你们应保留检查，但去解决工具本身的问题。 [OWASP 应用安全验证标准](https://owasp.org/www-project-application-security-verification-standard/) 定义了在三个不同严格级别下「通过」测试意味着什么。
- *在持续交付流水线中加入自动化渗透测试。* 你们可以对预发环境跑攻击者会对生产系统运行的同类扫描。
- *确保构建流水线安全。* 一个能在提交与部署之间注入代码的攻击者，根本不需要去找漏洞。 [SLSA](https://slsa.dev/) 安全框架提供了一条分级路径：较低级别确定「哪个提交生成了哪个制品」，较高级别则让构建本身可验证。
- *采用* [*设计安全*](https://www.cisa.gov/securebydesign) *（Secure by Design）实践。* CISA 的承诺（默认启用多因素认证；无默认密码；透明的漏洞披露机制）是一条合理的最低标准。
- *新代码优先选用内存安全语言。* 大部分严重漏洞都是内存安全缺陷，而这类问题不会出现在 Rust、Go 或托管运行时中。CISA、NSA 以及 [NCSC](https://www.ncsc.gov.uk/) 已[发布实用的路线图](https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps)。既有 C/C++ 代码无需重写，但新的 C/C++ 代码应当要求给出理由。借助 AI 的辅助重写也正变得越来越可行。

**实用提示：** 静态应用安全测试（SAST）工具作为 CI 动作运行，配合 OWASP Top 10 和特定语言的规则集，随处可得——既有开源方案，也内置于代码托管平台（GitHub 上的 CodeQL 是最常见的起点）。要评估构建来源，OpenSSF 发布了一个[可复用工作流](https://github.com/slsa-framework/slsa-github-generator)，能从 GitHub Actions 生成 SLSA 3 级证明；采用它的工作量远比 SLSA 规范本身暗示的要小。

和前面一样，用 AI 加速这项工作也有明确的机会：

- *AI 漏洞扫描。* 逻辑很简单：在攻击者动手之前，你们就应该用攻击者会用到的同类模型，扫描自己的代码和系统。这种方法只需一个隔离的智能体、一个过滤噪声的验证步骤，以及一条接入既有分类流程的路径。今天你们就能用 LLM 做到这一点。***如果本节你只落地一件事，就落地这一件。***
- *补丁生成。* 当 SAST 或扫描器产生一个发现时，前沿模型通常能为之提出补丁。这并不消除审核的必要性，但把开发者的工作从「理解缺陷并写修复」变成了「验证所提修复是否正确」。后者更快。同样的方法也适用于内存安全迁移：LLM 可以带着测试把一个自包含的 C 模块移植到 Rust；审阅者只需验证等价性，而无需从零开始写整套东西。

### 4. 找出代码中已有的漏洞

打补丁解决的是你们所依赖软件中的已知漏洞。但你们自己的代码库里藏着未知的漏洞。大多数长期运行的生产代码已被人类反复审查过，却从未被前沿模型审视过；而这类分析[往往能浮现出新的、此前被忽视的问题](https://www.youtube.com/watch?v=_IDbFLu9Ug8)。主动扫描可以在攻击者自己发现之前，识别出处于现代 LLM 能力范围内的漏洞。

- *按暴露面排定优先级。* 从解析不可信输入、执行身份验证或授权决策、或可从互联网访问的代码开始。这些路径最可能产生有影响的发现。
- *纳入遗留代码。* 早于当前审查实践的代码，或者其原作者已经离开的代码，往往近期受到的审查最少。这正是你们重新过一遍收益最大的地方。
- *为修复预留预算。* 对旧代码做一次结构良好的模型扫描，通常比部署 SAST 产生的发现更少，但其中真实的比例更高。要为修复这些缺陷规划工程时间。

**实用提示：** 挑一个当前所有者很少的面向互联网服务，扫描它的输入处理与身份验证逻辑。把智能体隔离运行，并加上验证步骤，这样你们就是基于已确认的发现来行动。把一个服务做好，是估算更大范围计划成本的一个合理基点。

### 5. 为遭入侵而设计（Design for breach）

攻击者总会试图在某个地方立足。你们需要限制他们从那里能触及的范围。

那些价值来自「摩擦」——让攻击*枯燥乏味*——而非硬性屏障的缓解措施（额外的跳板跳数、速率限制、非标准端口、基于短信的 MFA），对于那些能硬扛过这些枯燥步骤的对手来说，效果要差得多。我们下面的建议倾向于：即使在攻击者拥有无限耐心时依然成立的控制——硬件绑定的凭据、会过期的令牌、以及根本不存在的网络路径，而非仅仅是「不太方便」的路径。

- *采用零信任架构。* 对服务之间的每一次请求都做身份验证和授权，就像它来自互联网一样。CISA 的[零信任成熟度模型](https://www.cisa.gov/zero-trust-maturity-model)和 NCSC 的[零信任原则](https://www.ncsc.gov.uk/collection/zero-trust-architecture)都提供了分阶段采纳的路径。
- *把访问权限绑定到经过验证的硬件，而非凭据。* 生产系统和敏感的内部工具，应当只能从带有经过验证的硬件身份、并配齐防钓鱼 2FA（FIDO2 或密钥）的受管员工设备访问。仅凭被盗凭据永远不足以获得访问权限。即使生产服务之间的调用，也应植根于硬件身份。
- *按身份隔离服务。* 一台被攻陷的构建服务器，不应能查询生产数据库。一台被攻陷的笔记本，不应能触及构建基础设施。在接收端强制执行这一点：每个工作负载都应携带自己的加密身份，每个服务应只接受来自其策略所命名的具体调用方的连接。网络分段仍能缩小爆炸半径、降低噪声，但它只是个兜底手段。
- *用短期令牌替换长期有效的秘密。* 静态 API 密钥、内嵌凭据、共享的服务账号密码，是拥有模型辅助代码分析能力的攻击者最先会发现的东西。应使用由身份提供商颁发的、短期、窄范围的令牌。

**实用提示：** 完整的零信任是一个多年计划，但身份感知访问代理能把「设备已验证、MFA 把关」的访问放在内部服务之前，而无需从根本上改变其架构。各家主流云厂商都提供原生选项；针对本地或多云环境，也有若干开源和商业替代方案。至于秘密，每家主流云都有托管的秘密存储；把共享范围最广的那一个凭据移入其中并轮换它，对剩下的凭据而言是一种有用的「强制功能」。

### 6. 减少并清点你暴露的东西

本节基于两条重要原则。第一，你无法保卫你不知道的系统。第二，暴露面越小，可被攻击的就越少。

- *维护一份最新的资产清单，* 记录系统中每一个面向互联网的主机、服务和 API 端点。攻击者能跑自动侦察；你们的清单至少应当同样准确。把这些系统纳入你们的渗透测试和红队演练。
- *停用不再使用的系统。* 没有明确所有者的遗留服务，通常也无人打补丁。
- *尽可能缩减每个服务对外暴露的内容。* 默认拒绝网络入站，把 API 表面积限制在真正需要的范围。

**实用提示：** 全网扫描索引可公开检索；拿你们自己的 IP 段和域名去查一下，就能看到攻击者的侦察会看到什么。对于云资产，原生的清单工具（AWS Config、Azure Resource Graph、GCP Asset Inventory）已经存在；难点只在于去查询它们。

AI 在这里也能直接提供帮助：

- *修剪过时代码与系统。* 识别未使用的代码很枯燥——但正如上文所述，AI 模型擅长枯燥任务。一个能读取代码库和流量日志的模型，可以列出没有调用方、也没有流量的端点；在此基础上，它还能解释移除每一项会带来什么影响。
- *自主外部红队。* 让一个 AI 攻击性智能体从外部、在没有任何凭据、也无法访问源码的情况下，指向你们自己的边界。然后，让它做攻击者会做的事：摸清哪些东西可达、做指纹识别，并尝试把它发现的东西串联成一处立足点。这类自动化红队能抓到源码扫描看不到的东西：被遗忘的主机、暴露的管理界面、默认凭据、配置错误的存储。按与资产清单刷新相同的节奏来运行它。

### 7. 缩短事件响应时间

漏洞利用可能在补丁发布后数小时内就出现。需要数天才能响应的流程太慢了。以下是一些缩短事件响应时间的思路：

- *把模型放在警报队列的最前端。* 每一条入站警报，都应在人类看到之前先经过一轮自动化初查。这类「分类智能体」对你们的安全信息与事件管理（SIEM）平台拥有只读权限，并配有一组范围得当的查询工具，能把你们的注意力引导到最需要人类判断的警报上。
- *把仪表驻留时间和覆盖率放在第一位。* 这是 AI 自动化最有能力拉动的两个指标；当利用窗口缩短时，二者都最为关键。
- *把事件周边的文书工作自动化。* 在一次活跃事件中，模型应当做笔记、捕获证据、并行追查多条调查线索，并起草事后复盘与根因分析。而另一方面，*人类*应当负责做出遏制、披露和客户沟通的决定。事件期间人类的决策速度，绝不应在「本更适合交给 AI」的环节（如证据收集、书面记录）上被速率限制。
- *让模型驱动检测飞轮。* 摄取[威胁情报](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)、生成候选检测规则、搜寻匹配项、调优哪些规则该触发——这些现在都已在前沿模型能力之内，模型可以端到端地跑完整个流程。
- *针对五个同时发生的事件做一次桌面推演。* 标准演练假设的是：周一出现一个带有可用漏洞利用的关键 CVE。考虑到我们所看到的 AI 能力进步，这可能并不明智。要真正给你们的响应做压力测试，应当跑「同一周发生五个事件」的版本。
- *对照* [*MITRE ATT&CK*](https://attack.mitre.org/) *绘制检测覆盖图。* ATT&CK 提供了一套攻击者技术的标准词汇表，大多数检测工具本来就在使用它。弄清楚你们能检测哪些技术（以及不能检测哪些），比「改进检测」这个笼统目标更有用。你们应当优先覆盖横向移动和凭据访问。
- *提前制定紧急变更流程。* 生产补丁要走两周的变更审批周期，这本身就是一个安全风险。紧急遏制动作（如让某个服务离线、轮换凭据、或阻断一条网络路径）同理。你们应当提前决定：谁有权授权这些动作，以及授权能有多快。

**实用提示：** 挑一条已知假阳性率较高的「噪声」规则。把前沿模型接入它的警报流，让它对底层数据拥有只读权限，并让它为每一次触发产出结构化的处置结论。用两周时间拿它与人工审阅者比对一致性。如果一致率可以接受，再扩展到下一条规则。一次性把整条队列都自动化并不值得。另外，[Atomic Red Team](https://atomicredteam.io/) 是一个映射到 ATT&CK 技术的、小型安全测试开源库；跑其中几个、再看看你们现有的日志究竟检测到了哪些，是一个一下午就能完成、并能产出具体覆盖图的练习。

以下是一些 AI 能帮助缩短响应时间的方式：

- *首次分类做到 100% 覆盖。* 一个范围明确的分类智能体，可以调查每一条警报（而人类可能只看高于某严重性阈值的），并产出一份结构化的处置结论，供人类接受、驳回或升级。让这件事成立的关键机制是：给模型一套最小工具集（查询、思考、报告），让它自行选择调查策略，并用运营指标来衡量输出。
- *事件记录员与并行调查员。* 在一次活跃事件中，模型可以记录同期笔记、在证据收集时打上时间戳、追查响应人员还没轮到的独立调查线索，并在事件结束后根据记录起草事后复盘。这是前沿模型在安全工作中最不显眼的应用——但很可能也是影响最大的一个。
- *针对你们自己的环境做主动狩猎。* 那种能在源码里找漏洞的智能体，也能在你们的遥测数据里搜寻错误配置与失陷指标。你们可以按与外部攻击面扫描相同的节奏来运行它。

## 向他人提交漏洞报告的建议

如果你们正在扫描代码——无论是自己的依赖项、开源项目还是供应商产品——并把发现上报到上游，那么报告的质量决定了是否会有人据此行动。开源维护者已经收到大量低质量的自动化报告，许多人已经开始无视任何看起来由 AI 生成的内容。在不增加信号的情况下增加音量，只会让包括你们在内的所有人都更糟。

只有在有人验证过、并愿意署名的情形下，才应发送报告。具体来说：

- *用大白话说明这个缺陷及其影响。* 维护者应当仅从第一段就能理解出了什么问题、以及为什么重要，而无需运行任何东西。
- *走一遍代码路径。* 说明输入在哪里进入、在哪里被错误处理、后果在哪里发生。这正是把真实发现与模式匹配区分开来的部分。
- *提供可复现的步骤。* 维护者能运行的 PoC，或一份会失败的测试用例，比任何篇幅的解释都更有说服力。
- *附上一份你作为维护者会接受的补丁。* 一份补丁表明，报告者对代码库有足够了解，能以符合项目惯例的方式解决问题。
- *事先披露 AI 的参与。* 如果模型发现了缺陷或起草了报告，请在第一行就说明。维护者迟早会发现；隐瞒比披露更损害可信度。
- *尊重维护者的判断。* 如果他们拒绝这份报告，你们应当坦然接受。好合作带来的善意，比在一两个缺陷上争赢更有价值。

**实用提示：** 发送漏洞报告前，一个有用的自检是：关掉编辑器，凭记忆把缺陷讲一遍。如果你不回头看模型输出就描述不清到底出了什么问题，那你对其理解还不足以报告它。

## 如果你没有安全团队

上面的大部分建议都假设贵组织设有专门的安全职能。如果你是小型组织、独立开发者或开源维护者，面临的风险相同，但动作更简单：

- *开启自动更新，* 覆盖操作系统、浏览器，以及所有提供该选项的应用。这是单条最有效、且无需持续投入的动作。
- *与其自托管，不如优先选用托管服务。* 让拥有安全团队的供应商去跑数据库、认证和邮件，把打补丁的负担转嫁给他们。这类托管服务的成本，几乎总是低于一次事件的成本。
- *在每个支持的账户上使用密钥（passkey）或硬件安全密钥。* 短信验证码可被拦截，密码会被复用；硬件密钥无法被钓鱼。
- *在你们的代码托管平台上启用免费安全工具。* GitHub 的 Dependabot、密钥扫描和 CodeQL 对公共仓库免费，并能捕获企业级工具所捕获的那部分有意义的漏洞。启用它们只需几分钟。

*如果你维护一个开源项目，请发布一份 `SECURITY.md`，* 说明该联系谁、联系后会发生什么。AI 辅助扫描意味着你们收到的漏洞报告会比以前更多。其中一些很有价值；一些则是自动化的噪声。清晰的接收流程能帮你们区分二者，并向善意的报告者表明：他们的努力不会被浪费。

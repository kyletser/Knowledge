# 像智能体一样看待：我们如何在 Claude Code 中设计工具

构建智能体线束（agent harness）最难的部分之一，就是为它构造工具。

Claude 完全通过[工具调用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)来行动，而在 Claude API 中，工具可以用多种基元构造，例如 [Bash](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool)、[技能（Skills）](https://code.claude.com/docs/en/skills) 和[代码执行](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)。（关于 Claude API 中编程式工具调用的更多内容，可以读 [@RLanceMartin 的新文章](https://x.com/RLanceMartin/status/2027450018513490419)。）

那么，你该如何设计智能体的工具？是给它一个通用工具（比如 Bash 或代码执行），还是给五十个专用工具、每个用例一个？

要站在模型的视角思考，不妨想象自己拿到一道很难的数学题。你需要什么工具来解它？这取决于你自己的技能组合！

纸笔是最低配，但你会受限于手算。计算器更好，可你得知道怎么操作那些更高级的选项。最快、最强大的选择是一台计算机，但你必须知道怎么用它来写代码、跑代码。

这是一个很有用的设计框架：你想给模型的是「贴合它自身能力」的工具。但你又怎么知道它的能力边界在哪？答案是——留意它、读它的输出、做实验。你学会像智能体一样去「看」。

如果你正在构建智能体，就会遇到和我们同样的问题：什么时候该加工具、什么时候该删、又该如何分辨。下面是我们一边构建 Claude Code、一边给出的答案，包括我们最初走错的那些地方。

## 用 AskUserQuestion 工具改进「提问引导」（elicitation）

![](images/21c524f66032-69d919d46e9dceaa0cf307d9-b089e3d3.png)

在构建 AskUserQuestion 工具时，我们的目标是提升 Claude 向用户提问的能力（通常称为 elicitation，提问引导）。

虽然 Claude 原本只能用纯文本提问，但我们发现：回答这些问题给用户的感觉像是花了许多不必要的时间。我们如何降低这种摩擦、提升用户与 Claude 之间的通信带宽？

### 尝试一：改造 ExitPlanTool

我们试的第一种办法，是给 ExitPlanTool 加一个参数，让它在计划旁边附带一组问题。这是实现成本最低的修法，但它把 Claude 搞糊涂了——因为我们同时在要求它「制定计划」和「提一组关于这个计划的问题」。要是用户的回答和计划本身冲突怎么办？Claude 是不是得调用两次 ExitPlanTool？我们清楚这招不行，于是推倒重来。（想了解我们为什么做 ExitPlanTool，可以看[这篇讲提示词缓存的帖子](https://x.com/trq212/status/2024574133011673516)。）

### 尝试二：改输出格式

接着，我们尝试修改 Claude 的输出指令，让它用一种稍作变形的 Markdown 格式来提问。比如，要求它输出一个带要点的「问题列表」，备选答案放在括号里；我们再把它解析、格式化成面向用户的 UI。

Claude 通常能吐出这种格式，但并不可靠：它会多塞句子、漏掉选项，或者直接丢掉结构。于是进入下一个方案。

### 尝试三：AskUserQuestion 工具

![](images/0e7db4621316-69d919d46e9dceaa0cf307dc-208fceac.png)

最终我们落地了一个方案：创建一个 Claude 随时可以调用的工具，但特别提示它在计划模式下这样做。工具一旦触发，我们就弹出一个模态框展示问题，并阻断智能体的循环，直到用户回答。

这个工具让我们能够向 Claude 索取结构化输出，也帮我们确保 Claude 给用户提供多个选项。它还让用户可以把这套能力组合进自己的流程——比如在 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 里调用它，或在技能中引用它。

最重要的是，Claude 似乎「喜欢」调用这个工具，而且我们发现它的输出效果很好。毕竟，哪怕工具设计得再好，如果 Claude 不知道怎么调用它，它也形同虚设。

这就是 Claude Code 里「提问引导」的终态了吗？我们表示怀疑。随着 Claude 能力越来越强，服务它的工具也必须随之演进。下一节会讲一个「曾经好用、后来开始碍事」的工具案例。

### 能力升级：从 Todos 到 Tasks

![](images/86da8eacdf06-69d919d46e9dceaa0cf307df-9f83e911.png)

Claude Code 刚发布时，我们就意识到模型需要一个[待办清单（todo list）](https://platform.claude.com/docs/en/agent-sdk/todo-tracking)来保持在正轨上。待办项可以在开始时写好，模型干活时逐项勾掉。为此我们给了 Claude 一个 TodoWrite 工具，用来写或更新 Todos 并展示给用户。

但即便如此，我们还经常看到 Claude 忘记自己该做什么。为了适应，我们每 5 个回合插入一次系统提醒，把目标重新提示给 Claude。

随着模型变强，它们觉得待办清单反而成了限制。收到待办清单的提醒后，当 Claude 意识到需要改变路线时，它会认为「必须坚持列表」而不是去修改它。我们也看到 Opus 4.5 用子代理用得好多了，但子代理要怎么在一个共享的待办清单上协调？

看到这点，我们用[任务工具（Task tool）](https://x.com/trq212/status/2014480496013803643)替换了 TodoWrite。待办清单的重点是「让模型保持在轨」，而任务的重点是「让智能体之间能互相沟通」：任务可以带依赖关系、跨子代理共享更新，模型还能修改、删除它们。

随着模型能力提升，它们曾经需要的工具，现在反而可能束缚它们。持续重新审视「到底需要哪些工具」这一前提非常重要——这也是为什么，坚持用一小批能力画像相当接近的模型来支撑，会很管用。

## 设计搜索界面

我们构建过最有分量的工具，是那些让 Claude 自己找到上下文的工具。

Claude Code 刚在内部发布时，我们用的是 RAG：向量数据库预索引代码库，线束在每次响应前检索相关片段、塞给 Claude。RAG 虽然强大又快，但它需要索引和配置，而且在各种不同环境里都可能很脆弱。最关键的是——Claude 是*被给予*这段上下文的，而不是自己去*寻找*上下文。

但如果 Claude 能在网上搜索，为什么不能也搜索你的代码库？给它一个 Grep 工具，我们就能让它自己搜文件、自己构建上下文。

随着 Claude 越来越聪明，只要给了合适的工具，它构建上下文的能力就越来越强。

当我们推出 [Agent Skills](https://agentskills.io/home) 时，我们正式化了「渐进式披露（progressive disclosure）」这个思路——它允许智能体通过探索，逐步发现相关上下文。

Claude 现在能读技能文件，而这些文件又能引用模型可以递归读取的其他文件。事实上，技能的一个常见用途，就是给 Claude 追加更多搜索能力，比如教它怎么用某个 API、怎么查某个数据库。

一年之间，Claude 从「基本不会自己构建上下文」，进化到「能跨好几层文件做嵌套搜索、找到它需要的精确上下文」。

渐进式披露，如今成了我们「不新增工具也能加功能」的常用技法。下一节解释原因。

## 渐进式披露：Claude Code 指南子代理

Claude Code 现在有约 20 个工具，我们的团队经常重新审视：到底要不要全部保留，Claude 才能发挥最大效用。新增工具的门槛很高，因为这等于又给模型多了一个要想的选项。

比如，我们注意到 Claude 对「怎么用 Claude Code」知道得不够。你问它怎么加一个 MCP、或者斜杠命令是干嘛的，它答不上来。

我们本可以把这些信息全塞进系统提示词，但考虑到用户很少问这些，那只会带来上下文腐烂（context rot），还会干扰 Claude Code 的主业：写代码。

我们换用渐进式披露：给 Claude 一个指向其文档的链接，它需要时自己加载、搜索。这确实管用，但 Claude 往往会把一大坨文档拽进上下文，只为了找一个用户一句话就能得到的答案。

于是我们构建了「Claude Code 指南」——一个子代理，只要用户问起 Claude Code 本身，主代理就调用它。这个子代理在自己的上下文里做文档搜索，严格遵循「怎么搜、提取什么」的详细指令，最后只把答案交回来。主代理的上下文始终保持干净。

虽然这还不是完美方案（当你问 Claude 怎么给自己做初始化配置时，它仍会犯迷糊），但我们确实做到了「不新增工具，就扩展了 Claude 的行动空间」。

### 像智能体一样「看」，是一门艺术，不是科学

为模型设计工具，既是科学，也是艺术。它高度依赖你用的模型、智能体的目标，以及它所处的环境。

我们最好的建议？多实验、读你的输出、尝试新东西。而最重要的一条：试着像智能体一样去「看」。

*最成功的 Claude Code 部署，在配置、工具和团队结构上都呈现出一组可识别的共同模式。本文是 *Claude Code at scale* 系列的一部分，该新系列将介绍在工程组织以企业级规模使用 Claude Code 时的最佳实践。*

Claude Code 已在生产环境中运行，涵盖数百万行的单体仓库、有数十年历史的遗留系统、横跨数十个代码仓库的分布式架构，以及拥有数千名开发者的组织。这些环境带来了更小、更简单的代码库所没有的挑战，无论那是每个子目录各不相同的构建命令，还是分散在没有共享根目录的文件夹中的遗留代码。

本文介绍我们观察到的、促成 Claude Code 大规模成功落地的模式。我们用"大型代码库"指代范围广泛的部署：拥有数百万行的单体仓库、历经数十年构建的遗留系统、跨独立仓库的数十个微服务，或上述任意组合。这也包括在团队并不总是将其与 AI 编码工具联系起来的语言上运行的代码库，例如 C、C++、C#、Java、PHP。（在这些情况下，Claude Code 的表现往往好于大多数团队的预期，尤其是在最近的模型发布之后。）尽管每个大型代码库的部署都由其特定的版本控制、团队结构和长期积累的约定所塑造，但本文的模式在它们之间具有通用性，是考虑采用 Claude Code 的团队的一个良好起点。

## Claude Code 如何在大型代码库中导航

Claude Code 导航代码库的方式，和软件工程师一样：它遍历文件系统、读取文件、用 grep 精确找到所需内容，并跟踪代码库中的引用。它在开发者的机器上本地运行，无需构建、维护或上传到服务器的代码库索引。

由 RAG 驱动的 AI 编码工具，其工作原理是嵌入整个代码库，并在查询时检索相关片段。在大规模下，这类系统可能失效，因为嵌入管道跟不上活跃的工程团队。等到开发者查询索引时，它反映的已是数周、数天甚至数小时之前的代码库。于是检索会返回团队两周前就已重命名的函数，或引用在上个迭代中已被删除的模块，而且没有任何迹象表明它们已经过时。

智能体式搜索避开了这些故障模式。当数千名工程师提交新代码时，无需维护任何嵌入管道或集中式索引。每个开发者的实例都工作在实时代码库上。

但这种方法有一个权衡：当 Claude 拥有足够的起始上下文、知道该去哪里找时，它效果最好。这意味着 Claude 导航的质量，取决于代码库的设置是否到位，以及能否用 CLAUDE.md 文件和技能层层叠加上下文。如果你让它在一个十亿行的代码库中寻找某个模糊模式的所有实例，工作还没开始就会撞上上下文窗口的限制。在代码库设置上投入的团队，会看到更好的结果。

## 线束与模型同样重要

关于 Claude Code，最常见的误解之一是认为它的能力完全由所采用的模型决定。团队往往关注模型的基准测试，以及它在测试任务上的表现。而在实践中，围绕模型构建起来的生态系统——也就是线束——对 Claude Code 表现的影响，超过了模型本身。

线束由五个扩展点构建而成：CLAUDE.md 文件、钩子（hooks）、技能、插件和 MCP 服务器——每个都承担不同的功能。团队构建它们的顺序很重要，因为每一层都建立在之前的基础之上。还有两项附加能力——LSP 集成和子代理——让整个设置更加完整。下面我们逐一解释这些组件和能力的作用：

[**CLAUDE.md**](https://code.claude.com/docs/en/memory) **文件优先**。这些是 Claude 在每个会话开始时自动读取的上下文文件：根文件提供全局视角，子目录文件提供本地约定。它们为 Claude 提供了把任何事情做好的代码库知识。因为它们无论任务是什么都会在每个会话中加载，所以让它们只聚焦于广泛适用的内容，才能避免拖累性能。

[**钩子**](https://code.claude.com/docs/en/hooks-guide) **让设置自我改进**。大多数团队把钩子视为防止 Claude 做错事的脚本，但它们更有价值的用途是持续改进。一个停止钩子可以回顾会话期间发生的情况，并在上下文还很新鲜时提议更新 CLAUDE.md。一个启动钩子可以动态加载特定于团队的上下文，让每位开发者无需手动配置就能获得自己模块的正确设置。对于代码检查和格式化这类自动检查，钩子会以确定性的方式强制执行规则，比依赖 Claude 记住指令产生更一致的结果。

[**技能**](https://code.claude.com/docs/en/skills) **按需提供恰当的专业知识，而不会让每个会话都变得臃肿。** 在拥有数十种任务类型的大型代码库中，并非所有专业知识都需要在每个会话中出现。技能通过[渐进式披露](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)解决了这个问题：把专门的流程和领域知识卸载出去——否则它们会争夺上下文空间——并且只在任务需要时加载。例如，当 Claude 在评估代码是否存在漏洞时，会加载安全审查技能；而当做了代码改动、需要更新文档时，会加载文档处理技能。

技能还可以限定在特定的路径上，从而只在代码库的相关部分激活。一个负责支付服务的团队可以把他们的部署技能绑定到该目录，这样当有人在单体仓库的其他地方工作时，它绝不会自动加载。

[**插件**](https://code.claude.com/docs/en/plugins) **把行之有效的东西分发开来。** 大型代码库的一个挑战是，*好*的设置往往只停留在小圈子里。插件把技能、钩子和 MCP 配置打包成一个可安装的包，因此当一名新工程师在第一天安装该插件时，他会立即拥有和已经在用 Claude 的人相同的上下文与能力。插件更新可以通过[托管市场](https://support.claude.com/en/articles/13837433-manage-claude-cowork-plugins-for-your-organization)分发给整个组织。

例如，我们合作的一家大型零售组织构建了一个把 Claude 连接到其内部分析平台的技能，让业务分析师无需离开工作流就能拉取绩效数据。在向业务广泛推广之前，他们先把它作为插件分发了出去。

**语言服务器协议（LSP）集成让 Claude 拥有与开发者在 IDE 中相同的导航能力。** 大多数大型代码库的 IDE 已经在运行 LSP，支撑着"跳转到定义"和"查找所有引用"。把这一点呈现给 Claude，就赋予了它符号级的精度：它可以顺着函数调用找到其定义，跨文件追踪引用，并区分不同语言中同名的函数。没有它，Claude 只能做文本上的模式匹配，可能会定位到错误的符号。我们合作的一家大型企业软件公司，在推出 Claude Code 之前就全组织范围部署了 LSP 集成，正是为了让 C 和 C++ 在大规模下的导航可靠无误。对于多语言代码库而言，这是价值最高的投资之一。

**MCP 服务器扩展一切。** MCP 服务器是 Claude 连接到它原本无法触及的内部工具、数据源和 API 的方式。最成熟的团队构建了 MCP 服务器，把结构化搜索作为 Claude 可以直接调用的工具暴露出来。另一些团队则把 Claude 连接到内部文档、工单系统或分析平台。

[**子代理**](https://code.claude.com/docs/en/sub-agents) **把探索与编辑分开。** 子代理是一个独立的 Claude 实例，拥有自己的上下文窗口，它接收任务、完成工作，并只把最终结果返回给父代理。线束就位之后，一些团队会启动一个只读的子代理去梳理某个子系统并把结果写入文件，然后让主代理在掌握全貌的情况下进行编辑。

*Claude Code 的扩展层一览。*

下表总结了每个组件的作用、加载时机，以及我们在每个组件上看到的最常见错误：

| 组件 | 它是什么 | 加载时机 | 最适合 | 常见误区 |
| --- | --- | --- | --- | --- |
| CLAUDE.md | Claude 自动读取的上下文文件 | 每个会话 | 特定于项目的约定、代码库知识 | 把本该属于技能的可复用专业知识塞进它 |
| 钩子 | 在关键时刻运行的脚本 | 由事件触发 | 自动化一致的行为、捕捉会话学习 | 用提示词去处理本应自动运行的事 |
| 技能 | 针对特定任务类型的打包指令 | 按需、在相关时 | 跨会话和项目的可复用专业知识 | 把所有东西都加载进 CLAUDE.md |
| 插件 | 打包的技能、钩子、MCP 配置 | 配置后始终可用 | 在组织内分发行之有效的设置 | 让好的设置停留在小圈子里 |
| 语言服务器协议（LSP）\* | 通过特定于语言的服务器提供实时代码智能 | 配置后始终可用 | 类型化语言中的符号级导航与自动错误检测 | 以为它是自动生效的 |
| MCP 服务器 | 与外部工具和数据的连接 | 配置后始终可用 | 让 Claude 能访问它原本无法触及的内部工具 | 在基础工作就绪之前就先搭 MCP 连接 |
| 子代理\* | 针对特定任务的独立 Claude 实例 | 被调用时 | 把探索与编辑分开、并行工作 | 在同一会话里同时做探索和编辑 |
| \*LSP 通过插件层访问。子代理是一种委派能力，而非可配置的扩展点。 | | | | |

## 成功部署的三种配置模式

如何为一个大型代码库配置 Claude Code，在很大程度上取决于该代码库的结构。尽管如此，在我们观察到的部署中，有三种模式始终出现。

### 让代码库在大规模下可导航

Claude 在大型代码库中提供帮助的能力，受限于它找到正确上下文的能力。每个会话加载过多上下文会降低性能，而上下文太少又会让 Claude 盲目导航。最有效的部署会提前投入，让代码库对 Claude 而言清晰易读。以下几条模式反复出现：

- **保持 CLAUDE.md 文件精简且分层。** Claude 在代码库中移动时会逐级加载它们：根文件提供全局视角，子目录文件提供本地约定。根文件应当只放指针和关键注意事项；其余一切都只会沦为噪音。
- **在子目录中初始化，而不是在仓库根目录。** 当 Claude 的范围被限定在任务真正相关的那部分代码库时，它表现最好。在单体仓库中，这可能感觉反直觉，因为工具通常假定拥有根目录访问权；但 Claude 会自动向上遍历目录树，并加载沿途找到的每一个 CLAUDE.md 文件，因此根级别的上下文永远不会丢失。
- **按子目录划定测试和 lint 命令的范围。** 当 Claude 只改了一个服务却运行全套测试，会导致超时，并把上下文浪费在不相关的输出上。子目录级别的 CLAUDE.md 文件应当指定适用于该部分代码库的命令。这对面向服务的代码库很有效，因为每个目录都有自己的测试和构建命令。在具有深层跨目录依赖的编译型语言单体仓库中，按子目录划定范围较难实现，可能需要特定于项目的构建配置。
- **使用 `.ignore` 类文件（如 `.gitignore`）来排除生成的文件、构建产物和第三方代码。** 在 `.claude/settings.json` 中提交 `permissions.deny` 规则，意味着这些排除项是受版本控制的，因此团队中每位开发者都能获得同样的降噪效果，而无需自己配置。在某些代码库中，生成的文件本身就是开发工作的对象。开发代码生成器的开发者可以在本地设置中覆盖项目级的排除项，而不影响团队其他成员。
- **当目录结构本身不顶用时，构建代码库地图。** 对于代码没有整合在常规目录结构中的组织，在仓库根目录放一个轻量的 markdown 文件，列出每个顶级文件夹并附上一行说明其中内容，就能给 Claude 一份在打开文件之前可以先扫一眼的目录。对于拥有数百个顶级文件夹的代码库，分层方式效果最好：根文件只描述最高层的结构，子目录的 CLAUDE.md 文件提供下一层的细节，并随着 Claude 在树中移动而按需加载。对于更简单的情况，用 @ 提及 Claude 应当参考的具体文件或目录，也能达到同样的效果。
- **运行 LSP 服务器，让 Claude 按符号而非按字符串搜索。** 在大型代码库中用 grep 搜索一个常见函数名会返回数千个匹配项，而 Claude 要消耗上下文去打开文件，才能弄清哪个才是重要的。LSP 只返回指向同一符号的引用，因此过滤发生在 Claude 读取任何内容之前。要启用它，需要为你的语言安装一个[代码智能插件](https://code.claude.com/docs/en/discover-plugins#code-intelligence)以及相应的语言服务器二进制文件；Claude Code 文档中涵盖了可用的插件和故障排查方法。

**一个提醒**：存在一些边缘情况，即便分层式的 CLAUDE.md 方案也会失效，例如拥有数十万个文件夹和数百万个文件的代码库，或是基于非 git 版本控制的遗留系统。我们将在本系列未来的篇章中解决这些挑战。关于遗留系统，请参阅 AI 如何[*打破 COBOL 现代化的成本壁垒*](https://claude.com/blog/how-ai-helps-break-cost-barrier-cobol-modernization)。

### 随着模型智能提升，主动维护 CLAUDE.md 文件

随着模型演进，为当前模型编写的指令可能会对未来的模型起反作用。那些曾引导 Claude 走完它过去挣扎不已的模式的 CLAUDE.md 文件，等到下一代模型发布时，可能变得不再必要，甚至成为一种主动的限制。例如，一条要求 Claude 把每次重构都拆成单文件改动的 CLAUDE.md 规则，或许曾帮助较早的模型保持正轨，却会阻止较新的模型去做它本就擅长的、协调性的跨文件编辑。

为了弥补特定模型局限而构建的技能和钩子——无论是模型推理上的，还是 Claude Code 自身工具上的——一旦那些局限不复存在，就会变成负担。例如，一个拦截文件写入以在 Perforce 代码库中强制 `p4 edit` 的钩子，在 Claude Code 加入原生的 Perforce 模式后就变得多余了。

团队应当预期每三到六个月做一次有实质意义的配置审查；而当主要模型发布后，性能感觉像陷入瓶颈时，也值得做一次。

### 明确 Claude Code 管理与推广的所有权

仅有技术配置，还不足以推动采用。那些做对的团队，也在组织层面做了投入。

传播最快的推广，在广泛开放之前都先做了专门的基础设施投入。一个小团队——有时甚至只有一个人——把工具接好，使得开发者第一次接触 Claude 时，它就已经契合开发者的工作流。在一家公司，几位工程师构建了一套插件和 MCP，在第一天就可用。在另一家公司，一个专门负责管理 AI 编码工具的完整团队，在推广开始之前就已把基础设施准备就绪。两种情况下，开发者的初次体验都是富有成效而非令人沮丧的，采用率也从那里扩散开来。

![](images/e61a44f9971a-6a04e25f1984beb50dc5525b-fig2-phases-of-claude-cod.png)

如今从事这项工作的团队，往往隶属于开发者体验（DX）或开发者生产力（DP）部门，这通常也是负责新工程师入职和构建开发者工具的职能。在若干组织中，一个新兴角色是智能体经理（agent manager）：一个混合了 PM 与工程师职能、专门负责管理 Claude Code 生态系统的岗位。对于没有专门团队的组织，最小可行版本是一个 DRI（直接责任人）：一个人拥有 Claude Code 配置的所有权，有权对设置、权限策略、插件市场和 CLAUDE.md 约定做出决策，并有责任让它们保持更新。

自下而上的采用能激发热情，但如果没有人把行之有效的做法集中起来，就会走向碎片化。你需要有一个人或一个团队，去整理并推行正确的 Claude Code 约定（例如标准化的 CLAUDE.md 层级结构，或一组精选的技能和插件）。没有这项工作，知识就会停留在小圈子里，采用率也会陷入停滞。

在大型组织中，尤其是受监管行业中的组织，治理问题会早早浮现，例如：谁来控制哪些技能和插件可用？如何防止数千名工程师各自独立重建同样的东西？如何确保 AI 生成的代码与人类生成的代码经历相同的审查流程？为了尽早应对这些问题，我们建议从一组已批准的技能、必需的代码审查流程，以及受限的初始访问权限开始，并随着信心的建立而逐步扩展。

我们观察到，那些早早建立跨职能工作组的组织，部署最为顺畅——它们把工程、信息安全和治理的代表聚集在一起，共同定义需求并制定推广路线图。

## 将这些模式应用到你的组织中

Claude Code 是围绕传统的软件工程环境设计的：工程师是代码库的主要贡献者，仓库使用 Git，代码遵循标准目录结构。大多数大型代码库都符合这个模式，但非传统的设置——例如带有大型二进制资源的游戏引擎、采用非常规版本控制的环境，或是由非工程师向代码库贡献代码——则需要额外的配置工作。我们的指南假设采用传统设置，而我们描述的这些模式已在许多客户中奏效。任何剩余的复杂性，都需要结合你的代码库、工具和组织的具体情况来判断。这正是 Anthropic 的应用 AI 团队直接与工程团队合作，将这些模式转化为你组织的具体要求之处。

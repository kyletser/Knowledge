单个智能体系统足以高效处理大多数企业工作流，而多智能体架构能为你的组织解锁额外价值。本文将说明何时以及如何使用它们。

## 什么是多智能体系统？

多智能体系统是一种架构，其中多个 LLM 实例在彼此独立的对话上下文中运行，并通过代码进行协调。每个智能体负责任务中不同的一部分——例如，协调器在规划时，子代理负责研究——这能保护上下文、支持并行工作，并带来单个智能体无法维持的专业化能力。

存在多种协调模式（智能体群组、基于能力的系统、消息总线架构），但本文聚焦于「协调器—子代理」模式：一种分层模型，由一个主导智能体为特定子任务生成并管理专门的子代理。这种模式提供了简洁的协调机制，是刚接触多智能体系统的团队很好的起点。其他模式我们将在下一篇文章中详细探讨。

如今，多智能体系统常常被用在单个智能体表现更佳的场景中，不过这种权衡会随模型进步而不断演变。在 Anthropic，我们见过团队花数月搭建复杂的多智能体架构，最后却发现，只要在单个智能体上改进提示词，就能取得同等效果。

在构建多智能体系统并与生产环境中部署它们的团队合作之后，我们确定了多智能体始终优于单智能体的三种情况：上下文腐烂拉低性能时、任务可以并行运行时，以及专业化能改善工具选择或任务焦点时。在这些情况之外，协调成本通常会超过收益。

在本文中，我们将分享如何识别单智能体的局限、认清多智能体系统大放异彩的三种场景，并避免常见的实现错误。

## 为什么应从单智能体起步

一个设计良好、配备了合适工具的单个智能体，能完成的工作远超许多开发者的预期。

多智能体系统会带来额外开销。每多一个智能体，就意味着多一个潜在的故障点、多一套需要维护的提示词，以及多一个产生意外行为的来源。

我们观察到，有些团队搭建了复杂的多智能体系统——用独立的智能体分别负责规划、执行、审查与迭代——结果却发现，每次交接都会丢失上下文，而且花在协调上的 token 比执行任务本身还多。在我们的测试中，对于同等任务，多智能体实现通常比单智能体方案多用 3 到 10 倍的 token。这种开销来自智能体之间的上下文复制、智能体之间的协调消息，以及在交接时汇总结果。

## 多智能体系统的决策框架

当一个多智能体架构能解决单智能体无法克服的特定约束时，它才真正创造价值。这意味着多智能体架构应当只保留给那些能带来明显收益、足以证明额外成本合理的场景。托管基础设施也可以替你处理这个问题（参见 [Claude Managed Agents 中的多智能体编排](https://claude.com/blog/new-in-claude-managed-agents)）。

以下模式，是我们持续观察到此项投资能带来正回报的情况。

### 上下文保护

大语言模型的上下文窗口是有限的，而响应质量会随上下文增长而下降。当某个智能体的上下文累积了来自某一子任务、但对后续子任务无关的信息时，就会发生上下文腐烂。子代理提供了隔离：每个子代理都在自己干净的上下文中运行，专注于其特定任务。

设想一个客服智能体，需要在诊断技术问题的同时检索订单历史。如果每次订单查询都向上下文里塞进上千个 token，它推理技术问题的能力就会下降。

**单智能体方案：**

```python
# 单智能体把一切都累积在上下文中
conversation_history = [
    {"role": "user", "content": "My order #12345 isn't working"},
    {"role": "assistant", "content": "Let me check your order..."},
    # 工具返回结果追加了 2000+ token 的订单历史
    {"role": "user", "content": "... (order details, past purchases, shipping info) ..."},
    {"role": "assistant", "content": "Now let me diagnose the technical issue..."},
    # 上下文现在被智能体不需要的订单细节污染了
]
```

智能体必须一边推理技术问题，一边在上下文中维护 2000 多个与订单历史无关的 token，注意力被稀释，响应质量随之下降。

**多智能体方案：**

```python
from anthropic import Anthropic

client = Anthropic()

class OrderLookupAgent:
    def lookup_order(self, order_id: str) -> dict:
        # 拥有独立上下文的分离智能体
        messages = [
            {"role": "user", "content": f"Get essential details for order {order_id}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            messages=messages,
            tools=[get_order_details_tool]
        )
        # 只返回必要信息
        return extract_summary(response)

class SupportAgent:
    def handle_issue(self, user_message: str):
        if needs_order_info(user_message):
            order_id = extract_order_id(user_message)
            # 只获取所需内容，而非完整历史
            order_summary = OrderLookupAgent().lookup_order(order_id)
            # 注入精简摘要，而非完整上下文
            context = f"Order {order_id}: {order_summary['status']}, purchased {order_summary['date']}"

        # 主智能体上下文保持干净
        messages = [
            {"role": "user", "content": f"{context}\n\nUser issue: {user_message}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            messages=messages
        )
        return response
```

订单查询智能体处理完整的订单历史并提取出摘要。主智能体只接收它真正需要的 50–100 个 token，上下文保持聚焦。

当子任务产生大量上下文（超过 1000 个 token），但其中大部分信息与主任务无关；当子任务定义清晰、对要提取哪些信息有明确标准；以及对于使用前需要过滤的查询或检索操作时，上下文隔离最为有效。

### 并行化

并行运行多个智能体，能让你探索比单个智能体覆盖范围更大的搜索空间。这种模式已被证明对搜索和研究类任务特别有价值。

Anthropic 的研究团队在 [我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system) 一文中记录了这一点。一个主导智能体分析查询，并生成多个子代理，并行调查不同侧面。每个子代理独立搜索，然后返回提炼后的发现。多智能体搜索允许在更大的信息空间中进行探索，相比单智能体方案展现出了显著的准确率提升。

其核心实现是把一个问题拆解为相互独立的侧面，同时运行子代理，然后综合结果。

```python
import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def research_topic(query: str) -> dict:
    # 主导智能体将查询拆解为研究侧面
    facets = await lead_agent.decompose_query(query)

    # 生成子代理，并行研究每个侧面
    tasks = [
        research_subagent(facet)
        for facet in facets
    ]
    results = await asyncio.gather(*tasks)

    # 主导智能体综合各项发现
    return await lead_agent.synthesize(results)

async def research_subagent(facet: str) -> dict:
    """每个子代理都拥有自己的上下文窗口"""
    messages = [
        {"role": "user", "content": f"Research: {facet}"}
    ]
    response = await client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        messages=messages,
        tools=[web_search, read_document]
    )
    return extract_findings(response)
```

这种覆盖范围的扩大是有代价的。对于同等任务，多智能体系统通常比单智能体方案多消耗 3 到 10 倍的 token。原因包括：每个智能体都需要自己的上下文、智能体之间必须通过消息交换来协调，以及结果在智能体间传递时必须经过汇总。虽然并行化相比顺序执行全部工作有助于减少总执行时间，但由于总计算量大幅增加，多智能体系统的整体耗时往往反而比单智能体更长。

并行化的主要收益是「彻底性」，而非速度。当你需要搜索一个庞大的信息空间、或调查复杂问题的多个角度时，并行智能体能比受困于自身上下文限制的单个智能体覆盖更多内容。代价是更高的 token 消耗，以及通常更长的整体执行时间，以换取更全面的结果。

### 专业化

不同的任务有时受益于不同的工具集、系统提示词或专业领域。与其给单个智能体接入几十种工具，不如让专门的智能体配备与其职责相匹配的聚焦工具集，从而提升可靠性。

#### 工具集专业化

当智能体能用的工具过多时，性能就会下降。有三个信号表明工具专业化会有帮助：

1. **数量。** 一个智能体拥有过多工具（往往超过 20 个）时，便难以选对合适的那个。
2. **领域混淆。** 当工具横跨多个互不相干的领域（数据库操作、API 调用、文件系统操作）时，智能体会搞混哪个领域适用于当前任务。
3. **性能下降。** 新增工具导致既有任务性能退化，说明该智能体在工具管理上已触及上限。

#### 系统提示词专业化

不同的任务有时需要不同的人物角色、约束或指令，而这些内容组合在一起时会相互冲突。客服智能体需要共情与耐心；代码审查智能体需要精确与挑剔。合规检查智能体需要严格按规则行事；头脑风暴智能体则需要创造性的灵活性。当单个智能体不得不在相互冲突的行为模式间切换时，拆分成带有定制系统提示词的专门智能体，能产出更一致的结果。

每个专门智能体的好坏，取决于它的指令质量——那些能改善单个智能体输出的 [提示词工程最佳实践](https://claude.com/blog/best-practices-for-prompt-engineering)，同样适用于每个子代理的系统提示词。

#### 领域专业知识专业化

有些任务受益于深层领域上下文，而这会让通才智能体不堪重负。法律分析智能体可能需要关于判例法和监管框架的大量背景知识。医学研究智能体可能需要临床试验方法学的专业知识。与其把所有领域上下文都塞进单个智能体，专门的智能体可以承载与其特定职责相关的聚焦专业知识。

**示例：多平台集成。** 设想一个集成系统，智能体需要跨 CRM、营销自动化与消息平台工作。每个平台都有 10–15 个相关 API 端点。一个拥有 40 多个工具的单个智能体，常常难以正确选择，还会把跨平台的相似操作搞混。拆分成工具集聚焦、提示词定制的专门智能体，就能解决这类选择错误。

```python
from anthropic import Anthropic

client = Anthropic()

# 配备聚焦工具集与定制提示词的专门智能体
class CRMAgent:
    """负责客户关系管理操作"""
    system_prompt = """You are a CRM specialist. You manage contacts,
    opportunities, and account records. Always verify record ownership
    before updates and maintain data integrity across related records."""
    tools = [
        crm_get_contacts,
        crm_create_opportunity,
        # 8-10 个 CRM 专属工具
    ]

class MarketingAgent:
    """负责营销自动化操作"""
    system_prompt = """You are a marketing automation specialist. You
    manage campaigns, lead scoring, and email sequences. Prioritize
    data hygiene and respect contact preferences."""
    tools = [
        marketing_get_campaigns,
        marketing_create_lead,
        # 8-10 个营销专属工具
    ]

class OrchestratorAgent:
    """将请求路由到专门智能体"""
    def execute(self, user_request: str):
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            system="""You coordinate platform integrations. Route requests to the appropriate specialist:
- CRM: Contact records, opportunities, accounts, sales pipeline
- Marketing: Campaigns, lead nurturing, email sequences, scoring
- Messaging: Notifications, alerts, team communication""",
            messages=[
                {"role": "user", "content": user_request}
            ],
            tools=[delegate_to_crm, delegate_to_marketing, delegate_to_messaging]
        )
        return response
```

这种模式折射出高效的职业协作：拥有与其角色相匹配工具的专家，比试图在一切领域都保持专精的通才协作得更有效。然而，专业化也引入了路由复杂度。协调器必须正确分类请求并将其委派给正确的智能体，而错误路由会导致糟糕的结果。维护多个专门智能体还会增加提示词的维护开销。当各领域可以清晰分离、且路由决策明确无歧义时，专业化效果最佳。

## 何时超越了单智能体架构

除了总体框架之外，某些具体的信号表明，单智能体模式已经不够用了：

**逼近上下文上限。** 如果某个智能体经常使用大量上下文且性能在下降，上下文压力可能就是瓶颈。请注意，上下文管理的最新进展（[例如压实](https://platform.claude.com/cookbook/tool-use-automatic-context-compaction)）正在削弱这一限制，让单个智能体能跨越更长的时段维持有效记忆。

**管理大量工具。** 当智能体拥有 15–20 个以上工具时，模型要耗费大量上下文和注意力去理解自己的选项。在采用多智能体架构之前，不妨考虑使用 [工具搜索工具](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/tool-search-tool)（Tool Search Tool），它让 Claude 按需动态发现工具，而不是预先加载所有定义。这能 [将 token 用量减少多达 85%](https://www.anthropic.com/engineering/advanced-tool-use)，同时提升工具选择的准确度。

**可并行的子任务。** 当任务能自然拆解为彼此独立的部分（跨多个来源的研究、多个组件的测试）时，并行子代理能带来显著的加速。

这些阈值会随模型进步而变动。当前的限制只是实用指南，而非根本性约束。

## 以上下文为中心的分解

采用多智能体架构时，最重要的设计决策是如何在智能体之间划分工作。我们观察到，团队经常在这一选择上出错，导致协调开销抵消了多智能体设计本应带来的收益。

关键的洞见是：在分解工作时，采取**以情境为中心**的视角，而非以问题为中心。

**以问题为中心的分解（往往适得其反）。** 按工作类型划分（一个智能体写功能，另一个写测试，第三个做代码审查）会产生持续的协调开销。每次交接都会丢失上下文。负责写测试的智能体不了解某些实现决策背后的原因，而代码审查者又缺乏探索与迭代的上下文。

**以上下文为中心的分解（通常有效）。** 按上下文边界划分，意味着负责某个功能的智能体也应当负责它的测试，因为它已经掌握了必要的上下文。只有当上下文能够被真正隔离时，才应该拆分工作。

这一原则源自对多智能体系统失效模式的观察。当智能体按问题类型拆分时，它们会玩起一场「传话游戏」：在每次交接中来回传递信息，保真度不断下降。在一次针对软件开发角色（规划者、实现者、测试者、审查者）的专门智能体实验中，子代理花在协调上的 token 比花在真正工作上的还多。

**有效的分解边界包括：**

- **独立的研究路径。** 调查「亚洲市场趋势」与「欧洲市场趋势」可以在没有共享上下文的情况下并行推进。
- **接口干净的独立组件。** 有了清晰定义的 API 契约，前端与后端工作就能并行进行。
- **黑盒验证。** 一个只需运行测试并报告结果的验证者，并不需要实现上下文。

**有问题的分解边界包括：**

- **同一工作的连续阶段。** 同一功能的规划、实现与测试共享了太多上下文。
- **紧耦合的组件。** 需要不断来回交互的组件应当属于同一个智能体。
- **需要共享状态的工作。** 需要频繁同步理解的智能体应当保持在一起。

## 验证子代理模式

有一种跨领域始终有效的多智能体模式，那就是**验证子代理**。这是一个专门的智能体，唯一职责就是测试或验证主智能体的工作。

值得一提的是，能力更强的协调器模型（如 Claude Opus 4.5）越来越能够直接评估子代理的工作，无需单独的验证步骤。不过，当使用能力较弱的编排器、验证需要专门工具，或你想在工作流中强制设置显式的验证检查点时，验证子代理依然很有价值。

验证子代理之所以成功，是因为它们绕开了传话游戏问题。验证本质上只需要极少的上下文传递，因此验证者可以对系统做黑盒测试，而无需了解它的完整构建历史。

### 实现一个多智能体系统

主智能体完成一个工作单元。在继续之前，它会生成一个验证子代理，附上待验证的产物、明确的成功标准，以及执行验证所需的工具。

验证者无需理解产物为何要那样构建。它只需要判断产物是否满足指定的标准。

```python
from anthropic import Anthropic

client = Anthropic()

class CodingAgent:
    def implement_feature(self, requirements: str) -> dict:
        """主智能体实现功能"""
        messages = [
            {"role": "user", "content": f"Implement: {requirements}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[read_file, write_file, list_directory]
        )
        return {
            "code": response.content,
            "files_changed": extract_files(response)
        }

class VerificationAgent:
    def verify_implementation(self, requirements: str, files_changed: list) -> dict:
        """独立智能体验证工作"""
        messages = [
            {"role": "user", "content": f"""
Requirements: {requirements}
Files changed: {files_changed}

Run the test suite and verify:
1. All existing tests pass
2. New functionality works as specified
3. No obvious errors or security issues

You MUST run the complete test suite before marking as passed.
Do not mark as passing after only running a few tests.
Run: pytest --verbose
Only mark as PASSED if ALL tests pass with no failures.
"""}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[run_tests, execute_code, read_file]
        )
        return {
            "passed": extract_pass_fail(response),
            "issues": extract_issues(response)
        }

def implement_with_verification(requirements: str, max_attempts: int = 3):
    for attempt in range(max_attempts):
        result = CodingAgent().implement_feature(requirements)
        verification = VerificationAgent().verify_implementation(
            requirements,
            result['files_changed']
        )

        if verification['passed']:
            return result

        requirements += f"\n\nPrevious attempt failed: {verification['issues']}"

    raise Exception(f"Failed verification after {max_attempts} attempts")
```

### 多智能体系统的应用场景

验证子代理在以下场景很有效：

- **质量保证。** 运行测试套件、检查代码、对照模式校验输出。
- **合规检查。** 验证文档是否满足政策要求，对照规则检查输出。
- **输出验证。** 在交付前确认生成内容符合规格。
- **事实核查。** 用独立的智能体验证生成内容中的主张或引用。

### 早期胜利问题

验证子代理最显著的失效模式，是在没有充分测试的情况下就把输出标记为通过。验证者跑了一两个测试，看到它们通过，便宣告成功。

缓解策略包括：

- **具体标准。** 写明「运行完整的测试套件并报告所有失败」，而不是「确保它能工作」。
- **全面检查。** 要求验证者测试多种场景与边界情况。
- **负面测试。** 指示验证者尝试那些本应失败的输入，并确认它们确实失败。
- **明确指令。** 「在标记为通过之前，你必须运行完整的测试套件」这一指令至关重要。在没有对全面验证的明确要求时，验证智能体会走捷径。

## 在单智能体与多智能体系统之间做选择

多智能体系统功能强大，但并非普遍适用。在增加多个协调智能体的复杂度之前，请先确认：

1. **存在真正的约束**，且多智能体能解决它，例如上下文限制、并行化机会或专业化的需求。
2. **分解遵循上下文，而非问题类型。** 按工作所需的上下文来分组，而不是按工作种类来分组。
3. **存在清晰的验证点**，子代理能在无需完整上下文的情况下验证工作。

我们的建议？从最简单、可行的方案起步，只有在证据支持时才增加复杂度。

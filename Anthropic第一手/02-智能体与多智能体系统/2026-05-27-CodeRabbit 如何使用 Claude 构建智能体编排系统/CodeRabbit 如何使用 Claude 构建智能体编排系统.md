AI 编程工具，已经把「从想法到可用原型」之间的时间压缩到了极短。CodeRabbit 作为一家 AI 代码审查平台，却注意到一个随着吞吐量一同攀升的相反趋势：代码能通过编译、也能通过测试，却没有真正做出团队原本想要构建的东西。

CodeRabbit 的 AI 副总裁 David Loker 把根源定位在了模型的上游。有经验的开发者常常默认编码智能体理解着和他们相同的上下文，于是那些对他们来说「显而易见」的需求，他们并不会写下来。编码智能体于是用自己的「合理猜测」去填补这些空白。

为了弥合这道鸿沟，CodeRabbit 用 Claude 设计并搭建了一套智能体编排系统，它会在任何代码生成之前，先跑一段结构化的规划阶段。团队的核心论点是：规划质量决定了输出质量；而代码生成越便宜，走错方向所付出的代价就越高。

## 弥合 AI 编程中的内部知识鸿沟

当 CodeRabbit 团队研究其客户群中的 AI 生成 pull request 时，最高频的失败模式是：代码能编译、能通过测试，却仍然没有解决它本应解决的问题。

「随着我们作为开发者积累了经验，我们把很多知识内化了，」Loker 说，「所有这些东西都在我们脑子里，我们也默认其他开发者知道。但接着我们又把这个假设套用到了 AI 系统上，以为它也同样心领神会。我们甚至没有意识到自己正在做这些假设。」

模糊的提示词，会迫使底层系统用自认为合理的东西去填补空白。而这种猜测，往往与开发者心中的本意背道而驰。

Loker 举了一个自己的例子。在一个副业项目里搭建记忆系统时，他用编码智能体反复迭代了几个小时，直到一切都能跑起来。当他问智能体该怎么使用时，得到的指引是让他传一个用户 token 进来——可根本没有登录页面。他确实说过系统需要用户，却从未说过用户得有一种登录方式。智能体填补了这个空白，于是几个小时的成果，落进了一个「没有前门」的产品里。

「最后的结果就是，你在它上面又叠了一大堆东西，然后很久以后才发现这里有问题，」Loker 说，「在 AI 工作流里，滞后的验证可能极其昂贵。」

## 在 AI 编程方案之前运行的编排层

CodeRabbit 的应对之策，是在代码生成之前插入一套规划系统。它协调多个 Claude 模型，先分析需求、暴露隐含假设，再产出一份结构化的执行计划——明确界定「该构建什么」以及「需要满足哪些约束」。

「这套规划系统并非要取代 Claude Code 的 Plan Mode（规划模式），」Loker 说，「它是发生在 Claude Code 之前、更高一层的编排：把方向收窄、指准，让所有需要显式表达的东西都显式化，并且让我们清楚意识到所有正在被做出的假设。」

其产出是一份协作式的产品需求文档（PRD）：一份在完整上下文下拟定的计划，由团队各干系人共同确认，并在实现启动前经过审阅。Claude Code 接过这份计划，据以生成更细颗粒度的实现方案。这份计划由此成为一个共享的工件，记录下「做了什么决定、以及为什么」——它不仅帮助团队避免返工、在事后验证输出是否契合最初意图，还能用于新人上手。

## 在 Claude 模型家族间做路由

CodeRabbit 把每个模型档位与任务复杂度相匹配，以优化成本与延迟。Opus 驱动该编排循环，并承担「理解问题、定下总体方向」这类更高层的策略性工作。Sonnet 接过其输出，把它拆解为结构化的规划步骤。Haiku 则处理范围狭窄的操作，例如上下文蒸馏与定向工具调用——这类问题足够具体，小模型也能答得很好。

「如果 Haiku 在某项任务上表现和 Sonnet 一样好，我们就用 Haiku，」Loker 说，「如果评测框架告诉我们，给 Opus 更多空间后计划质量会提升，我们就给它更多空间。我们不做猜测。」

## 为「计划质量」构建评测框架

CodeRabbit 早已有一套成熟的代码审查评测系统，却没有任何东西用来评估规划产出。搭建这套基础设施，本身成了一个独立项目。

系统起步于手调的样例与人工检视。团队开发了一整套 LLM 评审器，对计划质量的各个维度打分。由于计划最终会产出代码，团队还能衡量：生成的代码是否真的可用、是否包含了多余的范畴（scope creep）、以及为了抵达那里花了多少 token。对同一个任务分别「带规划步骤」和「不带规划步骤」地跑一遍，就让他们有了一种方法，得以单独剥离出「规划」本身的价值。

「我们当初并没有意识到，那份计划该有的细节粒度究竟该多细，」Loker 说。过于细碎的计划，代码库稍有变动就立刻失效；过于高层的计划，又会给智能体留下自行填补假设的空间——而这恰恰是规划层本要解决的问题。找到那个「恰到好处的抽象层级」，需要反复迭代，而这也正是评测框架使之成为可能的原因。

## 在写下任何代码之前就抓住错误

在 AI 原生的编程工作流里，许多原本会在代码审查阶段才浮现的决策，如今都被提前到了规划层。在代码生成启动之前，先做出一份团队能够审阅、达成一致的计划，就能及早抓住错误。

「我们借助 Claude 生态所构建的，是一套全团队共享的规划系统，」Loker 说，「计划本身成了质量关卡。如果我们能确保这份计划在一开始就足够好，那么下游的影响是极其显著的。最终你拿到手的代码，会好上很多。」

**来自 CodeRabbit 团队的最佳实践**

- **你真正想要创造的是什么结果，又该如何衡量？** 不仅要对 AI 明确说明规格，还要界定你在 MPP（最大可能产品，Maximum Possible Product）中所想要的东西。
- **还有哪些假设仍然是隐含的？** 问问 Claude：缺了什么？计划里有没有哪些部分，是以隐含假设的形式出现、而非显式规格的？
- **哪些工作流或边界情况容易被遗忘？** 请 Claude 帮你找出那些你可能没考虑到的地方或情形。
- **在正式上线前，你如何确认输出契合意图？** 建立一份工作记录：一套被保存并复用的规划工件编年史。

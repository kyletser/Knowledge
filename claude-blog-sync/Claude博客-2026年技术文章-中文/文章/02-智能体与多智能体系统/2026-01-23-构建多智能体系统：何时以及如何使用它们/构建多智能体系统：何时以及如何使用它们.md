# 构建多智能体系统：何时以及如何使用它们

> 发布日期：2026-01-23 · [原文链接](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) · 机器翻译，仅供学习。

## 什么是多智能体系统？

多智能体系统是一种架构，其中多个 LLM 实例在单独的对话上下文中运行，并通过代码进行协调。每个智能体处理任务的不同部分（例如，子代理在协调器计划时进行研究），这可以保护上下文，实现并行工作，并允许单个智能体无法维持的专业化。

存在多种协调模式（智能体群、基于功能的系统和消息总线架构），但本文重点关注协调器子代理模式：分层模型，其中领导智能体生成并管理特定子任务的专用子代理。此模式提供了简单的协调模型，对于刚接触多智能体系统的团队来说是一个很好的起点。我们将在下一篇文章中详细探讨其他模式。

如今，多智能体系统通常应用于单个智能体性能更好的情况，尽管这种计算随着模型的改进而不断发展。在 Anthropic，我们看到团队花费数月时间构建复杂的多智能体架构，结果发现单个智能体上改进的提示取得了相同的结果。

在构建多个智能体系统并与在生产中部署它们的团队合作后，我们确定了多个智能体始终优于单个智能体的三种情况：当上下文污染降低性能时、当任务可以并行运行时以及当专业化改善工具选择或任务焦点时。在这些情况之外，协调成本通常会超过收益。

在本文中，我们分享如何识别单智能体限制，识别多智能体系统 Excel 的三种场景，并避免常见的实施错误。

## 从单个智能体开始的情况

精心设计的单个智能体加上适当的工具可以完成远远超出许多开发人员预期的工作。

多智能体系统会带来开销。每个额外的智能体都代表另一个潜在的故障点、另一组需要维护的提示词以及另一个意外行为源。

我们观察到团队构建了复杂的多智能体系统，并使用单独的智能体进行规划、执行、审查和迭代，结果发现他们在每次切换时都会丢失上下文，并且在协调上花费的代币多于执行的代币。在我们的测试中，对于同等任务，多智能体实现通常使用比单智能体方法多 3-10 倍的令牌。此开销源于智能体之间的上下文复制、智能体之间的协调消息以及汇总切换结果。

## 多智能体系统的决策框架

多个智能体架构在解决单个智能体无法克服的特定约束时提供价值。这意味着多智能体架构应保留用于其提供明显优势且证明额外成本合理的情况。 托管基础设施也可以为您处理这个问题（请参阅 [Claude Managed Agents 中的多代理编排）](https://claude.com/blog/new-in-claude-managed-agents).

以下模式代表了我们持续观察到此项投资正回报的情况。

### 上下文保护

大型语言模型的上下文窗口有限，响应质量可能会随着上下文的增长而降低。当智能体的上下文从一个子任务累积与后续子任务无关的信息时，就会发生上下文污染。子代理提供隔离，每个子代理都在自己的干净上下文中运行，专注于其特定任务。

假设客户支持智能体需要在诊断技术问题时检索订单历史记录。如果每次订单查找都会向上下文添加数千个令牌，则智能体的推理技术问题的能力就会降低。

‍

**单智能体方法：**

```
# Single agent accumulates everything in context
conversation_history = [
    {"role": "user", "content": "My order #12345 isn't working"},
    {"role": "assistant", "content": "Let me check your order..."},
    # Tool result adds 2000+ tokens of order history
    {"role": "user", "content": "... (order details, past purchases, shipping info) ..."},
    {"role": "assistant", "content": "Now let me diagnose the technical issue..."},
    # Context is now polluted with order details the agent doesn't need
]
```

智能体必须推理技术问题，同时在上下文中维护 2000 多个不相关订单历史记录的代币，从而分散注意力并降低响应质量。

‍

**多智能体方法：**

```
from anthropic import Anthropic

client = Anthropic()

class OrderLookupAgent:
    def lookup_order(self, order_id: str) -> dict:
        # Separate agent with its own context
        messages = [
            {"role": "user", "content": f"Get essential details for order {order_id}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            messages=messages,
            tools=[get_order_details_tool]
        )
        # Returns only essential information
        return extract_summary(response)

class SupportAgent:
    def handle_issue(self, user_message: str):
        if needs_order_info(user_message):
            order_id = extract_order_id(user_message)
            # Get only what's needed, not full history
            order_summary = OrderLookupAgent().lookup_order(order_id)
            # Inject compact summary, not full context
            context = f"Order {order_id}: {order_summary['status']}, purchased {order_summary['date']}"

        # Main agent context stays clean
        messages = [
            {"role": "user", "content": f"{context}\n\nUser issue: {user_message}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            messages=messages
        )
        return response
```

订单查找智能体处理完整的订单历史记录并提取摘要。主智能体仅接收其实际需要的 50-100 个令牌，保持上下文集中。

当子任务生成大量上下文（超过 1000 个标记）但大多数信息与主任务无关时，当子任务定义良好，并具有明确的提取信息标准以及在使用前需要过滤的查找或检索操作时，上下文隔离是最有效的。

### 并行化

并行运行多个智能体可以让您探索比单个智能体所能覆盖的更大的搜索空间。事实证明，这种模式对于搜索和研究任务特别有价值。

Anthropic 的研究团队将此记录在 [我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。领导智能体分析查询并生成多个子代理以并行调查不同方面。每个子代理独立搜索，然后返回经过提炼的结果。通过允许探索更大的信息空间，多智能体搜索比单智能体方法显示出显着的准确性改进。

核心实现将问题分解为独立的方面，同时运行子代理，然后综合结果。

```
import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def research_topic(query: str) -> dict:
    # Lead agent breaks query into research facets
    facets = await lead_agent.decompose_query(query)

    # Spawn subagents to research each facet in parallel
    tasks = [
        research_subagent(facet)
        for facet in facets
    ]
    results = await asyncio.gather(*tasks)

    # Lead agent synthesizes findings
    return await lead_agent.synthesize(results)

async def research_subagent(facet: str) -> dict:
    """Each subagent has its own context window"""
    messages = [
        {"role": "user", "content": f"Research: {facet}"}
    ]
    response = await client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        messages=messages,
        tools=[web_search, read_document]
    )
    return extract_findings(response)
```

这种覆盖范围的扩大是有代价的。对于同等任务，多智能体系统通常比单智能体方法消耗多 3 到 10 倍的令牌。发生这种情况是因为每个智能体都需要自己的上下文，智能体必须交换消息进行协调，并且在智能体之间传递时必须对结果进行汇总。虽然与顺序运行所有工作相比，并行性有助于减少总执行时间，但由于总计算量的大幅增加，多智能体系统通常比单智能体系统花费更长的时间。

并行化的主要好处是彻底性，而不是速度。当您需要搜索大型信息空间或调查复杂问题的多个角度时，并行智能体可以比在其上下文限制内工作的单个智能体涵盖更多内容。代价是更高的代币使用量和更长的总执行时间，以换取更全面的结果。

### 专业化

不同的任务有时受益于不同的工具集、系统提示词或专业领域。与其提供单个智能体来访问数十种工具，不如提供与其职责相匹配的专用工具集的专用智能体可以提高可靠性。

#### **工具集专业化**

当智能体可以访问太多工具时，性能会受到影响。三个信号表明工具专业化将有所帮助：

1. **数量。** 智能体拥有太多工具（通常超过 20 个），很难选择合适的工具。
2. **域混乱。** 当工具跨越多个不相关的域（数据库操作、API 调用、文件系统操作）时，智能体会混淆哪个域适用于给定任务。
3. **性能下降。** 添加新工具会降低现有任务的性能，这表明智能体已达到其工具管理能力。

#### **系统提示词专业化**

不同的任务有时需要不同的角色、约束或指令，这些角色、约束或指令在组合时会发生冲突。客户支持智能体需要具有同理心和耐心；代码审查智能体需要精确且关键。合规性检查智能体需要严格遵守规则；头脑风暴智能体需要创造性的灵活性。当单个智能体必须在冲突的行为模式之间切换时，通过定制系统提示词分成专门的智能体可以产生更一致的结果。

每个专用智能体的好坏取决于其说明 - 相同 [提示词工程最佳实践](https://claude.com/blog/best-practices-for-prompt-engineering) 改进单个智能体的输出的功能适用于每个子代理的系统提示词。

#### **领域专业知识专业化**

有些任务受益于深层领域上下文，这会让通才智能体不知所措。法律分析智能体可能需要有关判例法和监管框架的广泛背景。医学研究智能体可能需要有关临床试验方法的专业知识。专门的智能体可以承载与其特定职责相关的集中专业知识，而不是将所有领域上下文加载到单个智能体中。

**示例：多平台集成。** 考虑一个集成系统，其中智能体需要跨 CRM、营销自动化和消息平台工作。每个平台都有 10-15 个相关的 API 端点。具有 40 多个工具的单个智能体通常很难正确选择，从而混淆跨平台的类似操作。通过专用工具集和定制的提示词拆分为专门的智能体可解决选择错误。

```
from anthropic import Anthropic

client = Anthropic()

# Specialized agents with focused toolsets and tailored prompts
class CRMAgent:
    """Handles customer relationship management operations"""
    system_prompt = """You are a CRM specialist. You manage contacts,
    opportunities, and account records. Always verify record ownership
    before updates and maintain data integrity across related records."""
    tools = [
        crm_get_contacts,
        crm_create_opportunity,
        # 8-10 CRM-specific tools
    ]

class MarketingAgent:
    """Handles marketing automation operations"""
    system_prompt = """You are a marketing automation specialist. You
    manage campaigns, lead scoring, and email sequences. Prioritize
    data hygiene and respect contact preferences."""
    tools = [
        marketing_get_campaigns,
        marketing_create_lead,
        # 8-10 marketing-specific tools
    ]

class OrchestratorAgent:
    """Routes requests to specialized agents"""
    def execute(self, user_request: str):
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            system="""You coordinate platform integrations. Route requests to the appropriate specialist:
- CRM: Contact records, opportunities, accounts, sales pipeline
- Marketing: Campaigns, lead nurturing, email sequences, scoring
- Messaging: Notifications, alerts, team communication""",
            messages=[
                {"role": "user", "content": user_request}
            ],
            tools=[delegate_to_crm, delegate_to_marketing, delegate_to_messaging]
        )
        return response
```

这种模式反映了有效的专业协作，拥有与其角色相匹配的工具的专家比试图保持跨所有领域专业知识的通才更有效地协作。然而，专业化会带来路由复杂性。协调器必须正确分类请求并委托给正确的智能体，错误路由会导致不良结果。维护多个专用智能体也会增加提示词的维护开销。当域可明确分离且路由决策明确时，专业化效果最佳。

## 超越单一智能体架构

除了总体框架之外，某些具体信号表明单智能体模式已经过时：

**接近上下文限制。**如果智能体经常使用大量上下文并且性能下降，则上下文压力可能是瓶颈。请注意，上下文管理的最新进展（[比如压实](https://platform.claude.com/cookbook/tool-use-automatic-context-compaction)）正在减少这一限制，允许单个智能体在更长的时间内保持有效内存。

**管理许多工具。** 当智能体拥有 15-20 个以上工具时，模型会花费大量上下文和注意力来了解其选项。在采用多智能体架构之前，请考虑使用 [工具搜索工具](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/tool-search-tool)，它允许 Claude 按需动态发现工具，而不是预先加载所有定义。这个可以 [令牌使用量减少高达 85%](https://www.anthropic.com/engineering/advanced-tool-use) 同时提高刀具选择的准确性。

**可并行的子任务。** 当任务自然分解为独立的部分（跨多个来源的研究、多个组件的测试）时，并行子代理可以提供显着的加速。

这些阈值将随着模型的改进而变化。当前的限制代表了实际指导方针，而不是基本限制。

## 以上下文为中心的分解

当采用多智能体架构时，最重要的设计决策是如何在智能体之间划分工作。我们观察到，团队经常错误地做出这种选择，从而导致协调开销，从而抵消了多智能体设计的优势。

关键的见解是采用 **以情境为中心的观点** 而不是在分解工作时以问题为中心的观点。

**以问题为中心的分解（常常适得其反）。** 按工作类型划分（一个智能体编写功能，另一个编写测试，第三个审查代码）会产生持续的协调开销。每次切换都会失去上下文。测试编写者智能体缺乏对为何做出某些实施决策的了解，并且代码审查者缺乏探索和迭代的背景。

**以上下文为中心的分解（通常有效）。** 按上下文边界划分意味着处理功能的智能体也应该处理其测试，因为它已经拥有必要的上下文。只有当上下文能够真正隔离时才应该分割工作。

这一原理是通过观察多智能体系统中的故障模式得出的。当智能体按问题类型划分时，他们会进行“电话游戏”，在每次切换时来回传递信息，从而降低保真度。在一项专门针对软件开发角色（计划者、实施者、测试者、审阅者）的智能体实验中，子代理在协调上花费的代币比在实际工作上花费的代币更多。

**有效的分解边界包括：**

- **独立的研究路径。** 调查“亚洲市场趋势”与“欧洲市场趋势”可以在没有共同背景的情况下并行进行。
- **具有干净接口的独立组件。** 通过明确定义的 API 合约，前端和后端工作可以并行进行。
- **黑盒验证。** 只需要运行测试并报告结果的验证者不需要实现上下文。

**有问题的分解边界包括：**

- **同一工作的连续阶段。** 同一功能的规划、实施和测试共享太多上下文。
- **紧密耦合的组件。** 需要不断来回的组件属于同一个智能体。
- **需要共享状态的工作。** 智能体那些需要经常同步理解的人应该保持在一起。

## 验证子代理模式

一种跨域一致有效的多智能体模式是 **验证子代理**。这是一个专用的智能体，其唯一职责是测试或验证主要的智能体的工作。

值得注意的是，功能更强大的协调器模型（如 Claude Opus 4.5）越来越能够直接评估子代理工作，而无需单独的验证步骤。但是，当使用功能较弱的编排器、验证需要专门的工具或您想要在工作流程中强制执行显式验证检查点时，验证子代理仍然很有价值。

验证子代理之所以成功，是因为它们回避了电话游戏问题。验证本质上需要最少的上下文传输，因此验证者可以对系统进行黑盒测试，而无需了解系统构建方式的完整历史记录。

### 实施多智能体系统

主要智能体完成一个工作单元。在继续之前，它会生成一个验证子代理，其中包含要验证的工件、明确的成功标准以及执行验证的工具。

验证者不需要理解为什么工件是这样构建的。它只需要确定工件是否满足指定的标准。

```
from anthropic import Anthropic

client = Anthropic()

class CodingAgent:
    def implement_feature(self, requirements: str) -> dict:
        """Main agent implements the feature"""
        messages = [
            {"role": "user", "content": f"Implement: {requirements}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[read_file, write_file, list_directory]
        )
        return {
            "code": response.content,
            "files_changed": extract_files(response)
        }

class VerificationAgent:
    def verify_implementation(self, requirements: str, files_changed: list) -> dict:
        """Separate agent verifies the work"""
        messages = [
            {"role": "user", "content": f"""
Requirements: {requirements}
Files changed: {files_changed}

Run the test suite and verify:
1. All existing tests pass
2. New functionality works as specified
3. No obvious errors or security issues

You MUST run the complete test suite before marking as passed.
Do not mark as passing after only running a few tests.
Run: pytest --verbose
Only mark as PASSED if ALL tests pass with no failures.
"""}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[run_tests, execute_code, read_file]
        )
        return {
            "passed": extract_pass_fail(response),
            "issues": extract_issues(response)
        }

def implement_with_verification(requirements: str, max_attempts: int = 3):
    for attempt in range(max_attempts):
        result = CodingAgent().implement_feature(requirements)
        verification = VerificationAgent().verify_implementation(
            requirements,
            result['files_changed']
        )

        if verification['passed']:
            return result

        requirements += f"\n\nPrevious attempt failed: {verification['issues']}"

    raise Exception(f"Failed verification after {max_attempts} attempts")
```

### 多智能体系统应用

验证子代理有效用于：

- **质量保证。** 运行测试套件、检查代码、根据模式验证输出。
- **合规性检查。** 验证文档是否符合政策要求，根据规则检查输出。
- **输出验证。** 交付前确认生成的内容符合规格。
- **事实核查。** 使用单独的智能体验证生成内容中的声明或引用。

### 早期胜利问题

验证子代理最重要的失败模式是在没有进行彻底测试的情况下将输出标记为通过。验证者运行一两个测试，观察它们通过，并宣布成功。

缓解策略包括：

- **具体标准。** 指定“运行完整的测试套件并报告所有失败”而不是“确保它有效”。
- **全面检查。** 要求验证者测试多种场景和边缘情况。
- **阴性测试。** 指示验证者尝试应该失败的输入并确认它们确实失败。
- **明确的指示。** “在标记为通过之前，您必须运行完整的测试套件”的说明至关重要。在没有明确要求全面验证的情况下，验证智能体走捷径。

## 在单智能体和多智能体系统之间进行选择

多智能体系统功能强大，但并不普遍适用。在添加多个协调智能体的复杂性之前，请确认：

1. **存在真正的限制** 多个智能体解决的问题，例如上下文限制、并行化机会或专业化需求。
2. **分解遵循上下文，而不是问题类型。** 根据需要的背景而不是工作类型来进行分组工作。
3. **存在明确的验证点** 子代理可以在不需要完整上下文的情况下验证工作。

我们的建议？从最简单、可行的方法开始，只有在证据支持的情况下才增加复杂性。

# 使用 LLM 保护源代码

> 发布日期：2026-05-27 · [原文链接](https://claude.com/blog/using-llms-to-secure-source-code) · 机器翻译，仅供学习。

模型能力正在快速但不均衡地进步。我们曾经 [与安全团队合作](https://www.anthropic.com/glasswing) 查找并修复自己的代码和开源软件中的漏洞，这项工作让我们更好地了解了如何使用模型来保护源代码。 **我们的主要收获：发现现在可以直接并行化，瓶颈已转移到验证、分类和修补**.

为了对这种差异给出一些指示，作为 [我们自己扫描](https://www.anthropic.com/research/glasswing-initial-update) 截至 2026 年 5 月 22 日，我们已披露开源软件漏洞 1,596 个。据我们所知，其中 97 个已修复。

本指南将介绍如何使用 Claude Opus 构建威胁模型，发现代码库中的漏洞，然后验证、分类和修补它们。虽然我们没有找到所有答案，但我们将分享团队如何扩展发现以及在后期阶段提供的帮助。 *今天就开始使用* [*随附的回购协议*](https://github.com/anthropics/defending-code-reference-harness) 其中包括交互式工作流程的技能和用于自主扫描的演示工具；当您阅读时，我们将指出实现每个步骤的技能。

## **查找并修复循环**

发现和修复最多漏洞的团队集中在现有最佳实践的变体上。我们将它们提炼为一系列六个步骤：

1. **威胁模型：** 在开始扫描之前确定什么算作漏洞。
2. **沙盒：** 构建沙箱环境来隔离智能体并证明漏洞利用。
3. **发现：** 让模型查找源代码中的漏洞。
4. **验证：** 独立确认哪些发现实际上是可利用的。
5. **分类：** 删除重复的结果、分配严重性并确定需要修复的优先级。
6. **修补：** 应用修复程序，确认漏洞已消除，并搜索变体。

![](images/928a59f50ef9-6a17340b26b22fa10e3ed68e-image1.png)

对威胁建模和沙盒的一次性投资为防御者的循环（发现、验证、分类和修补的重复循环）提供动力，其中瓶颈不是发现漏洞，而是发现之后发生的一切。

前两个步骤（构建威胁模型和沙箱）是循环其余部分的设置。这些通常每个代码库完成一次，并在底层系统发生变化时重新访问。接下来的四个步骤是您将针对源运行的循环：发现、验证、分类和修补。

代码库的第一次运行通常会产生最多的结果。后续运行的漏洞往往会更少（尽管通常更复杂），因为较简单的漏洞在之前的运行中已得到修补。然而，不要指望 *nth* 运行新发现为零。模型是随机的，大型代码库可能会存在一长串漏洞，即使代码未更改，这些漏洞也会继续出现。

在代码库的第一次迭代中，您应该多次运行循环，根据新发现的数量和您对该系统的风险承受能力来决定何时停止。在第一次迭代之后，继续定期扫描 (1) 或每当代码发生有意义的更改时 (2)。

接下来，我们将详细介绍每个步骤，解释它的重要性、它产生什么以及如何实施它。

## **1. 威胁模型：定义什么算作漏洞**

误报的最常见原因是模型缺乏对您的信任边界的充分了解。模型可能会将代码标记为易受攻击，因为它假设客户端可以发送损坏的值或攻击者可以控制配置，即使这些输入是 *值得信赖的* 在你的环境中。相反，模型可能会假设面向互联网的服务仅限内部使用，因此会低估真正的漏洞。在这两种情况下，模型关于威胁模型的错误是错误的，而不是代码的错误。

> *一个团队注意到他们的发现中存在一种模式：模型在具有详细记录的威胁模型、系统设计文档、要求和约束的系统上表现最佳。当威胁模型被明确定义时，模型的发现“90% 的时间都是可利用的”。*

您可以使用 Claude 分两步构建威胁模型：

**首先，从代码、文档和漏洞历史记录中引导。** 向模型提供您在第一天就会向新安全工程师提供的信息：架构文档、wiki、入口点、git 历史记录和过去的漏洞。这有助于克服仅从代码推断隐含知识、权衡和设计决策的挑战。然后，要求模型创建威胁模型，其中包括系统上下文、资产、入口点和信任边界。最后，让模型集群过去的错误并列出相关的漏洞类别。确保威胁模型记录了您关心和不关心的漏洞以及原因。

> *一个团队审查了数百个过去的 CVE 和安全修复提交，将它们提炼成“bug 形状”提示，并向模型询问两个问题：修复是否完成，是否已应用于其他地方？他们在一小时内发现了三个可利用的问题。正如他们所说：“‘人们过去利用过的东西’有时是比‘在这个代码库中找到我的漏洞’更容易成功的作弊代码。”*

**其次，让模型采访熟悉该系统的人。** 考虑 [肖斯塔克的四个问题](https://github.com/adamshostack/4QuestionFrame): *我们正在建设什么？会出现什么问题？我们正在做什么呢？我们做得好吗？* 首先运行引导步骤，这样受访者就不会从头开始。这样，他们就可以从草稿开始，而不是花费大量时间从头开始研究和构建威胁模型。虽然访谈步骤是可选的，但它添加了模型无法从代码或文档中获取的上下文，从而改善了模型的威胁。

一些做法可以产生很大的不同：

- **考虑您的依赖项的安全策略。** 许多开源项目都发布了一份。例如，vLLM [`security.md`](https://docs.vllm.ai/en/latest/usage/security.html), SQLite 的 [《黑魔法防御术》](https://www.sqlite.org/security.html), 和 [ImageMagick 的安全策略](https://github.com/ImageMagick/ImageMagick/security/policy)。您的威胁模型应直接考虑它们，而不是从头开始重建策略。
- **说出什么是可信的。** 如果您信任配置文件或经过身份验证的客户端，请将其记录在威胁模型中。这些假设有助于将不可利用的错误与实际的利用分开。
- **包括一个 `THREAT_MODEL.md` 与代码。** 将其放在存储库中并在代码更改时更新它。然后发现智能体可以在搜索之前读取它，跳过已知的非问题。

您将在两个地方使用威胁模型。在发现中，作为范围**:** 对代码进行分区，确定目标的优先级，并跳过超出范围的内容。这有助于处理无法完全扫描的大型代码库。在分类中，作为过滤器：广泛扫描后，使用威胁模型更好地校准系统和环境的严重性。

> *一个扫描大型项目的团队发现误报率为 40%，并深入研究了原因。研究结果是可重复的，并且 PoC 证明了可利用性。但拥有该代码的开发团队将其视为误报，因为这些错误不符合该项目的威胁模型。另一个团队的 CISO 简洁地说：“[模型]有很好的代码上下文，但没有很好的我们上下文。”*

**尝试一下** [**威胁-模型技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/threat-model)**.** 它会完成本节中描述的两个步骤 -`bootstrap` 从你的代码、CVE 和 git 历史记录中得出草稿，面试会引导系统所有者回答 Shostack 的四个问题来完善它。输出是一个 `THREAT_MODEL.md` 在发现和分类步骤中使用的文件。

## **2. 沙箱：安全运行智能体并验证可利用性**

**沙箱的目的之一是保护您的系统。** 为了让模型能够安全、自主地运行，需要一个强大的隔离层。如果没有它，智能体可能会超出目标并做出意想不到的事情。

> *一个团队告诉模型它没有网络访问权限（实际上它有网络访问权限），而模型发现它无论如何都可以从 GitHub 获取。另一个团队在扫描中观察到智能体回答了 GitHub 问题。这两个操作都不是恶意的，但都表明需要通过代码和配置来强制执行约束。*

将隔离与您的威胁模型相匹配。容器非常适合发现智能体读取代码，但在 microVM（如 Firecracker）或完整 VM 中运行目标及其 PoC，并锁定出口，因此任何内容都无法到达您的生产系统。并且永远没有凭证（`~/.aws`, `~/.ssh`, `.env`）可用于智能体。

仅在设置时授予沙盒网络访问权限。提取依赖项、构建、安装工具、部署目标并运行现有测试以确认一切正常。然后，对环境进行快照并删除其网络访问。在扫描期间，仅允许流量通过本地代理路由至模型API。在每次运行开始时加载快照，以便每次扫描都从相同的干净状态开始。

**沙箱的另一个目的是证明可利用性。** 在静态扫描期间，模型读取代码并假设可能会损坏的内容，但它无法测试路径是否可达或是否存在补偿控制。因此，模型可能会标记出您实际上并不关心的不可利用的代码正确性错误。当团队构建一个沙箱，智能体可以在其中编译代码、运行测试并引爆概念验证时，不可利用的发现显着下降。

> *一个进攻安全团队构建了一个安全带，为智能体提供了一个测试台，并具有简单的验证规则：只有当智能体能够构建概念验证并在测试台上运行时，这才是真正的肯定。六周后他们的评估是“最大的功效杠杆是提供模型测试床、实时系统和运行 PoC。”*

构建沙箱时，尽可能多地固定，以便每次运行在相同的环境中使用相同的代码：图像标签、提交 SHA、依赖项和构建命令。缓存本地副本，以便构建不需要网络，并且目标是使容器持久，以便多个测试循环可以加载它。

> *一个团队的扫描标记了一个漏洞，该漏洞是智能体下载旧版本库而不是实际部署的库的副产品。一位工程师发现了这一点，他阅读了脚本并发现正在下载不同的依赖项。他们现在构建 Docker 容器，其依赖项固定为与生产相匹配，因此查找智能体和验证智能体与攻击者操作的工件相同。*

构建足够忠实于生产的沙箱非常重要。排除依赖项（例如队列或数据存储）可能会导致生产中可能存在的错误报告不足。相反，忽略生产防御（例如 WAF 或身份验证网关）会导致模型报告您的生产环境已缓解的不可利用的发现。

尽管如此，如果由于云依赖性、数据存储或其他现实世界的复杂性而构建代表性沙箱不切实际，请从发现步骤（如下）开始。您不一定需要在沙箱中运行 PoC。 Frontier模型擅长通过分析源代码来发现漏洞。包括我们自己在内的多个团队发现这种方法很有效。权衡是在验证阶段，如果没有运行目标，我们就无法用 PoC 来证明发现结果，因此要预留更多时间进行验证。一旦大量的发现证明其合理性，您也可以稍后投资沙盒。

**请参阅** [**马具 `README.md`**](https://github.com/anthropics/defending-code-reference-harness/tree/main/harness)**作为参考沙箱。** 在此实现中，智能体和目标在 gVisor 隔离的容器中运行，出口锁定到模型API。目标是从固定到特定提交的 Dockerfile 构建的，其中 [`setup_sandbox.sh`](https://github.com/anthropics/defending-code-reference-harness/blob/main/scripts/setup_sandbox.sh) 处理设置阶段。

## **3.发现：提供丰富的上下文、更短的提示词和有用的工具**

为发现智能体提供对其可根据需要加载的上下文的访问权限，例如威胁模型、架构文档和过去扫描的结果。当智能体了解您的信任边界以及系统的实际部署方式时，它可以更好地识别特定于您的系统的漏洞。

我们发现前沿模型在发现阶段可以从日益简单的提示词中受益。与直觉相反，更规范的提示词会使发现变得更糟——长清单往往会降低模型的创造力并产生更少的新错误。以下是一些有助于发现阶段的提示提示：

- **提供目标和背景。** 指出“为什么”和“什么”——为什么要扫描、重要的发现是什么样的、正在扫描什么系统——并将“如何扫描漏洞”留给模型。 Frontier模型越来越擅长安全任务，而过于规范可能会缩小他们尝试的范围。
- **尝试询问特定的漏洞类别。** 如果您想关注先前 CVE 或代码库语言指导的特定类型的漏洞，请说出来。描述漏洞类别、它的作用以及它往往存在的位置，以便模型可以在您的代码库中识别它。
- **定义输出。** 要求提供包含预定义字段的结构化报告，并对它们进行排序，以便模型的推理建立在每个字段的基础上。示例字段包括理由、发现、影响、严重性等。包括逃生舱口，以便模型可以提前退出薄弱的发现。

为模型提供搜索和读取代码库的工具，例如 grep、glob 等。还让模型使用您的团队可能使用的特定于安全的工具，例如 SAST 扫描器或模糊器。询问模型特定任务需要哪些工具并提供它们。最后，让模型根据需要构建工具：最近的前沿模型越来越擅长编写他们需要的工具。

> *除了源代码之外，一个渗透测试团队还提供了智能体工具来发送请求、检查响应和查询流量日志。因此，智能体不需要猜测是否可以到达路径，并且可以针对正在运行的应用程序测试每个候选者，将其真阳性率提高到接近 100%。*

让模型首次通过系统来分区搜索空间，例如按攻击面、端点或组件。然后，将这些分区提供给并行发现智能体，这样它们就不会收敛于相同的浅层错误。最后，运行系统级传递，将分区级发现结果作为上下文来搜索漏洞。

> *尝试暴力发现的团队很快就遇到了收益递减的问题。来自一个团队：“我们最初尝试横向扩展并发送更多智能体，但回报有限。”另一个增加了焦点区域和并行智能体的数量，并遇到了“大量问题”，其中大多数是彼此重复的。*

如果您有沙箱来运行目标，请要求发现智能体构建发现结果的 PoC，例如脚本、崩溃的输入或失败的测试。构建 PoC 有助于智能体迭代并确定发现结果，并且该工件为验证智能体提供了具体的评估证据。尽管如此，智能体无法重现的发现仍然可以报告，并标记为未经证实，因此您可以保持较高的召回率。

**的** [**`vuln-scan` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/vuln-scan) 在这个阶段是有帮助的。它读取你的 `THREAT_MODEL.md`，将目标划分为重点区域，并按区域扇出并行审查智能体。输出是下一步直接使用的结构化结果。

## **4. 验证：过滤掉不可利用的发现**

发现优化召回；验证优化 *为了精确*。换句话说，发现应该发现尽可能多的漏洞——甚至是不太可能的漏洞——而验证应该排除那些实际上无法利用的发现。当智能体尝试执行以下操作时 *两者* 在同一步骤中，它可以自我审查并排除可利用的真阳性。我们通过惨痛的教训了解到了这一点，要求发现智能体也验证结果导致他们过滤掉单独验证步骤本可以确认的真实阳性结果。

验证者智能体应该独立于发现智能体。在没有共享文件系统或对话历史记录的新容器中运行验证程序。如果验证者暴露于发现智能体的推理，它可能会简单地同意而不是测试该声明。因此，仅向验证者提供 (1) 概念证明或书面发现和 (2) 代码库，以便验证者可以搜索发现者错过的缓解措施（例如，上游验证、身份验证门、类型约束或无法访问的代码）。

如果单个验证通过仍然让太多不可利用的发现通过，请尝试运行多个独立的验证程序。他们可以考虑不同的角度或使用不同的模型运行。然后，以多数票表决。还可以考虑让一个单独的法官在发现和验证智能体的结果之间做出决定。

提示词验证智能体的发现反驳了智能体的的发现。让验证者假设每个发现都是误报，并寻找发现错误的原因。包括验证者智能体可以用来确定结果是否为真阳性的明确标准。当发现智能体的输出不包含 PoC 时，这一点最为重要。旨在排除尽可能多的不可利用的发现，以减少手动审核的工作量。

> *在我们合作过的团队中，添加对抗性验证器将发现阶段不可利用的发现率大致降低了一半。要求验证者还建立一个概念验证来确认该漏洞，从而使误报率接近于零。这两个步骤一起有助于显着减少下游分类和修补负载。*

如果您能够在沙箱中充分重现生产环境（请参阅步骤 2），则提示词验证器智能体可以构建并执行可重现的概念验证 (PoC)。如果 PoC 有效，您可以断定该发现是可利用的。请注意，反之亦然——无法生成有效的 PoC 并不能证明误报。

> *一个扫描开源包的团队构建了一个验证步骤，有助于关闭循环：扫描包，生成概念证明，然后部署一个使用该包并触发 PoC 的模拟应用程序。他们的看法是：“验证是最大的障碍，而 PoC 就是验证。”*

## **5. 分类：按根本原因删除重复数据，按先决条件和影响排名**

虽然验证确认发现是可利用的，但分类会评估修补优先级。以前，当发现需要更多努力时，发现错误的工程师也会对其进行分类。现在，模型能够在午餐前找到一百个候选人，分类已成为瓶颈。

正确的分类有助于防止警觉疲劳。如果您提交了太多重复的错误或严重程度过高的错误，产品工程师可能会停止阅读它们，即使是那些需要立即修补的错误。开源维护者特别有可能被未经分类的发现所淹没，因为他们收到来自依赖其软件的许多不同用户的报告。

> *多个团队都分享了同样的教训：如果我们向产品工程师发送一堆发现，其中大多数是不可利用的，他们就会对报告失去信任并放弃。他们还优先考虑关键和重要的发现，以避免下游工程师不知所措。其他团队通过将模型指向他们现有的积压工作（之前的扫描仪、之前的模型的开放发现、错误赏金摄入量）找到了胜利，并在几天内清除了数百个过时的项目。*

要消除重复的结果，请考虑根本原因。扫描器通常会在多个调用站点标记一个错误，或报告单个根本原因的多种症状。这是一种实用的方法：首先，使用廉价的确定性传递：相同的文件，相同的类别，漏洞行号彼此在十行以内。然后，让模型对剩下的内容应用定性规则：

- **视为重复**：相同的根本原因，措辞不同；多个调用站点报告了相同的漏洞；每个端点报告缺少全局保护（如身份验证检查）；或者在同一路径中标记一个原因及其结果。
- **视为独特**：同一文件中的不同漏洞类别；不同的变量到达不同的汇点；一个助手中存在两个独立的错误；对两个端点进行相同的缺失检查，但每个端点都需要自己的修复。

如果您的工具为每个发现生成 PoC 和补丁，则消除重复发现的另一种方法是检查一个发现的补丁是否也解除了其他发现的 PoC。

重复数据删除后，根据以下内容评估每个发现的严重性：

- **可达性。** 攻击者可以从真实的入口点访问此代码，还是只能从内部代码和端点访问？
- **攻击者控制。** 不受信任的输入是否完好无损地到达接收器，或者上游是否有某些东西对其进行清理或限制？
- **前提条件。** 必须具备哪些条件才能触发该错误：非默认设置、特定功能标志、攻击者必须达到的狭窄时间窗口？
- **认证。** 未经身份验证的攻击者是否可以触发它，或者是否需要登录用户或管理员？
- **读与写。** 攻击者可以只读取数据，还是也可以修改数据？
- **爆炸半径。** 如果 PoC 发生，谁会受到影响？一个用户还是所有用户、一个租户还是平台、用户层还是内核？

要将评分细则转换为分数，请在分配严重性之前让模型写出每个问题的答案。首先检查证据可以防止模型锚定错误类别（“SQL 注入，非常关键”），然后夸大严重性以匹配。作为起点：未经身份验证的远程访问的零先决条件至关重要或高度严重。一两个前提条件，或者一条经过身份验证的路径，是中等的。三个或更多，或仅限本地，价格较低。调整您的系统的阈值。

模型可能会夸大严重性，因为它们没有足够的上下文。他们可能不知道攻击者实际控制的输入是什么，或者他们看不到补偿控制。作为前者的一个示例，如果由未经身份验证的请求触发，则 SQL 注入很关键，但如果由仅限管理的配置文件触发，则不存在问题。对于后者，上游 WAF 或防止漏洞利用的身份验证可能无法仅从源代码中看到。

解决方案是在分类过程中提供威胁模型，告诉模型您在系统中关心和不关心哪些类型的漏洞。例如，澄清“我们信任经过身份验证的客户端”可以简化或删除整个类别的批评。

> *一个团队发现，模型通常过于自信，除非有需要验证的内容，或者有更多背景信息来了解某些内容是否预计成为威胁模型的一部分。他们的解决方案是为分类智能体提供与发现智能体相同的威胁模型。*

**尝试一下** [**`triage` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/triage)**.** 它同时进行验证和分类：对每个发现进行多票验证、跨运行的重复数据删除以及根据派生的可利用性进行重新排名。输出是一个简短的、排名的、拥有的列表，而不是原始转储。

## **6. 修补：关闭循环并改善下一个周期的上下文**

修补是关闭循环并修复漏洞的地方。它还有助于根据经过验证的发现（更新信任边界或需要更多审查的组件）改善威胁模型，并将过去的发现反馈到下一次扫描的上下文中。每个周期都会强化代码库，并使下一次扫描更明智。

在修补之前，编写一个因现有代码而失败的新测试。然后，实施修复并确认相同的测试现在已通过，而不会破坏其他任何内容。 （是的，这是测试驱动开发）。如果您不添加测试，修复可能会默默地倒退，并且很难追溯证明该错误是真实的。

> *一位渗透测试人员发现他们生成的补丁不一致——有些是好的，有些是坏的——直到线束告诉模型通过针对修补的代码重新运行概念验证来验证补丁。通过提供模型反馈进行迭代，补丁质量大幅提高，节省了人工审核时间。*

模型可能会狭隘地解决特定调用站点的发现问题，而不是根本原因。只需提示模型识别并修复根本原因即可有效。然后，让模型查找两个级别的变体：(1) 相同的模式，其中在其他地方存在其他调用站点或相同错误代码的副本，以及 (2) 相同的类，其中具有一个 SQL 注入漏洞的代码库往往具有更多的 SQL 注入漏洞。使用经过验证的发现和补丁更新威胁模型以关闭循环。

在发布补丁之前，请运行对抗性检查。有新发现智能体作为攻击者探测该补丁，以确认该补丁是否全面。然后，简化生成的补丁以解决侵入性太大的补丁。最少的补丁更容易审查，并且不太可能引入新的错误。提示词用于修复根本原因的最小更改 - 无需重构、无需路过清理、无需重新格式化。

> *一个团队谈到最常见的补丁失败问题：“推荐的补丁往往具有尽可能严格的限制，以至于它们会中断与其他服务的连接。它可以解决问题，但首先会破坏允许服务正常工作的依赖关系。”*

您可以根据一系列检查来验证每个补丁，从最便宜的开始：

1. **构建。** 补丁编译并通过新测试。
2. **尝试重现。** 原来的 PoC 应该停止工作。这会捕获无效的补丁。
3. **检查回归。** 原来的测试套件仍然通过。这会捕获损坏的或过度限制的补丁。
4. **重新攻击。** 新发现智能体运行对抗性检查。这会捕获不完整的补丁。

最后，虽然模型可以编写补丁，但人类仍然需要拥有它。生成的补丁可能会以可预测的方式失败——修复症状而不是根本原因、阻止合法输入或删除对依赖服务的访问。目标是尽可能地验证每个补丁，以便减少人工审核的工作量。目标是帮助开发团队专注于模型可能不知道的细微差别（例如，传入的更改、代码风格），而补丁所需的审查和更新最少。

**尝试一下** [**`patch` 技能**](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/patch)**.** 它使用分类输出并针对每个发现生成候选差异，并由独立审阅者智能体检查每个发现。

## **开始使用**

尝试自己运行循环。克隆 [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness) 和 `run /quickstart` 在 Claude Code 中。它引导您在演示目标上完成从威胁建模到扫描到分类的交互式工作流程。该存储库还包括一个自主线束和一个 /customize 技能，用于根据您的环境更新线束。

然后，在您自己的代码上运行它。选择服务或套餐。从代码和文档中引导威胁模型，并进行采访。投资构建您的环境沙箱。扫描。使用独立的智能体验证结果。根据您的标准进行分类，并审查所有评级为高及以上的内容。修补。然后定期重新扫描。

您的第一次扫描将显示比您预期更多的发现。大多数都需要验证和分类。管道预算 *之后* 在您预算更多扫描之前进行扫描。

您可能会发现一些有用的资源：

- [Claude 安全](https://www.anthropic.com/product/security)：Anthropic的托管产品，用于智能体式漏洞检测和修补。
- [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)：具有交互式工作流程技能和自主运行演示工具的配套存储库。
- [`claude-code-security-review action`](https://github.com/anthropics/claude-code-security-review)：GitHub 操作，Claude 作为每个拉取请求的安全审核员。
- [威胁情报丰富智能体](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)：构建智能体的食谱，丰富了针对威胁情报源的妥协指标。
- [漏洞检测智能体](https://platform.claude.com/cookbook/claude-agent-sdk-06-the-vulnerability-detection-agent)：构建智能体的食谱，构建威胁模型、扫描漏洞并将发现的结果分类到结构化报告中。

## **前进**

我们相信模型会变得越来越容易 [发现并利用漏洞](https://red.anthropic.com/2026/exploit-evals) 在代码中。因此，作为防御者，我们的工作是在对手利用代码中的漏洞之前找到并修复它们。一些团队甚至将他们的工具与事件联系起来，其中错误赏金报告触发自动变体分析，安全审查触发扫描并附加候选结果，或者经过验证的漏洞更新静态分析工具以防止将来发生这种情况。

这项工作至关重要且风险很高。但如果做得好，这将是一个更大、更有希望的转变的开始，我们将在那里 *能够* 在攻击者利用漏洞之前找到并修复漏洞。

# 智能体标签中的智能体身份：用于自主、团队范围 AI 的新访问权限模型

> 发布日期：2026-06-24 · [原文链接](https://claude.com/blog/agent-identity-access-model) · 机器翻译，仅供学习。

为了使 AI智能体在人类智能体团队中发挥最佳作用，它需要访问与人类相同的工具、文档和上下文。

在“单人游戏”AI 体验（一个人与一名助手聊天）中，这很简单：您连接自己的帐户，智能体代表您进行操作。但在“多人游戏”AI 体验中 [Claude 标签](http://anthropic.com/news/introducing-claude-tag)，Claude 与许多人同时坐在一个共享频道中，它利用了属于 *工作空间*，而不是任何一个人。

为了使多人游戏体验发挥作用，Claude 需要为这些工具拥有自己的帐户，该帐户由管理员设置并绑定到工作区。我们将此访问称为模型 ***智能体身份***.

在这篇文章中，我们将解释智能体身份的工作原理、它如何将权限从每个用户转移到每个频道，以及如何在您自己的工作区中很好地确定其范围。

## **为什么“充当用户”会失败**

当您使用 AI 作为个人助理时，您可以连接 Google Drive、GitHub 和日历等平台，并让模型使用 *你的* 访问权限以读取和写入其中。

此模型不适用于 Claude 标签，原因有两个：

- **增加智能体自主权。** AI智能体能够可靠地自行完成的任务长度为 [大约每四个月翻一番](https://www.anthropic.com/institute/recursive-self-improvement)。智能体现在安排自己的任务以供稍后使用，并在发出请求的人注销后很久才响应事件。当用户设置例程来触发他们在特定情况下采取行动时，智能体基本上可以自主工作。

- **多人团队。** Claude 标签将 Claude 放置在团队已经工作的共享空间中，例如，三名工程师和一名 PM 一起调试的通道。但当有多人掌舵时，谁的权限适用？没有任何一个人的选择是永远正确的。这使管理员能够独立于相关人员来定义智能体在 Slack 中可以执行的操作，以及对 Slack 中所做操作的明确跟踪。

### Claude 充当其本身

在 Claude 标签处于活动状态的通道中，Claude 不代表单个用户进行操作。它在它接触的每个系统中都有自己的帐户：它作为 Claude 应用程序在 Slack 中发布，作为 Claude GitHub 应用程序打开拉取请求，并在管理员配置的服务帐户下查询您的仓库。

而且由于不存在个人用户凭证，共享通道永远不会成为进入某人私人文档的侧门。

### 继承权限

在智能体身份模型中，管理员在工作区级别定义一个身份（连接和技能 Claude 随处可见的基线集），并且每个渠道默认继承它。然后，在有意义的情况下，他们可以在通道级别覆盖它，例如通过授予工程通道对 GitHub 和数据仓库的访问权限，或者将 CRM 连接限制到单个专用通道。

除了凭据之外，管理员还定义：

- **存储库访问：** Claude 可以读取和写入哪个存储库。
- **连接器：** Claude 用于完成其工作的工具和 API 键。在整个组织中，不同的 API 密钥可以以不同的权限级别连接到同一服务（例如，Claude 可能在通用通道中获得只读仓库访问权限，并在数据团队的私有通道中获得写入访问权限）。
- **技能和插件：** 指令、脚本和资源文件夹 Claude 动态加载以提高专门任务的性能。
- **站立指示：** 每个通道的自定义说明和上下文。

由于此模型围绕不同的 Claude 身份工作，因此撤销该身份会结束 Claude 在使用该身份的任何地方的访问权限。与审核数十个用户帐户中的单个智能体操作相比，这需要更少的管理工作。

## 智能体身份模型的工作原理

智能体身份取代了“该用户可以做什么？”的问题。 “这个智能体在这个隔间里能做什么？”这与每用户访问控制列表不同：这意味着，如果通道的配置文件授予 Claude 该权限，则无法直接访问存储库的通道成员可以要求 Claude 读取该存储库。

这很不寻常，但我们认为这是实现适用于自主多人游戏智能体的访问模型的必要步骤。下面，我们概述了如何考虑设定这些界限。

### 身份边界如何运作

Claude标签为每个私人频道创建独特的身份；工作区中的公共频道共享工作区级别的标识。 Claude 在法律通道中的身份无法访问未在该通道中授予的代码，其在工程通道中的身份无法读取未在该通道中授予的法律文档。内存和访问尊重这些边界：Claude 在私人频道中学到的内容永远不会出现在更广泛的工作空间中。

该身份属于频道，因此默认情况下频道中的任何人都可以标记 Claude，并且管理员可以将每个频道的配置文件范围限制为权限最低的成员。在企业计划中，基于角色的访问控制让管理员可以进一步决定哪些成员可以调用 Claude，因此通道可以控制智能体可以访问的内容以及谁可以请求。

### 对工具和上下文的广泛默认访问

![](images/3280d8e2abc7-6a3a0eae87418506ee6e5b08-agent-access-scoping-2.jpg)

团队如何在 Claude 标签中确定 Claude 的工具访问范围：广泛、低风险的集成在智能体身份下的共享渠道中运行，而个人或团队特定的工具则保留在 DM 中并以用户身份运行。

在 Anthropic 中运行 Claude 标签，我们发现它的价值与工具和上下文访问相结合。每个连接的系统都使其他系统变得更加有用，因为 Claude 可以将它们之间的上下文结合起来——将来自 Slack 的线程、来自 Drive 的文档、来自跟踪器的票证以及来自仓库的查询拉入一个单一工具无法提供的答案。

充分利用 Claude 的团队是那些从一开始就授予其慷慨访问权限的团队，并根据其组织的管理首选项减少访问权限。智能体身份为管理员提供了足够广泛的范围，让 Claude 能够执行有用的跨系统工作，边界足够牢固，访问权限永远不会到达未授予的地方。我们的建议是从几个渠道的基线配置文件开始，阅读审计跟踪，然后在工作证明合理的地方扩展访问权限，一次授权一次。

对于需要更精细粒度的组织，管理员可以在特定渠道中禁用 Claude 标签。管理员还可以应用基于角色的访问控制 (RBAC) 来限制特定用户对 Claude 标签的访问。

### 直接消息

使用 Claude 标签，直接消息的工作方式与共享通道中的工作方式不同。 DM 在用户的个人 Claude.ai 帐户上运行 - 他们的连接器、凭据和结果上的名称。这使得 DM 成为使用 Claude 处理任务和使用永远不应该存在于频道中的工具的合适场所，例如电子邮件草稿或只有您拥有许可证的软件。

### 安全和审计

当管理员将连接添加到通道的配置文件时，凭证将独立存储并映射到该通道的身份，然后在请求时注入到网络边界。管理员未允许的任何主机的出站流量将被完全阻止。在审计方面，使用智能体凭据进行的每个例程、内存写入和网络调用都会被记录，并且由于 Claude 在其自己的服务帐户下运行，因此这些操作也会记录在每个连接的系统自己的日志中。

## 接下来是什么

智能体身份是Claude标签访问模型的基础。未来，我们计划加强 Claude 标签的安全产品，包括即时凭证授予（以便用户可以立即批准单个敏感操作，而无需永久扩大智能体的范围）以及为具有更复杂许可结构的组织提供身份感知覆盖。这将在智能体的范围之上添加用户级检查，因此 Claude 仅在通道的配置文件和请求用户自己的权限允许时才起作用。

Claude Tag 等产品中从单人游戏到多人游戏 AI 的转变使得长时间运行、基于团队的工作成为可能。智能体身份确保 Claude 对工具的访问范围足够广泛，足以发挥作用，但范围也足以确保企业规模的安全。

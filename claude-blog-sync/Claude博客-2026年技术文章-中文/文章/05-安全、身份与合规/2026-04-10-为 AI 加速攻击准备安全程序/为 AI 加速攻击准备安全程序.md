# 为 AI 加速攻击准备安全程序

> 发布日期：2026-04-10 · [原文链接](https://claude.com/blog/preparing-your-security-program-for-ai-accelerated-offense) · 机器翻译，仅供学习。

本周早些时候，我们宣布了 Glasswing 项目——我们紧急尝试将最新前沿模型、Claude Mythos 预览版的强大网络安全功能用于防御目的。在 [公告](https://www.anthropic.com/glasswing)——以及 [随附的技术博客文章](https://red.anthropic.com/2026/mythos-preview/)—我们描述了 AI模型如何快速减少查找和利用软件漏洞所需的资源、时间和技能。

着眼于 AI 的快速进展，我们还注意到，不久之后类似功能级别的模型就会得到广泛应用。在接下来的 24 个月内，AI模型将发现代码中未被注意到（可能长达数年）的大量错误，并将其链接到有效的漏洞利用中。事实上，公开的、子 Mythos 级别的模型已经可以 [发现严重漏洞](https://www.anthropic.com/news/mozilla-firefox-security) 传统的评论已经错过了很长一段时间。

值得庆幸的是，这是双向的：虽然攻击者可以使用 AI 移动得更快，但采用 AI 工具来保护自己的防御者也可以。在这篇文章中，我们根据我们的安全团队和研究人员在使用前沿 AI模型来保护真实代码库和系统时观察到和学到的知识，提供安全建议和实用技巧。当我们进入 AI 驱动的网络安全时代时，我们希望安全团队和其他人会发现此建议很有用。

下面的许多建议已经成为现有安全共识的一部分；我们根据我们发现哪些控制措施有效以及哪些控制措施被削弱，对它们进行了优先级排序。如果您的组织根据 SOC 2 和 ISO 27001 进行报告，这些将直接映射到您已经跟踪的控制措施。

当我们和我们的 Glasswing 项目合作伙伴继续开展网络安全工作时，我们将更新本指南。

## **现在该怎么办**

### **1. 缩小补丁间隙**

AI模型在识别未修补系统中已知的、已修补的漏洞的签名方面非常有效。将补丁反转为有效的漏洞正是这些模型Excel 所进行的机械分析。这意味着补丁发布和漏洞利用之间的时间间隔正在缩小。

- *修补所有内容* [*CISA 已知被利用的漏洞 (KEV) 目录*](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) *立即。* 此目录包含已确认正在积极利用的漏洞。此列表中可通过网络访问的任何内容都应视为紧急情况。
- *使用* [*EPSS*](https://www.first.org/epss/) *优先考虑其余的事情。* 利用预测评分系统 (EPSS) 提供每日更新的概率，表明给定的常见漏洞和暴露 (CVE) 在未来 30 天内将被利用。首先修补 KEV 列表，然后修补高于所选 EPSS 阈值的所有内容，这将帮助您将数千个开放的 CVE 转变为可管理的队列。
- *减少暴露于互联网的系统的修补时间。* 我们建议在漏洞可用后 24 小时内修补面向互联网的应用程序，并在几天内修补其他漏洞。
- *自动补丁部署和重启* 自动更新导致中断的风险是可以接受的。手动审批步骤会增加延迟，而延迟现在是主要风险。

**实用提示：** 大多数云和操作系统供应商已经提供了补丁自动化；启用它通常是一个简单的配置更改。对于容器映像和依赖项清单，多个开源扫描程序作为单个持续集成步骤运行，并使用 KEV 目录和 EPSS 中的数据注释 CVE，因此内置了优先级。

### **2. 准备好处理大量的漏洞报告**

大约在接下来的两年里，您用于接收、确定优先级和修复漏洞（无论是在您自己的代码中还是在您从供应商处购买的软件中）的流程将承受比现在更大的压力。您的漏洞管理流程应该计划来自供应商和上游的更多补丁。

- *计划增加查找量的数量级。* 摄入、分类和补救跟踪等方面需要跟上暴露的漏洞数量的增加。如果您的安全会议仍然围绕电子表格和每周会议进行，那么您不太可能跟上。值得考虑一定程度的自动化——当然，人类也参与其中，以协助处理这里的庞大数量。
- *检查开源依赖项的安全性。* 大多数软件供应链大多是开源的。大多数开源项目没有服务级别协议或维持高安全级别的承诺。 [OpenSSF 记分卡](https://securityscorecards.dev/) 自动对分支保护、模糊测试覆盖范围、签名版本和维护者活动等信号的每个依赖性进行评分。它在 CI 中运行，有助于识别未维护的包。
- *对您的供应商应用同样的期望。* 您的第三方风险管理流程应询问供应商如何 *他们* 他们自己是否正在为加速利用时间表做准备，以及他们是否正在扫描自己的代码。

‍**实用提示：** 研究评估易受攻击代码的可达性的开源软件和第三方服务。通过对更新进行回归测试，构建自动化流程，持续向您的 IT 和生产基础设施提供新的软件更新，以确保您可以快速部署它们。

上面我们提到了这些过程的自动化。 AI 可以通过多种重要方式提供帮助：

- *加快分流速度。* 分诊是一个瓶颈，因为它需要专家审查和分类。前沿模型可以针对现有待办事项删除重复的结果，利用其对资产的了解来估计风险，并在预先识别受影响的代码路径的情况下起草补救通知单。
- *检查您的依赖项是否存在冗余。* 大多数大型代码库都会积累多个执行相同工作的库（多个 HTTP 客户端；多个 JSON 解析器）。这给了攻击者更多的机会，而你却没有获得任何功能上的好处。将 LLM 指向锁定文件并询问哪些依赖项重叠（以及迁移和整合会是什么样子）是一个一小时的练习，通常会得到回报。
- *AI 升级自动化。* Frontier模型越来越有能力生成补丁以与漏洞报告一起包含。当报告清晰彻底时，甚至可能进行概念验证，模型可以直接测试补丁以确认漏洞利用路径已关闭。它还可以直接自动化接受上游补丁的过程，验证升级不会破坏测试或内部系统。
- *AI 销售*。一些小的依赖项在 OpenSSF 记分卡上的得分很低——可能是因为它们没有得到积极维护。您不应该继续依赖这些；相反，您应该考虑让 LLM 编写自己的代码来重新实现您实际使用的功能。

### **3. 在发布之前发现错误**

预防永远胜于治疗。您应该假设最终会发现到达生产环境的错误，因此您的安全测试需要提前进行。

- *将静态分析和 AI 辅助代码审查添加到您的持续集成管道中，* 并根据高置信度结果进行块合并。如果误报导致此操作不切实际，您应该保留检查，但要解决工具问题。这 [OWASP应用程序安全验证标准](https://owasp.org/www-project-application-security-verification-standard/) 定义了在三个不同严格级别下“通过”测试的情况。
- *将自动化渗透测试添加到您的持续交付管道中。* 您可以对攻击者针对您的生产系统运行的扫描进行相同的扫描。
- *确保构建管道的安全。* 可以在提交和部署之间注入代码的攻击者不需要找到漏洞。的 [SLSA](https://slsa.dev/) 安全框架提供了分级路径：较低级别确定哪个提交生成哪个工件，而较高级别使构建本身可验证。
- *采用* [*设计安全*](https://www.cisa.gov/securebydesign) *做法。* CISA 的承诺（默认多因素身份验证；无默认密码；透明的漏洞报告）是合理的最低标准。
- *新代码首选内存安全语言。* 大部分严重漏洞是内存安全错误，这些错误不会出现在 Rust、Go 或托管运行时中。 CISA、NSA 和 [NCSC](https://www.ncsc.gov.uk/) 有 [发布了有用的路线图](https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps)。现有的 C/C++ 代码不需要重写，但新的 C/C++ 代码应该需要理由。 AI 辅助重写也越来越可行。

**实用提示：** 静态应用程序安全测试 (SAST) 工具作为 CI 操作与 OWASP Top 10 和特定于语言的规则集运行，广泛可用，既是开源的，又内置于代码托管平台中（GitHub 上的 CodeQL 是最常见的起点）。为了评估构建来源，OpenSSF 发布了 [可重用的工作流程](https://github.com/slsa-framework/slsa-github-generator) 从 GitHub Actions 生成 SLSA 3 级证明；采用它的工作量比 SLSA 规范建议的要少得多。

和以前一样，使用 AI 可以明显加快这项工作：

- *AI漏洞扫描。* 这里的逻辑很简单：您应该在攻击者使用之前使用攻击者使用的相同类型的模型扫描您自己的代码和系统。这种方法只需要一个隔离的智能体、一个过滤噪声的验证步骤以及进入现有分类流程的路径。您现在就可以使用 LLM 来完成此操作。 ***如果您实现本节中的一件事，请实现它。***
- *补丁生成。* 当 SAST 或扫描仪产生结果时，前沿模型通常可以为其提出补丁。这并没有消除审查的需要，但它将开发人员的工作从“理解错误并编写修复程序”更改为“验证建议的修复程序是否正确”。后者更快。同样的方法适用于内存安全迁移：LLM 可以通过测试将独立的 C 模块移植到 Rust；审阅者可以验证等效性，而不是从头开始编写整个内容。

### **4. 查找代码中已有的漏洞**

修补程序可解决您所依赖的软件中的已知漏洞。但您自己的代码库包含未知的代码。大多数长时间运行的生产代码已经被人类审查过很多次，但从未被前沿模型检查过，而这种分析 [往往会出现新的、以前被忽视的问题](https://www.youtube.com/watch?v=_IDbFLu9Ug8)。主动扫描可以在攻击者自己发现之前识别现代 LLM 所能触及的漏洞。

- *按曝光优先。* 从解析不受信任的输入、强制执行身份验证或授权决策或可从 Internet 访问的代码开始。这些是发现最有可能产生影响的路径。
- *包括遗留代码。* 早于当前审查实践的代码，或者其原始作者已经离开的代码，通常最近受到的审查最少。这就是您从新通行证中获得最大收益的地方。
- *修复预算。* 对旧代码进行结构良好的模型扫描通常会比 SAST 部署产生更少的发现，但其中真实的比例更高。计划工程时间来修复错误。

**实用提示：** 选择一项当前所有者很少的面向互联网的服务，并扫描其输入处理和身份验证逻辑。单独运行智能体并添加验证步骤，以便您根据已确认的发现采取行动。正确完成一项服务是估算更广泛计划成本的合理基础。

### **5. 突破设计**

攻击者会试图在某个地方找到立足点。您需要限制他们从那里可以到达的范围。

缓解措施的价值来自于摩擦——发起攻击 *乏味的*——相对于硬性屏障（额外的枢轴跳数、速率限制、非标准端口、基于 SMS 的 MFA），对于那些能够通过这些繁琐步骤的对手来说，效果要差得多。我们下面的建议倾向于即使在攻击者有无限耐心的情况下也能保持控制：硬件绑定的凭据、过期的令牌和不存在的网络路径，而不是仅仅不方便的路径。

- *采用零信任架构。* 对服务之间的每个请求进行身份验证和授权，就好像它来自互联网一样。 CISA的 [零信任成熟度模型](https://www.cisa.gov/zero-trust-maturity-model) 和 NCSC 的 [零信任原则](https://www.ncsc.gov.uk/collection/zero-trust-architecture) 两者都提供了分阶段的采用路径。
- *将访问权限绑定到经过验证的硬件而不是凭据。* 生产系统和敏感的内部工具只能从具有经过验证的硬件身份并与防网络钓鱼 2FA（FIDO2 或密钥）配对的托管员工设备访问。仅凭被盗的凭据永远不足以获得访问权限。即使生产服务之间的调用也应该植根于硬件身份。
- *按身份隔离服务。*受损的构建服务器不应该能够查询生产数据库。受损的笔记本电脑应该无法访问构建的基础设施。在接收端强制执行此操作：每个工作负载都应携带自己的加密身份，并且每个服务应仅接受来自其策略名称的特定调用者的连接。网络分段仍然可以减少爆炸半径和噪音，但它只是一个后盾。
- *用短期令牌替换长期秘密。* 静态 API 密钥、嵌入式凭据和共享服务帐户密码是攻击者在使用模型辅助代码分析时首先会发现的东西。使用由身份提供商颁发的短期、范围狭窄的令牌。

**实用提示：** 完全零信任是一个多年计划，但身份感知访问代理将设备验证、MFA 门控的访问置于内部服务之前，而无需从根本上改变其架构。每个主要的云提供商都提供本机选项，并且针对本地或多云环境存在多种开源和商业替代方案。对于秘密，每个主要云都有一个托管秘密存储；将最广泛共享的单个凭证移至一个凭证中并轮换它对于其余凭证来说是一种有用的强制功能。

### **6. 减少并清点你暴露的东西**

本节基于两个重要原则。首先，你无法保卫你不了解的系统。其次，暴露的表面越小，受到攻击的程度就越小。

- *维持当前库存* 系统中每个面向互联网的主机、服务和 API 端点的信息。攻击者可以进行自动侦察；您的库存至少应该同样准确。将这些系统包含在您的渗透测试和红队中。
- *停用未使用的系统。* 没有明确所有者的遗留服务通常也未打补丁。
- *最大限度地减少每个服务公开的内容。* 默认拒绝网络入口并将 API 表面积限制为实际需要的大小。

***实用提示：*** 互联网范围内的扫描索引可公开搜索；查询您自己的 IP 范围和域，即可了解攻击者的侦察情况。对于云资产，原生库存工具（AWS Config、Azure Resource Graph、GCP Asset Inventory）已经存在；工作就是询问它们。

AI 也可以在这里直接提供帮助：

- *修剪过时的代码和系统。* 识别未使用的代码很乏味，但如上所述，AI模型擅长于乏味的任务。具有代码库和流量日志读取权限的模型可以列出没有呼叫者且未接收流量的端点；从那里，它可以解释删除每一项会产生什么影响。
- *自主外部红队。* 从外部将 AI 攻击性智能体指向您自己的周边，无需凭据，也无法访问源。然后，让它做攻击者会做的事情：计算出可到达的内容，对其进行指纹识别，并尝试将其发现的内容链接到立足点。这种自动化的红队可以捕获源扫描未发现的东西：被遗忘的主机、暴露的管理界面、默认凭据和错误配置的存储。以与库存刷新相同的节奏运行它。

### **7. 缩短事件响应时间**

漏洞可能会在补丁发布后数小时内出现。需要数天的响应过程太慢了。以下是有关如何缩短事件响应时间的一些想法：

- *将模型放在警报队列的前面。* 每个入站警报都应该在人类看到之前进行自动的首次调查。这种“分类智能体”具有对安全信息和事件管理 (SIEM) 平台的只读访问权限以及一组范围广泛的查询工具，可以将您的注意力引导到最需要人工判断的警报。
- *将仪器停留时间和覆盖范围放在首位。* 这是AI自动化最有能力移动的两个指标；当利用窗口缩短时，两者都最重要。
- *围绕事件自动进行簿记。* 在发生活跃事件期间，模型应记笔记、捕获工件、进行并行调查并起草事后分析和根本原因分析。另一方面， *人类* 应该拨打遏制电话、披露电话和客户沟通电话。事件期间的人类决策速度不应在最好交给 AI 的方面受到速率限制，例如证据收集或记录。
- *让模型驱动检测飞轮。* 摄取 [威胁情报](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)，生成候选检测，寻找匹配，并调整哪些火灾现在都在前沿模型的范围内，模型可以端到端地运行该过程。
- *运行一个桌面来处理五个同时发生的事件。*标准练习假设一个具有可用漏洞的关键 CVE 在周一命中。考虑到我们所看到的 AI 功能的改进，这可能是不明智的。要真正对您的响应进行压力测试，您应该运行同一周发生五个事件的版本。
- *地图检测覆盖范围* [*米特雷攻击&CK*](https://attack.mitre.org/)*.* ATT&CK 提供了大多数检测工具已经使用的攻击者技术的标准词汇表。了解哪些技术可以检测（哪些技术不能）比“改进检测”的总体目标更有用。您应该优先考虑横向移动和凭证访问的覆盖范围。
- *提前制定紧急变更程序。*生产补丁的两周变更批准周期本身就是一个安全风险。这同样适用于紧急遏制行动（例如使服务脱机、轮换凭证或阻止网络路径）。您应该提前决定谁可以授权这些内容以及授权的速度。

**实用提示：** 选择一个已知误报率较高的噪声规则。将前沿模型连接到其警报流中，并具有对底层数据的只读访问权限，并让它为每次触发生成结构化配置。与人工审核员衡量两周的一致性。如果一致率可以接受，则扩展到下一条规则。立即自动化整个队列是不值得的。分别地， [原子红队](https://atomicredteam.io/) 是一个映射到 ATT&CK 技术的小型安全测试的开源库；运行一些并检查您现有的日志记录实际检测到哪些是一个下午的练习，可以生成具体的覆盖图。

以下是 AI 可以帮助缩短响应时间的一些方法：

- *首次分流覆盖率 100%。* 范围明确的分类智能体可以调查每个警报（人们可能只查看高于给定严重性阈值的警报），并生成人类可以接受、拒绝或升级的结构化处置。这项工作的机制是为您的模型提供一个最小的工具集（查询、思考、报告），让它选择自己的调查策略，并根据运营指标衡量输出。
- *事件抄写员和平行调查员。* 在活跃事件期间，模型可以记录收集到的同期笔记、时间戳工件，进行响应者尚未完成的独立调查跟踪，并在事件结束后从记录中起草事后分析。这是前沿模型在安全工作中最不引人注目的应用，但它可能是影响最大的一个。
- *针对您自己的环境主动狩猎。* 可以在源代码中查找漏洞的同类智能体可以在遥测中寻找错误配置和妥协指标。您可以按照与外部攻击面扫描相同的节奏运行它。

## **向他人提交漏洞报告的建议**

如果您正在扫描代码（您自己的依赖项、开源项目或供应商产品）并向上游报告结果，那么这些报告的质量决定了是否有人对其采取行动。开源维护者已经收到了大量低质量的自动化报告，许多人已经开始忽略任何看起来由 AI 生成的内容。在不添加信号的情况下增加音量会使问题变得更糟，包括您在内。

仅当有人验证并愿意在报告上署名时才应发送报告。具体来说：

- *用通俗易懂的语言陈述该错误及其影响。* 维护者应该能够从第一段中理解出了什么问题以及为什么它很重要，而无需运行任何东西。
- *遍历代码路径。* 显示输入的输入位置、处理不当的位置以及后果发生的位置。这是区分真实发现和模式匹配的部分。
- *提供工作复制品。* 维护者可以运行的概念验证或失败的测试用例比任何数量的解释都更可信。
- *包含建议的补丁* 你 *如果你是维护者就会接受。* 补丁表明报告者对代码库有足够的了解，能够以符合项目惯例的方式解决问题。
- *预先披露 AI 参与情况。* 如果模型发现了错误或起草了报告，请在第一行中说明。无论如何，维护者都会发现；隐瞒它比披露它的可信度更高。
- *听从维护者的判断。* 如果他们拒绝这份报告，你应该接受。易于合作所带来的善意比赢得一场 bug 的争论更有价值。

**实用提示：** 在发送漏洞报告之前，一个有用的自我检查是关闭编辑器并凭记忆解释该错误。如果您在不参考模型输出的情况下无法描述出了什么问题，那么您对它的理解还不够深入，无法报告它。

## **如果您没有安全团队**

上述大部分建议都假设您的组织拥有专门的安全职能。如果您是小型组织、独立开发人员或开源维护者，则存在相同的风险，但操作更简单：

- *开启自动更新* 适用于您的操作系统、浏览器以及提供它的每个应用程序。这是最有效的单一行动，不需要持续的努力。
- *与自托管相比，更喜欢托管服务。* 让拥有安全团队的提供商来运行数据库、身份验证和电子邮件，会将修补负担转移给他们。像这样的托管服务的成本几乎总是低于一个事​​件的成本。
- *使用密钥或硬件安全密钥* 在每个支持他们的帐户上。短信代码可以被拦截，密码可以被重复使用；硬件密钥无法被钓鱼。
- *在您的代码主机上启用免费安全工具。* GitHub 的 Dependabot、秘密扫描和 CodeQL 对公共存储库免费，并且捕获了企业工具捕获的有意义的份额。启用它们需要几分钟。

*如果您维护一个开源项目，请发布 `SECURITY.md`*说明联系谁以及联系他们后会发生什么。 AI辅助扫描意味着您将收到比以前更多的漏洞报告。有些会很有价值；有些则很有价值。有些会是自动噪音。清晰的接收流程可以帮助您区分他们，并向善意的记者发出信号，表明他们的努力不会白费。

# 将 Claude Opus 4.7 与 Claude Code 结合使用的最佳实践

> 发布日期：2026-04-16 · [原文链接](https://claude.com/blog/best-practices-for-using-claude-opus-4-7-with-claude-code) · 机器翻译，仅供学习。

[Opus 4.7](https://www.anthropic.com/news/claude-opus-4-7) 是迄今为止我们最强大的通用模型，适用于编码、企业工作流程和长时间运行的智能体式任务。它比 Opus 4.6 更好地处理歧义，更有能力发现错误和审查代码，更可靠地跨会话传递上下文，并且可以在缺乏指导的情况下推理模糊的任务。

在我们的 [发布公告](https://www.anthropic.com/news/claude-opus-4-7)，我们注意到两个变化——更新的标记器和在更高的努力水平上进行更多思考的倾向，尤其是在较长会话的后期轮流中——影响了标记的使用。因此，当用 Opus 4.7 替换 Opus 4.6 时，可能需要进行一些调整才能实现最佳性能。对提示词和安全带进行一些调整可以产生很大的不同。

这篇文章将介绍 Claude Code 中的更改以及如何最有效地使用 Opus 4.7。

## 构建交互式编码会话

Opus 4.7 的令牌使用和行为可能会有所不同，具体取决于您是部署具有单用户轮次的更自主的异步编码智能体还是具有多用户轮次的更具交互性的同步编码智能体。在交互设置中，它会在用户转向后进行更多推理：这提高了其在长时间会话中的连贯性、指令遵循性和编码质量，但它也倾向于使用更多令牌。

为了充分利用 Claude Code 中的 Opus 4.7，我们发现将 Claude 更像是您委派的有能力的工程师，而不是您逐行指导的结对程序员：

- **在第一轮中预先指定任务。** 包含意图、约束、验收标准和相关文件位置的明确任务描述为 Opus 4.7 提供了提供更强大输出所需的上下文。在多次回合中逐步传达的模糊提示词往往会降低代币效率，有时还会降低整体质量。
- **减少所需的用户交互次数。** 每个用户轮流都会增加推理开销。将您的问题分批处理，并为模型提供继续前进所需的背景信息。
- **使用** [**自动模式**](https://claude.com/blog/auto-mode) **在适当的时候。** 对于您信任模型无需频繁签入即可安全执行的任务，自动模式可缩短周期时间。它特别适合您预先提供完整上下文的长时间运行的任务。自动模式现已在 Claude Code Max 用户的研究预览中可用 - 您可以使用 Shift+Tab 将其打开。
- **设置已完成任务的通知**。要求 Claude 在完成任务时播放声音，它可以创建自己的基于钩子的通知。

## Opus 4.7 的推荐工作量设置

![](images/4379c44639a2-69e1088ee4f61fecf4983993-opus-4-7-agentic-coding-p.png)

Claude Code 中 Opus 4.7 的默认工作级别现在为 `xhigh`。这是一个新的努力水平 `high` 和 `max` 这使用户可以更好地控制难题的推理和延迟之间的权衡。我们建议对大多数智能体式编码工作使用 xhigh，特别是对于智能敏感的任务，例如设计 API 和模式、迁移遗留代码以及审查大型代码库。

以下是针对每个努力级别的一些额外指导：

- **`medium` 和 `low`**：适用于成本敏感、延迟敏感或范围狭窄的工作。模型在处理更困难的任务时的能力会低于在较高工作水平下的能力，但它仍然优于在相同工作水平下运行的 Opus 4.6（有时需要更少的令牌）。
- **`high:`**：平衡智能和成本。如果您正在运行并发会话或希望减少支出而不导致质量大幅下降，请选择“高”。
- **`xhigh` （默认，推荐）**：大多数编码和智能体式使用的最佳设置。它具有强大的自主性和智能性，而不会出现 max 在长时间智能体式运行时产生的失控令牌使用情况。
- **`max`**：在真正困难的问题上挤出额外的表现，但表现出收益递减，并且更容易过度思考。有意将其用于测试模型在评估中的最大上限等任务以及对情报极其敏感和非成本敏感的用途。

如果您要升级到新的模型，我们建议您努力尝试，而不是仅仅移植旧设置。您可以在同一任务期间在工作量级别之间切换，以更有效地管理令牌使用和推理。

我们已将 Opus 4.7 的默认工作量级别设置为 xhigh，因为我们相信这是大多数编码任务的最佳设置。如果您是现有的 Claude Code 用户，但尚未手动设置您的努力级别，您将升级到 `xhigh` 自动。您仍然可以手动调整您的努力。

## 使用适应性思维进行工作

**Opus 4.7 不支持具有固定思维预算的扩展思维。** 相反，Opus 4.7 提供了适应性思维。这使得思考 *可选的* 在每个步骤中，并允许模型决定何时根据上下文使用更多思考。它可以快速响应简单的查询，在某个步骤无法从中受益时跳过思考，并将其思考标记投入到最有可能有用的地方。通过智能体式运行，这可以带来更快的响应和更好的用户体验。

适应性思维在此版本中得到了有意义的改进，特别是 Opus 4.7 不太容易过度思考。

如果你想更多地控制思维速度，直接使用提示词：

- **如果你想要更多思考，** 尝试这样说：“在回答之前仔细思考，一步一步地思考；这个问题比看起来更难。”
- **如果你想减少思考，** 尝试这样的话：“优先考虑快速响应而不是深入思考。如有疑问，请直接响应。”您将节省令牌，但可能会在更困难的步骤中失去一些准确性。

## 值得了解的行为变化

Opus 4.6 和 4.7 之间的一些默认行为发生了变化，如果您仔细调整了提示词或旧版模型的安全带，则值得了解一下。

**响应长度根据任务复杂性进行校准。** Opus 4.7 不像 Opus 4.6 那样默认详细。您可以期待简单查找的较短答案和开放式分析的较长答案。如果您的用例依赖于特定的长度或样式，请在提示词中明确说明。我们发现，你想要的声音的积极例子比消极的“不要这样做”指令更有效。

**模型调用工具的次数较少，而推理的次数较多。** 在许多情况下这会产生更好的结果。如果你想要 *更多* 工具的使用（例如，在智能体式工作期间进行更积极的搜索或文件读取），提供明确描述何时以及为何应使用该工具的指导。

**默认情况下它会生成更少的子代理。** Opus 4.7 在何时将工作委托给子代理方面往往更加明智。如果您的用例受益于并行子代理（例如，跨文件或独立项目扇出），我们建议将其拼写出来。例如：

不要为您可以在单个响应中直接完成的工作生成子代理（例如，重构您已经可以看到的函数）。当跨项目分散或读取多个文件时，在同一轮中生成多个子代理。

## 接下来要尝试什么

Opus 4.7 在长时间运行的任务上比之前的模型表现更好。这使得它非常适合监督曾经成为瓶颈的任务，例如复杂的多文件更改、不明确的调试、跨服务的代码审查以及多步骤智能体式工作。

我们建议继续努力 `xhigh` 看看你的第一个转弯会带你走多远。

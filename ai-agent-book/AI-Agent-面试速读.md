# AI Agent 面试速读：一本书讲透 Agent 工程

> 目标：用一份文档建立完整框架，并能在面试中说明“是什么、为什么、怎么做、如何验证”。
>
> 建议：先读“90 秒总述”和“面试高频题”，再按薄弱点回看对应章节。本书最重要的观点不是某个框架或 API，而是：**模型会变，围绕上下文、工具、验证构建的工程原则不会过时。**

## 1. 90 秒总述：如何定义和构建 Agent

现代 Agent 可以概括为：**Agent = LLM + 上下文 + 工具**。

- LLM 是“大脑”，负责理解、规划、决策；在强化学习视角中对应策略（Policy）。
- 上下文是“眼睛”，包括系统指令、用户需求、环境状态、历史轨迹、检索到的知识和工具定义；对应观察空间（Observation Space）。
- 工具是“手脚”，把决策变成对外部世界的读写、计算、通信和执行；对应动作空间（Action Space）。

它的基本运行方式是 ReAct 循环：**观察 → 思考/规划 → 调用工具 → 获得观察 → 修正计划**，直到达成目标、交给人、或触发终止条件。Agent 并不等于“能连续调用 LLM”；真正的难点是让它在长任务、高风险和不确定环境中仍然可靠。

生产级系统的关键是 **Harness 工程**：模型外部的上下文管理、工具接口、权限控制、结果验证、错误恢复、预算与停止机制。模型越自主，出错影响面越大，Harness 越重要。面试中可以总结为：

> 我不把 Agent 当作一个 prompt，而是把它当作一个带有观察、行动、状态和反馈闭环的软件系统。模型负责不确定性的判断，代码负责确定性的约束与验证；每一次改动都用评估证明它真的更好。

## 2. 总体架构：先约束，再自治

### 工作流、Agent 与混合式架构

工作流由程序预先确定步骤，适合规则稳定、合规严格、失败不可接受的环节，例如身份核验、支付、退款和审批。自主 Agent 自行决定下一步，适合开放式检索、诊断、规划、异常处理和跨系统任务。

推荐的落地顺序是：**先优化提示与工具描述 → 将稳定环节固化为工作流 → 仅把真正需要判断的部分交给 Agent**。实际系统往往是混合式：例如客服的查单、权限校验和付款走确定性流程；理解模糊诉求、制定补救方案和写沟通内容由 Agent 完成；高风险操作必须人工确认。

### 可在白板上画出的生产架构

```text
用户 / 外部事件
        │
意图识别、身份与权限、风险分级
        │
任务编排器 ─────→ 检索 / 记忆 / 状态栏
        │                    │
        ├──→ LLM 决策循环 ←──┘
        │         │
        │   工具选择与参数校验
        │         │
        ├──→ 低风险工具直接执行
        ├──→ 高风险工具：审核 / 人工确认
        │         │
        └──→ 结果验证、重试或降级、审计日志
                           │
                    离线评估与持续改进
```

这里要强调两条边界：**不可信内容只能作为数据，不能升级成指令；模型可以提出行动，确定性策略决定它能否执行。**

## 3. 上下文工程：决定 Agent 上限的第一杠杆

### 上下文不是聊天记录，而是 Agent 当下看到的全部世界

一次调用的上下文通常由静态前缀和动态轨迹组成：

- 静态前缀：系统提示词、角色边界、业务规则、工具定义、少量稳定知识。
- 动态轨迹：用户请求、工具返回、当前任务状态、临时检索结果和中间结论。

许多“模型不够聪明”的问题，本质是它没有看见关键事实，或看见了太多无关内容。固定模型后，最有效的能力杠杆通常是扩展或重构观察空间与动作空间，也就是改善上下文和工具；但不是把所有资料都塞进去，而是做到**相关、按需、可控**。

### KV Cache 与提示词设计

Transformer 会缓存前缀计算结果（KV Cache）。因此应让稳定内容尽量位于前缀并保持不变，把用户特有、频繁变化的内容置于后部；不要每一轮重写系统提示或插入随机内容，否则会丢失缓存收益并增加成本、延迟。

好的系统提示词不是规则堆砌，而是可执行的 SOP：目标、边界、决策顺序、例外处理、输出格式和升级条件。把 prompt 当代码管理：版本控制、评审、回归评估、模块化拆分。若 Agent 经常选错工具，优先检查工具描述和边界案例，而不是马上换模型。

### Skills、状态栏与压缩

- **Skills**：把大量低频、专业、易变的说明写成可按需加载的文件；常驻的只应是名称、描述和触发条件。它以检索替代了平铺工具列表，降低选择过载。
- **状态栏**：用确定性代码维护“目标、进度、已确认事实、失败原因、剩余预算、待确认事项”等结构化状态，避免模型从长轨迹里自己统计。状态栏是高优先级信息源，必须可观测、可测试，不能让 LLM 随意编造。
- **上下文压缩**：长任务不能简单截断历史，否则会重复调用、忘记约束或误判完成。正确做法是把大输出落盘，保留摘要、关键决策、标识符、证据来源和未完成事项；原文可按需回溯。压缩是有损的，所以需要“摘要 + 原始资料索引”的双层设计。

### 提示注入的面试回答

检索文档、网页、邮件和工具返回都可能含恶意指令，不能因为它们出现在上下文里就赋予同等信任。防线包括：数据与指令分层、外部内容标记为不可信、最小权限、敏感操作二次确认、结构化参数校验、独立审核器只读取结构化调用信息，以及完整审计。核心原则是：**不要试图只靠模型“识别坏指令”，要让即使模型被诱导也没有越权能力。**

## 4. 记忆与 RAG：解决跨会话与私有知识问题

### 三者怎么区分

| 机制 | 解决什么问题 | 更新速度 | 典型内容 |
| --- | --- | --- | --- |
| 上下文 | 当前任务暂时状态 | 每轮 | 对话、工具结果、当前计划 |
| 记忆 / RAG | 跨会话、可更新的外部知识 | 分钟到天 | 用户偏好、公司文档、历史案例 |
| 微调 / 后训练 | 稳定且可泛化的行为模式 | 周到月 | 格式、风格、工具策略、能力 |

不要用微调来记住频繁变化的事实；不要把每段对话都塞进上下文；也不要把 RAG 当成“检索到资料就一定正确”。先分析问题是缺事实、缺当前状态、缺工具，还是模型本身不会完成该策略。

### 用户记忆

用户记忆从简单事实笔记逐渐升级为带有来源、时间、置信度、适用范围和冲突关系的结构化情境卡片。成熟实践是双层记忆：

1. 少量稳定的用户画像/偏好常驻，提供概览；
2. 细节按需检索，并附来源和时间，支持冲突消解与删除。

必须考虑隐私、用户可见与可编辑、过期策略、撤回/删除，以及“记忆内容本身也可能被注入”的风险。

### RAG 的完整回答框架

RAG 的目标不是“向量检索”，而是在正确时间把正确证据送到模型面前。典型链路是：

```text
解析与清洗 → 合理分块 → 建索引 → 召回候选 → 混合检索 → 重排序 →
带来源的上下文组装 → 生成 / 验证 / 引用
```

- 分块要保留语义边界和元数据；只有固定字数切块容易割裂上下文。
- 稠密向量检索擅长语义相似，BM25 等稀疏检索擅长专名、数字、代码和精确关键词；生产中常采用混合召回。
- 重排序在较小候选集上做精排，通常比盲目增大 top-k 更有效。
- 用 Recall@k 等指标评估“答案证据是否被召回”，再单独评估最终答案，避免把检索失败和生成失败混为一谈。
- 对全局理解、多跳关系，可采用层次摘要（如 RAPTOR）、实体关系图（GraphRAG）或由 Agent 主动制定多轮检索计划。

## 5. 工具与 MCP：让 Agent 能做事，也能安全地做事

### 工具设计原则（ACI）

工具应按 Agent 的目标设计，而不是机械映射底层 API。核心权衡是粒度、通用性、参数复杂度、变更频率和模型能力：高频、参数复杂、风险高的能力适合专用工具与强 schema；变化快、低频的操作可用 Skill + 通用执行器表达。

一个好工具需要明确：何时使用、何时不用、输入/输出 schema、约束、代价、异常和真实示例。参数传递必须保真，不能在模型不知情时静默改写输入、追加参数或截断结果；否则模型看到的世界和工具操作的世界不一致，会形成无法自我诊断的循环失败。

常见工具可分为感知、执行、协作、事件触发和用户沟通五类。感知操作通常只读，适合缓存和并行；执行操作有副作用，必须严格控制顺序、权限和幂等性。

### MCP 的价值与风险

MCP 提供工具与上下文连接的标准化互操作方式，降低了接入成本；但每接入一个第三方服务器，也就引入一个新的信任边界。风险包括工具描述投毒、同名工具遮蔽、供应链更新被劫持和凭证滥用。

因此要审查描述、锁定版本、最小权限发放短期凭证、为工具建立可信身份与命名空间，并将高风险调用交给独立 Sidecar 审核器。尤其警惕“致命三要素”同时存在：**可访问私有数据、会处理不可信内容、能够对外通信**；三者连通后，提示注入就可能升级为真实数据外泄。

### 高风险执行的分层防线

1. 输入与 schema 校验：路径、金额、命令、参数类型快速失败，不做“智能纠错”。
2. 策略与权限：按用户、资源、环境、动作和参数动态评估风险，不只按工具名称分级。
3. 沙箱与最小权限：限制目录、网络、凭证范围、速率和资源预算。
4. 提议者—审核者：Agent 先提出行动，独立规则或模型审核；审核者只看结构化数据，避免被自然语言注入操纵。
5. 人工确认与事后验证：不可逆、资金、权限、对外发送操作须确认；执行后读取真实状态验证结果并写审计日志。

## 6. Coding Agent：为什么“代码 + 文件系统”是元能力

Coding Agent 的典型闭环是：理解需求 → 搜索代码与文档 → 制定最小修改 → 编辑 → 运行测试/检查 → 根据真实反馈修复 → 汇报证据。它之所以成熟，不只因模型擅长写代码，更因为软件工程已有测试、类型系统、版本控制、CI 和代码审查这些天然 Harness。

代码是 Agent 的元能力：它既能完成任务，也能把复杂推理外化为可运行、可验证的程序，还能创造工具、适配新系统、生成 UI 或让子 Agent 协作。对于多工具批处理，让模型生成脚本在执行环境里保存中间变量，最后只返回结构化结论，通常比每步都经过 LLM 更省 token、更稳定。

面试中要避免说“让 Agent 自我修改就会越来越强”。正确表述是：**自我修改必须是小范围候选变更，经过测试、评估、灰度发布和可回滚治理；没有验证器的自我改进只是放大错误。**

## 7. 评估：没有评估，就没有可靠迭代

评估闭环是：**可复现环境 → 代表性数据集 → 自动/人工判定 → 统计分析 → 定位失败 → 系统改进 → 回归验证**。这是把 Agent 工程从经验调参变成科学工程的基础。

### 评什么

- 结果：任务成功率、事实正确性、完整性、用户价值。
- 过程：工具选择、步骤数、重复调用、是否遵守关键流程。
- 可靠性：不同随机种子、页面变化、API 抖动和长程任务下的稳定性。
- 安全：越权、数据外泄、危险操作和合规违规应是一票否决项。
- 资源：延迟、token、工具调用次数、重试次数、单任务总成本。

### 必会指标

- **Pass@k**：尝试 k 次至少成功一次，衡量能力上限。
- **Pass^k**：尝试 k 次全部成功，衡量稳定可靠性。
- **Best@k**：k 次中最佳得分，适合开放式、连续评分任务。

不要用 Pass@k 掩盖关键业务的不稳定性。例如单次成功率 60% 时，Pass@5 约为 99%，但 Pass^5 只有约 7.8%；一个“总有一次能成功”的 Agent 并不适合付款或生产变更。

### LLM-as-a-Judge 怎么用才可信

开放任务没有唯一标准答案时，可让 LLM 按 Rubric 评分。Rubric 应由领域专家定义，覆盖正确性、完整性、过程、安全和常见陷阱；评分档位必须有可验证行为和边界案例，明确防止幻觉、冗长、关键词堆砌等奖励作弊。

上线前要用人工金标集校准评判模型，持续抽检成功/失败/边界样本；重要任务可采用异构多评委。LLM Judge 是规模化的近似，不是免除人工判断的理由。

## 8. 后训练与持续进化：把经验变成可验证的能力

### SFT 与 RL

预训练获得通用语言与世界知识；**SFT（监督微调）**用高质量示例稳定格式、风格和已有模式；**RL（强化学习）**通过环境反馈优化长程决策与泛化策略。可记成书中的结论：**SFT 更擅长记忆，RL 更擅长泛化**；二者常是先后关系，先让输出格式可用，再让 RL 学会在环境中做决策。

真正拉开差距的常常不是某个 RL 算法，而是高保真环境、有效奖励和任务数据分布。只奖励最终成功会造成稀疏反馈与信用分配困难；需要引入过程信号、可验证子目标，并惩罚“结果碰巧对但路径危险/违规”的行为。模拟环境能扩大训练规模，但模拟偏差也会成为能力上限。

### 持续进化的四种更新载体

从运行轨迹获得证据后，应把问题放到最合适的位置修复：

| 更新载体 | 适合解决的问题 | 特点 |
| --- | --- | --- |
| 知识文档 / 记忆 | 新事实、案例、用户偏好 | 更新快、可追溯 |
| Prompt / Skill | 操作规范、决策启发式 | 成本低、易验证 |
| 程序 / Harness | 确定性规则、校验、工具缺陷 | 可测试、可靠性高 |
| 模型参数 | 稳定且跨任务可泛化的行为 | 成本高、风险与验证成本也高 |

线上执行与离线学习必须分离：线上只记录证据和轨迹；离线生成候选修改、评估、灰度发布、监控，再保留或回滚。优先做局部、可归因、可验证、可回滚的更新，避免把一条偶然失败直接写入长期记忆或模型参数。

## 9. 多模态、实时与多 Agent

### 多模态和实时交互

语音 Agent 的架构从级联式 ASR → LLM → TTS，演进到端到端全模态，再到可打断、边听边想边说的全双工模式。核心取舍是质量、可控性、首响应延迟和打断处理。Computer Use 通过截图感知与鼠标键盘操作进入 GUI 世界，但每一步都要面对页面变化、定位误差、长程步骤累积和高延迟，因此仍应优先 API/结构化工具，GUI 作为兜底。机器人则进一步要求视觉—语言—动作模型、实时闭环和 Sim2Real 泛化。

一句话概括：多模态不是“多接一个输入”，而是把 Agent 放进持续变化的物理/交互环境，因此要重新设计延迟、状态同步、打断、容错与安全边界。

### 多 Agent 的正确使用方式

多 Agent 的两个正交维度是：

- 上下文共享还是独立：共享信息无损但上下文膨胀；独立 Agent 通过文件、消息或精炼交接包协作，隔离性更好。
- 协作拓扑：对等互审适合少量迭代；管理者—执行者适合复杂动态分工；去中心化适合职责对等、控制权需要流转的系统。

多 Agent 并非天然优于单 Agent。关键判断是：协作是否带来了单 Agent 在同等计算预算下没有的新信息，例如代码执行、网页观测、独立检索、渲染截图或外部验证。若只是多个 Agent 反复阅读同一段文本并投票，往往只是在增加成本和通信噪声。

一个实用分工是“规划者—执行者—验证者”：最强模型承担规划，执行者访问工具，验证者基于真实环境结果判断是否完成。循环的瓶颈通常在验证器，而不是再增加一轮自我反思。

## 10. 面试高频题：可直接使用的回答骨架

### Q1：如何从零设计一个企业 Agent？

先明确用户目标、风险边界和不可接受的失败，再把任务拆成确定性步骤与需要判断的步骤。为后者设计最小上下文、可靠知识源和按风险分层的工具；再定义离线评估集、线上监控指标和人工兜底。先用工作流跑通高频路径，记录失败轨迹后再把自治能力逐步扩展。上线不是终点，必须有评估、灰度、回滚和审计闭环。

### Q2：如何降低幻觉？

先区分三类根因：缺事实就用检索并要求引用证据；缺当前状态就用工具读取真实环境；模型把不确定内容当结论，就要求声明不确定性、使用结构化验证和必要时升级人工。不能只靠一句“不要幻觉”的 prompt；更可靠的是让重要结论可追溯、重要动作可验证、严重错误可阻断。

### Q3：RAG、记忆、微调分别什么时候用？

频繁变化或私有事实用 RAG；跨会话的用户偏好和长期状态用记忆；稳定且需要泛化的行为模式、格式或策略用微调/后训练。选择依据是知识变化频率、个性化程度、是否需要可解释与删除，以及错误成本。

### Q4：长任务为什么容易失败，如何治理？

轨迹变长会造成上下文膨胀、注意力分散、KV Cache 成本上升、关键状态丢失和重复调用。用状态栏显式维护任务事实，用摘要与文件系统外化大结果，设置步骤/时间/成本预算，检测重复工具调用和连续失败；让子任务隔离上下文，达到阈值时恢复、降级或人工接管。

### Q5：如何保证工具调用安全？

将风险精确到“工具 + 参数 + 资源 + 用户身份”，而不是只给工具贴标签。前置做 schema/策略校验和最小权限；高风险动作用独立审核器、沙箱和人工确认；执行后读取真实状态验证，并保留审计日志。第三方 MCP 同时按供应链处理：审查、版本锁定、凭证隔离、命名空间和持续监控。

### Q6：怎样衡量 Agent 变好了？

不能只看主观体验或单次成功率。建立代表真实分布且无泄漏的测试集，在可复现环境中同时评结果、过程、安全、成本、延迟与稳定性；开放任务用经人工校准的 Rubric 和 LLM Judge。对关键业务看 Pass^k 而不是 Pass@k；每次优化必须做回归和统计显著性检查。

### Q7：什么时候使用多 Agent？

当任务可并行、角色有互补工具/权限、或需要独立外部验证时使用；例如研究任务的并行检索与交叉核验、代码生成后的测试与审查。若所有 Agent 只共享同样文本、没有新观测，则单 Agent + 更好的工具/验证器通常更简单、成本更低。

### Q8：如何做成本与延迟优化？

先从评估中定位瓶颈，而非盲目换小模型。常用手段包括：稳定前缀复用 KV Cache、减少无关上下文、检索后重排、压缩大工具返回、读操作并行、模型路由、把多步工具编排放入脚本执行、为任务设置预算与早停。最终看单次 API 价格没有意义，应看“成功完成一个任务的总成本”。

## 11. 容易失分的表述与更好的说法

| 容易失分 | 更好的工程表述 |
| --- | --- |
| “加个 Agent 就能自动化。” | “先判断任务中哪些环节需自治，哪些应由工作流或人工控制。” |
| “RAG 能解决幻觉。” | “RAG 只能提高证据可得性；还要评估召回、要求引用并验证关键结论。” |
| “多 Agent 会更聪明。” | “只有带来独立观测、工具能力或验证信号时，多 Agent 才可能优于单 Agent。” |
| “让模型自我反思直到成功。” | “必须有外部验证、预算、停止条件和升级路径；自我声明不能证明成功。” |
| “安全靠 system prompt。” | “Prompt 只能影响倾向，安全要靠权限、隔离、确定性校验和人工审批。” |
| “评测跑一次成功了。” | “要看任务分布、稳定性、对抗样本、成本和回归；关键业务需要 Pass^k。” |

## 12. 最后背下来的十句话

1. Agent = LLM + 上下文 + 工具；模型负责判断，系统负责把判断变成可靠行动。
2. ReAct 是“观察—行动—再观察”的闭环；没有真实反馈就很容易假完成。
3. 在模型固定时，上下文与工具往往是最大的能力杠杆。
4. 上下文工程的目标不是塞更多 token，而是提供更相关、更结构化、更可追溯的信息。
5. RAG 解决知识可得性，记忆解决跨会话状态，微调解决稳定的可泛化行为。
6. 工具要按 Agent 目标设计，参数与返回值必须保真；高风险操作必须分层防护。
7. Harness 是 Agent 的竞争力：权限、验证、恢复、预算、审计和人机协作缺一不可。
8. 评估是迭代的地基；没有可复现评估，就无法证明一次改动是真进步。
9. SFT 与 RL 的核心差异不在名词，而在数据、环境、奖励和可验证反馈。
10. 多 Agent 的价值来自新信息和外部验证，不来自“多几个模型一起聊天”。
